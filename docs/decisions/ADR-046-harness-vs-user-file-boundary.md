# ADR-046: 하네스 소유 파일과 사용자 소유 파일의 경계

- Status: Accepted
- Date: 2026-07-19
- PR: (이 PR)
- Extends: ADR-020 (project-scope default + install log)
- Context:

  한 사이클(v26.121.0~125.0) 안에서 **같은 질문이 세 번 다른 얼굴로** 나왔고, 그때마다 그 자리에서
  즉흥으로 답이 정해졌다. 질문은 하나다 — **하네스가 사용자의 파일에 무엇을 해도 되는가.**

  | 언제 | 그때의 질문 | 그때의 답 |
  |------|-------------|-----------|
  | F-1f | uninstall 이 `.mcp.json`·`.gitignore` 를 지워도 되나 | 안내만 하고 안 지운다 |
  | F-1 위저드 | install 화면에서 체크 해제하면 지워야 하나 | 안 지운다. 제거는 `uninstall` 로만 |
  | R-3a | update 가 사용자가 고친 스킬을 덮어써도 되나 | (본 ADR 에서 결정) |

  셋을 따로 정하면 서로 모순될 수 있다. 실제로 **모순 직전까지 갔다**: F-1 은 "하네스는 사용자
  것을 지우지 않는다"를 세웠는데, `update` 는 이미 `rules`·`hooks`·`CLAUDE.md` 를 **아무 확인 없이
  덮어쓰고** 있었다(`update-mode.ts:106-118`, `:88-91`). 원칙과 코드가 이미 어긋나 있었고, 아무도
  그걸 결정으로 기록한 적이 없어서 어긋난 줄도 몰랐다.

  **R-3a 의 실제 증상**: `update` 의 대상 목록에 `skills` 가 아예 없다(`update-mode.ts:53-78`).
  `templates/skills/` 28개는 첫 설치 때만 복사되고 그 뒤로 영원히 고정된다. 렌더는
  `updateMode.updated` 를 순회하므로(`install-render.ts:431`) **행 자체가 안 나온다** — 거짓
  주장은 없지만 사용자가 누락을 알아챌 단서가 0이다. 결과적으로 스킬 개선분에 **기존 사용자에게
  가는 통로가 없다.**

- Decision:

  **파일의 소유자를 기준으로 세 동사의 권한을 고정한다.** 소유자 판정은 추정이 아니라 **설치
  시점 sha256 대조**로 한다 (선례: `rootClaudeMd { path, sha256 }`, `install-log.ts:74`).

  | 파일 | install | update | uninstall |
  |------|---------|--------|-----------|
  | 하네스가 만들고 사용자가 안 고침 | 쓴다 | **덮어쓴다** | 지운다 |
  | 하네스가 만들고 **사용자가 고침** | 백업 후 쓴다 | **`.bak` 남기고 덮어쓴다** | **안 지운다** |
  | 사용자 파일에 병합(`.mcp.json`·`.gitignore`) | 병합한다 | 보존 | **안 지운다, 안내만** |
  | `.claude/` 밖 (`.github/workflows/`) | 만든다 | 건드리지 않는다 | **안 지운다, 안내만** |

  파생 규칙 셋:

  1. **install 은 제거하지 않는다.** 위저드 체크 해제는 "안 깐다"이지 "지운다"가 아니다. 설치
     화면 안의 삭제는 실수 한 번이 되돌릴 수 없는 삭제가 된다. 제거 동사는 `uninstall` 하나뿐이다.
  2. **update 는 최신화가 기본이고, 사용자 편집분은 잃지 않는다.** 편집분을 이유로 갱신을
     건너뛰지 않는다 — 그러면 R-3a 가 그대로 재현된다. 최신판을 자리에 놓고 편집분을 `.bak` 로
     남긴다. **최신판이 활성, 편집분이 백업** — 반대가 아니다 (사용자 결정 2026-07-19).
  3. **판정 불가는 보수적으로 처리한다.** 해시 기록이 없는 레거시 설치는 "안 고쳤음"을 증명할 수
     없으므로 내용이 다르면 `.bak` 를 남긴다. 첫 업데이트 한 번만 시끄럽고 그 뒤로는 정확해진다.

  install log 스키마를 두 번 확장한다 (ADR-020 확장):
  - `rootFiles[]` — `.claude/` 밖 생성/수정분 (F-1f, v26.124.0 선반영)
  - 스킬 파일별 `sha256` — 위 소유자 판정의 근거

- Alternatives:

  - **update 가 사용자 편집분을 건너뛴다** — 편집분은 안전하지만 그 스킬은 영원히 낡는다. R-3a
    를 파일 단위로 축소 재현하는 것이라 기각.
  - **전부 덮어쓴다 (rules·hooks 와 동일 취급)** — 코드는 가장 단순하나 파생 규칙 1과 정면 충돌.
    스킬은 rules 와 달리 사용자가 자기 워크플로에 맞춰 손대는 물건이다.
  - **최신판을 `.new` 로 병기하고 편집분을 자리에 둔다** — 최신판이 비활성이라 사용자가 병합할
    때까지 개선이 실제로 적용되지 않는다. 사용자가 활성/백업 방향을 명시 선택했다.
  - **레거시 설치를 "안 고침"으로 간주하고 조용히 덮어쓴다** — `.bak` 노이즈는 없지만 증명 없이
    편집분을 파괴할 수 있다. 비가역 손실 > 일회성 노이즈.
  - **F-1 과 R-3a 를 별개 ADR 로 분리** — 같은 경계 질문의 두 적용례라 분리하면 다시 모순 위험.

- Consequences:

  - `update` 가 스킬을 갱신하기 시작하면서 **스킬 개선분에 배달 통로가 생긴다.** 이 통로가 없으면
    새 스킬을 만들어도 신규 설치자에게만 도달한다.
  - 레거시 사용자의 첫 업데이트에서 `.bak` 가 최대 50개(파일 수 상한) 생길 수 있다. 비가역이
    아니고 1회성이다. 렌더에 보존 건수를 노출해 놀라지 않게 한다.
  - install log 가 커진다 — 파일 50개 × 해시 1건. 실측 기준 수 KB 로, 조회 성능에 영향 없다.
  - `rules`·`agents`·`commands`·`hooks` 는 **현행 유지(무조건 덮어쓰기)**. 본 ADR 은 그 동작을
    바꾸지 않고 "그렇게 하기로 한 것"으로 명시만 한다. 사용자 편집 빈도가 낮고 하네스 규약의
    SSOT 라 최신화가 우선이라는 판단 — 반증(편집분 손실 보고)이 나오면 스킬과 같은 처리로 승격한다.
  - 새 lifecycle 동사(예: `sync`)를 추가하려면 위 표에 행을 추가해야 한다 — 표가 SSOT 다.
