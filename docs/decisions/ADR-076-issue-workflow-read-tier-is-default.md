# ADR-076: 이슈 워크플로 스킬의 읽기 단계를 기본 활성으로 내린다

- Status: Accepted
- Date: 2026-08-17
- PR: #321
- Context / Decision / Alternatives / Consequences: 아래

## Context

`gh-issue-workflow` 스킬은 전 트랙 상주로 설치되지만, 활성 조건이
`docs/SPEC.md` 에 `issue_tracking: enabled` 한 줄이 있을 때만이었고 **없으면 스킬이 통째로
skip** 됐다. 그 플래그가 활성화의 SSOT 였다.

실측(2026-08-17, 이 저장소): 플래그가 **없다**(`grep -n issue_tracking docs/SPEC.md` → exit 1).
그 상태로 열린 이슈가 6건(#294 #295 #297 #301 #305 #316) 있었고, 에이전트는 작업을 시작할 때
그 6건을 **한 번도 읽지 않았다**. 사용자가 이슈로 활발히 일하는 저장소에서도 그랬다.

즉 스킬이 설치돼 있다는 사실과 작동한다는 사실이 달랐고, 그 차이를 아무도 볼 수 없었다.

이 결정이 ADR 인 이유: **설치받는 낯선 저장소의 동작이 바뀐다.** `change-management` 기준
Major CR 이고, 이 저장소는 더 작은 동작 변경에도 ADR 을 썼다(ADR-063 5자산 opt-in ·
ADR-074/075 위저드).

## Decision

활성 조건을 **한 단계 → 세 단계**로 나눈다.

| 단계 | 조건 | 허용 |
|---|---|---|
| 비활성 | GitHub remote 없음 또는 `gh auth status` 실패 | 없음 (에러도 안 낸다) |
| **읽기 (기본)** | remote + `gh` 인증 | 이슈·코멘트 **읽기**. 등록 **제안** |
| 적극 | `docs/SPEC.md` 에 `issue_tracking: enabled`, 또는 **사용자가 이 세션에서 이슈 등록·계층화를 명시적으로 요청** | 요청이 오면 이슈 초안을 먼저 보이고 승인 후 등록 |

**원격 쓰기 규칙은 어느 단계에서도 바뀌지 않는다** — `WRITE`/`UPDATE` 는 사용자가 그 변경을
요청했을 때만 하고, 실행 전에 영향받는 이슈 번호와 바뀔 내용을 보여준다.

적극 단계의 두 번째 가지는 **관측 가능한 술어**로 쓴다. 초안에 있던 *"사용자가 이슈 기반으로
일하겠다고 했거나"* 는 대화 맥락에 대한 에이전트의 해석이라 사후에 아무렇게나 성립한다 —
독립 리뷰가 "자물쇠 없는 두 번째 문"이라고 지적했고, 그 지적이 맞다.

## Alternatives

- **구본 유지(전면 opt-in)** — 기각. 위 실측이 그대로 재발한다. 문제는 스킬이 없는 것이 아니라
  있는데 안 도는 것이었다.
- **적극 단계를 기본으로** — 기각. 이슈를 안 쓰는 저장소에서 매 요청마다 등록을 권하게 되고,
  그건 잡음이자 원격 쓰기 표면에 대한 상시 압박이다.
- **위저드에서 설치 시 묻기** — 보류. 질문 +1 의 비용이 이득을 넘는지 판단할 근거가 없고,
  읽기 기본은 파괴적이지 않아 물어서 얻을 것이 적다. 적극 단계 기본값을 나중에 바꾸게 되면
  그때 재고한다.

## 적용 범위

`templates/skills/gh-issue-workflow/SKILL.md` 의 활성 조건과 그 descriptor. **다른 스킬의
활성 조건에는 적용하지 않는다** — 읽기가 무해한 것은 이 스킬의 읽기가 원격을 안 바꾸기
때문이고, 그 성질은 스킬마다 다르다.

## Consequences

**얻는 것**: 설치 직후부터 에이전트가 착수 전에 열린 이슈와 코멘트를 읽는다. 결정이 코멘트에
있는데 본문만 읽고 시작하는 형태가 닫힌다.

**치르는 것**:
- 낯선 저장소에서 `gh issue list` / `gh issue view --comments` 가 사용자 토큰으로 실행된다.
  원격 변경은 없지만 **컨텍스트 오염 비용**이 있다(열린 이슈가 많은 저장소에서 특히).
  이 비용은 아직 계측하지 않았다 — 스킬 본문이 목록 범위를 제한하지만 상한은 없다.
- 활성화의 SSOT 가 "파일 한 줄"에서 "세 조건"으로 늘었다. grep 하나로 판정하던 것이
  판정 절차가 됐다.

**되돌리는 법**: 활성 조건 표에서 읽기 행을 지우고 구본 문장(`issue_tracking: enabled` 없으면
자동 비활성)을 되살린다. 코드 변경은 없다 — 스킬 본문만 움직인다.

**남은 결정**: 적극 단계를 위저드에서 고르게 할지(#318). 이 ADR 은 읽기 기본만 확정한다.
