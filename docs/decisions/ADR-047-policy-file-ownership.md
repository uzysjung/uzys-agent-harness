# ADR-047: 정책 파일에도 소유자 판정을 적용한다

- Status: Accepted
- Date: 2026-07-20
- PR: (이 PR)
- Extends: ADR-046 (하네스 소유 파일과 사용자 소유 파일의 경계)

## Context

ADR-046 이 "하네스가 사용자 파일에 무엇을 해도 되는가"의 답을 정하고 v26.126.0 으로 구현됐다.
그런데 **실제 커버리지는 `.claude/skills/` 뿐이었다.** 같은 `update` 실행 안에서:

| 자산 | 덮어쓰기 | 삭제 |
|------|----------|------|
| `.claude/skills/` | sha256 기준선 대조 → 편집분 `.backup-<stamp>` | 하지 않음 (ADR-046 명시) |
| `.claude/rules` · `agents` · `commands` · `hooks` | **`copyFileSync` 무조건** | **`unlinkSync` 무조건** |

`install` 은 더 좁았다 — `backupFileIfChanged` 가 걸린 건 `.claude/settings.json` **하나뿐**이고,
기존 설치 위 `install`(= `add` 모드)은 `resolveBackupPath` 에서 `.claude/` 통짜 백업도 받지 않는다.
즉 재설치가 사용자가 고친 룰·훅을 흔적 없이 밀었다.

사용자 보고로 드러났다: "재설치하면 rules, hooks 를 그냥 덮치는 것 같다."

근본 원인은 ADR-046 이 **문제를 자산 종류로 좁게 잡은 것**이다. 결정 자체("사용자가 쓴 것은
잃지 않는다")는 자산 종류와 무관한데, 구현은 그때 눈앞에 있던 스킬에만 적용됐다. 이것은
`feedback_surface_symmetry`(명령 계열 비대칭)와 같은 계열의 실패다 — 한 축이 일부에만 있으면
**빠진 쪽이 입증 책임을 진다.**

`pruneOrphans` 는 별도로 더 나빴다. "templates 에 없으면 삭제"는 폐기된 하네스 룰과 **사용자가
직접 쓴 팀 규칙**을 구분하지 못한다. 둘 다 templates 에는 "없음"이다.

## Decision

**소유자 판정을 정책 파일 전체로 확장한다.** 판정 근거는 install log 의 `policyFiles`
(경로 → 설치 시점 sha256), 적용 대상은 `POLICY_DIRS`(rules · agents · commands/uzys · hooks).

| 상황 | 판정 | 처리 |
|------|------|------|
| 디스크 == 기준선 | 사용자가 안 고쳤다 | 조용히 덮어쓴다 |
| 디스크 != 기준선 | 사용자가 고쳤다 | `.backup-<stamp>` 남기고 **최신판을 자리에** |
| 기준선 기록 없음 | 판정 불가 | 보수적으로 백업 (레거시 설치의 첫 1회) |

**삭제는 소유를 증명할 수 있을 때만 한다.** 기준선에 있으면 하네스가 깔았던 것이므로 지우고
(폐기 룰 회수), 없으면 사용자가 만든 것이므로 **손대지 않는다**. 기록이 아예 없으면
아무것도 지우지 않는다 — 폐기 룰이 남는 비용보다 사용자 파일을 지우는 비용이 크다.

`install` 과 `update` 는 **같은 기준선**을 쓴다. 두 명령이 서로 다른 기준으로 "사용자가 고쳤다"를
판정하면 한쪽이 백업한 것을 다른 쪽이 조용히 밀 수 있다.

정책 디렉터리 목록은 `POLICY_DIRS`(`install-log.ts`) 하나가 SSOT 다. `runUpdateMode` 의 동기화
대상과 기준선 수집 범위가 같은 목록에서 나와야 한다 — 두 곳에 적으면 한쪽에만 디렉터리가
추가됐을 때 기준선 없는 디렉터리가 생기고, 그 안의 파일이 전부 "판정 불가"로 떨어진다.

## Alternatives

- **내용 비교로 판정** (`backupFileIfChanged` 방식) — 기각. 하네스가 개선해서 달라진 파일도
  "다르다"로 잡혀 **릴리즈마다 전 사용자에게 백업본이 쌓인다.** `fs-ops.ts` 가 ADR-046 때
  이미 같은 이유로 기각한 방식이다.
- **`add` 모드에서도 `.claude/` 통짜 백업** — 기각. 매 설치마다 디렉터리 사본이 생겨 노이즈가
  크고, 어느 파일이 왜 백업됐는지 알 수 없다. 파일 단위 판정이 정보량이 많다.
- **prune 시 백업 후 삭제** — 사용자 선택지로 제시했으나 기각됨. 파일은 여전히 자리에서
  사라져 다음 세션에 로드되지 않는다. 커스텀 룰에는 "백업됨"이 "동작함"을 대신하지 못한다.
- **prune 전면 폐지** — 기각. 폐기된 하네스 룰이 영구히 남아 상주 컨텍스트 비용이 된다
  (ADR-043 계측 최소 하네스와 충돌). 소유가 증명되면 회수하는 게 맞다.

## Consequences

- 사용자가 고친 룰·훅이 재설치·update 에서 살아남는다. 최신판이 활성이고 편집분이 백업이다
  (ADR-046 의 결정을 그대로 승계).
- **레거시 설치(로그에 `policyFiles` 없음)는 첫 update 에서 변경된 정책 파일 전부가 백업된다.**
  1회성이며, 그 update 가 기준선을 채워 다음부터는 조용해진다.
- **레거시 설치는 그 1회 동안 prune 이 작동하지 않는다.** 폐기 룰 회수가 한 사이클 늦어지는
  대신 사용자 파일 삭제 위험이 0 이 된다. 의도한 트레이드오프다.
- install log 스키마에 `policyFiles` 가 추가된다. 부재를 정상으로 다뤄야 한다
  (v26.131.x 이하 로그가 그 상태) — **부재를 "전부 하네스 것"으로 읽으면 사용자 파일을 지운다.**
- `updateDir` / `pruneOrphans` 시그니처가 바뀐다(`PolicySyncCtx` 필수). 컴파일 타임에 호출부가
  전부 잡히므로 조용한 누락 경로가 없다.
