# ADR-074: 트랙이 고르는 자산도 사용자가 보고 해제한다

- Status: Accepted
- Date: 2026-08-16
- PR: #309

## Context

사용자 지적 두 문장에서 출발했다 — *"기술스택 선택했다고 알아서 설치되는 구조는 개선해."* ·
*"설치항목에 대해서는 모두 투명하게 다 보여줘야 해."*

위저드 3단계는 `EXTERNAL_ASSETS`(외부 큐레이션)만 물었다. `manifest.ts` 가 `applies()` 로
트랙에서 유도하는 **룰·에이전트·훅·스킬은 화면에 한 번도 안 나온 채** 깔렸고, 사용자는 설치가
끝난 뒤 요약에서 처음 봤다. 실측하면 그 수가 적지 않다.

| 트랙 | rules | agents | hooks | skills | 합 |
|---|---|---|---|---|---|
| `executive` | 3 | 5 | 3 | 7 | 18 |
| `tooling` | 6 | 9 | 3 | 6 | 24 |
| `full` | 6 | 9 | 3 | 14 | **32** |

**32개가 묻지도 않고 들어간다.** 이 저장소가 파는 것이 "검증된 룰·훅·스킬을 설치하는 CLI"인데,
무엇이 들어오는지 고를 수 없다면 그건 큐레이션이 아니라 통짜 배포다.

## Decision

**3단계 맨 앞 두 페이지에 트랙 baseline 을 전부 체크된 상태로 노출하고, 체크를 풀면 안 깔리게
한다.** 기본값을 바꾸는 것이 아니라 **기본값을 보이게** 하는 것이다 — 아무것도 안 건드린
사용자의 설치 결과는 이전과 같고, 그 불변식을 테스트가 고정한다.

새 식별자 네임스페이스 `baseline:<kind>/<name>` 을 둔다(`asset:` · `option:` 과 같은 자리).
전달 경로는 `InstallSpec.baselineExclude` 이고, `userOverride.forceExclude` 와 **섞지 않는다** —
저쪽은 `EXTERNAL_ASSETS` id 를 보고 이쪽은 manifest 대상을 본다. 한 필드에 담으면 오타 하나가
어느 목록의 미스인지 판별할 수 없고, 조용히 아무것도 안 하는 제외 지시가 생긴다.

**2페이지로 나눈 근거는 실측이다.** `full` 32항목 + 헤더가 clack `groupMultiselect` 의 "페이지당
≤ ~30행" 제약을 한 페이지로는 못 지킨다. 가르는 축은 역할이다 — 정책·가드(`rules`·`hooks`) /
실행 능력(`agents`·`skills`).

### 함께 정한 것 넷

1. **목록은 manifest 에서 derive 한다.** 이름을 화면 쪽에 옮겨 적으면 그게 두 번째 하드코딩
   사본이 되고, 자산이 늘어도 화면은 그대로인 상태가 조용히 생긴다.
2. **구조 자산은 후보가 아니다.** `settings.json`·앵커·`.mcp.json`·스켈레톤은 빼는 순간 설치가
   반쪽이 된다. 판별은 대상 경로 접두 하나이고, 잘못된 id 가 들어와도 이것들은 안 빠진다.
3. **해제한 룰은 `.claude/` 와 `AGENTS.md` 양쪽에서 빠진다.** 한쪽만 거르면 claude 에서 뺀 룰이
   codex/opencode 에 그대로 깔린다 — #300(ADR-071)이 정확히 그 형태였다.
4. **`--without baseline:<kind>/<name>` 도 받는다.** 위저드에서 되는 것이 플래그로 안 되면 그건
   표면 비대칭이고, 이 리포가 세 번 적발당한 형태다.

## Alternatives

- **스킬·외부 자산만 사전 체크로, 룰·훅은 트랙 고정** — 기각(사용자 확정). *"룰은 여전히 알아서
  깔린다"* 가 남아 같은 질문을 다시 부른다.
- **한 페이지에 32개** — 기각. 터미널을 넘겨 스크롤이 생기고, 그게 v26.99.0 에서 사용자가 이미
  보고한 "선택 row 가 너무 많다"의 실제 메커니즘이다(ADR-028).
- **`userOverride.forceExclude` 재사용** — 기각. 위 Decision 의 판별 불가 문제.
- **설치 후 요약에만 전부 나열** — 기각. 사후 고지는 선택이 아니다.

## 적용 범위

위저드 3단계 · `--without` 플래그 · `runInstall` 의 baseline 복사 경로 · 4 CLI 룰 전달 경로 ·
설치 화면과 확인 화면의 제외 보고 · **`update` 의 자산 복구 경로**. **범위 밖**: 외부 자산 선택
경로는 그대로다 · `uninstall`/`list` 는 baseline 자산을 아직 다루지 않는다(선재 상태).

**`update` 가 왜 범위 안인가** — 초안은 *"`update` 는 이 목록을 묻지 않는다(기존 설치본의 선택을
그대로 갱신한다)"* 로 적었는데 **거짓이었다**(독립 리뷰 F1 실측). 제외가 install log 에 없어서
`update` 가 트랙에서 manifest 를 다시 유도했고, 뺀 룰·에이전트가 되살아나며 화면엔
*"added by this release"* 로 찍혔다 — 같은 릴리즈에서 방금 설치한 파일인데도. 되살아나는 종류가
룰·에이전트뿐이라(스킬은 `dir` 엔트리, 훅은 `needsReinstall`) 사용자가 "해제"의 뜻을 세울 수도
없었다. **그래서 `InstallLog.spec.baselineExclude` 에 남기고 `installNewAssets` ·
`refreshExternalCli` 가 존중한다.** 후자가 필요한 이유는 `AGENTS.md` 가 룰을 파일 하나에 **합쳐**
렌더하기 때문이다 — `refreshOnly` 의 "디스크에 있는 것만"이 룰 단위로는 작동하지 않는다.

## Consequences

- **위저드가 5페이지에서 7페이지가 된다.** 페이지가 0건이면 건너뛰지만 **그 분기는 현재 도달하지
  않는다**: `COMMON_RULES`(3)·`ALWAYS_HOOKS`(3)가 `applies: all` 이라 첫 페이지는 어떤 트랙에서도
  6항목 아래로 안 내려가고, 둘째 페이지도 전 트랙 최소 9항목이다. 초안이 사유로 적었던
  *"`.claude/` 를 안 만드는 CLI 조합"* 은 **성립하지 않는다** — `listBaselineTargets` 는 `tracks`
  만 보고 `spec.cli` 를 받지도 않아서, codex 단독 설치도 같은 행을 다 렌더한다(리뷰 F/A4).
- **위저드는 `ecc-plugin` 여부를 baseline 페이지 시점에 모른다.** 그 자산은 같은 3단계의 뒤쪽
  페이지에서 고르는데 baseline 이 앞에 있다. 결과는 **한 방향으로만 틀린다**: `!withEcc` 폴백
  에이전트 4종이 화면에 뜨는데 `ecc-plugin` 을 고르면 안 깔린다. 반대(안 보여 준 것이 깔리는 것)와
  오제외는 생기지 않는다. 고치려면 baseline 페이지를 자산 페이지 **뒤로** 옮겨야 하는데, 그건
  사용자가 확정한 "맨 앞에서 전부 보여준다"를 뒤집는 결정이라 여기서 하지 않는다.
- **해제는 설치 시점에만 작동한다.** 이미 깔린 것을 빼려면 `uninstall` 을 따로 쓴다 — 체크 해제가
  제거를 뜻하지 않는다는 기존 규약(v26.125.0)과 같다. `add`·`reinstall` 에서 그 상태가 실제로
  생기므로 설치 화면이 해당 항목에 `(still on disk)` 를 붙인다 — 안 붙이면 화면이 "빠졌다"고
  말하는 동안 그 룰이 계속 상주한다(리뷰 F4).
- **훅을 해제하면 `settings.json` 배선도 빠진다.** 새 코드가 아니라 install 이 이미 부르던
  `cleanStaleHookRefs` 가 없는 스크립트 참조를 지운다.
- **미검증**: 실환경 Docker 시나리오 · 실제 터미널에서의 7페이지 체감. 페이지 행수는 실측
  기반이지만 사용자 터미널 높이는 우리가 모른다.
- **선재 결함 하나가 드러났다**(고치지 않음): `commands/uzys` 는 `POLICY_DIRS` 항목이자 스켈레톤
  디렉터리인데 `templates/` 에 원본 파일이 0개다. baseline 후보 판별에서 자연히 제외되지만,
  빈 디렉터리가 모든 설치본에 생기는 것은 그대로다.
