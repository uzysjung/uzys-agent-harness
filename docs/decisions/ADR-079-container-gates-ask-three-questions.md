# ADR-079: 컨테이너 검증은 세 질문만 묻고, 배달 방식마다 하나가 게시를 막는다

- Status: Accepted
- Date: 2026-08-28
- PR: #379
- Refs: ADR-077 (CI 목표·가드레일 G1~G5), Epic #366, #369

## Context

ADR-077 이 **G2 = "고른 자산이 디스크에 실재한다"** 를 "완벽히 커버"로 선언했다. 그 축을 볼
도구는 이미 있었다 — `test/docker/scenarios/` 의 시나리오 20개. 그런데 **아무도 안 돌렸고**,
`.github/workflows/` 안의 `docker` 매치는 주석 한 줄이 전부였다.

배선하기 전에 쟀다(2026-08-28 실측, 컨테이너):

| | 결과 |
|---|---|
| 전체 | 20개 중 **6개 red** · 순차 **20.3분** |
| 배선 대상이던 realcli 3종 | **3개 다 red** |
| red 지속 기간 | codex·antigravity **63일**(ADR-023 이 없앤 산출물을 계속 요구) · opencode **12일**(#311 로 개정된 룰 문장) · dev-method **26일**(ADR-060 이 통합한 스킬 이름) |

**6건의 원인이 전부 같았다.** 시나리오가 카탈로그·룰 본문의 사실(스킬 이름 · 버전 pin ·
문장)을 **다시 타이핑한 두 번째 사본**을 들고 있었고, 원본이 *정상적으로* 바뀔 때마다 썩었다.
`bmad-method` pin 이 6.8.0 → 6.9.0 으로 올라가자 시나리오만 red 로 남은 것이 전형이다.

시간도 문제였다. 20.3분 중 검사 자체는 초 단위이고, **93%가 github/npm 왕복**이다
(실측: 외부 자산 포함 설치 14초 · 제외 1초 · 17개 시나리오의 총 설치 호출 30회).

## Decision

### 1. 컨테이너 시나리오는 세 질문만 묻는다 (사용자 확정 2026-08-28)

> ① 항목이 복사됐나 · ② 설치가 실제로 됐나 · ③ 설치된 것이 원하는 버전인가

**파일 내용이 원본과 같은지는 묻지 않는다.** 설치는 복사이고, 복사본을 원본과 맞대 보는 것은
자기 자신과의 대조다 — 원본이 바뀌면 반드시 깨지는데 그 깨짐은 결함이 아니다. 변환 로직
(frontmatter 보존 · `uzys-` 접두 오염 · opencode 커맨드 frontmatter 생성)은 **단위 테스트가
소유한다**: `tests/codex/transform.test.ts` · `tests/antigravity/transform.test.ts` ·
`tests/opencode/commands.test.ts`. 컨테이너에서 같은 것을 다시 물으면 중복이면서 잘 썩는다.

### 2. 기대 목록은 유도한다. 모집단이 0 이면 red 다

이름·버전·문장을 시나리오에 적지 않는다. 카탈로그(`DEV_METHOD_SKILL_IDS` · `method.version`) ·
설치 기록(`.harness-install.json`) · `templates/rules/` 에서 유도한다. 유도가 0건이면
**초록이 아니라 빨간불**을 낸다 — 모집단 0 은 "위반 없음"이 아니라 "아무것도 안 쟀음"이고,
그 초록이 가장 비싼 거짓말이다.

### 3. 게시를 막는 것은 배달 방식마다 하나 — 2개다

제품의 배달 방식은 넷뿐이다: **템플릿 복사 · `npx skills add` · `npm i` · `npx <cmd>@<ver>`**.
경우의 수를 다 도는 것은 같은 질문을 다시 묻는 것이라, 방식마다 한 번씩만 건드린다.

| | 게이트 | 덮는 배달 방식 | 실측 |
|---|---|---|---|
| **게시 차단**(`test.yml` `docker-e2e` → `publish.needs`) | `dev-method-skills` | 템플릿 복사(4 CLI 자리) + `npx skills add` | 32초 |
| **게시 차단** | `pinned-versions` | `npm i`(pin 대조) + `npx <cmd>@<ver>` | 72초 |
| 신호(`docker-scenarios.yml`, 태그+수동) | 나머지 15개 + realcli 3개 | update · uninstall · 백업 보존 · scope · 실 CLI 인식 | 약 19분 |

실 CLI(realcli)를 차단에서 뺀 이유: 그 이미지는 `antigravity.google` 설치 스크립트와
codex/opencode 글로벌 설치를 받는데, 그건 **우리 제품이 옳은지가 아니라 남의 CLI 가 우리
파일을 알아보는지**를 재는 축이다. 그쪽 사고로 우리 게시가 막히는 것은 근거가 약하고,
막히는 게이트는 우회되어 없느니만 못하다(#237).

### 4. #344 형태는 단위 테스트가 막는다

"기본 추천 자산인데 배달 방식이 claude 전용이라 다른 CLI 사용자에게 조용히 안 간다"는
컨테이너가 볼 수 없다 — 그 자산은 애초에 목록에서 빠지므로 디스크를 아무리 봐도 안 보인다.
`tests/cli-external-path.test.ts` 에 불변식을 넣었다: **`has-dev-track` 자산은
`assetCliSupport` 가 4 CLI 전부여야 한다.** 기존 테스트들은 support 가 `method.kind` 와
*일치하는지*만 봐서 이 형태를 통과시켰다.

## Alternatives

- **20개 전부 게시 차단.** ADR-077 의 선언과 가장 일치하지만 릴리즈에 +약 25분이 붙고,
  남의 설치 엔드포인트가 우리 게시를 막는다. 기각.
- **전부 신호(게시 안 막음).** 릴리즈 시간 영향 0 이지만 G2 를 "완벽히 커버"한다는 선언이
  거짓이 된다. 기각.
- **시나리오별 매트릭스 병렬.** 벽시계 약 4분으로 줄지만 배선이 한 겹 는다. 먼저 순차로
  돌려 실제 소요·실패율을 관측한 뒤 판단한다(보류).
- **내용 대조를 유도형으로 자동화.** 룰 본문에서 canary 를 뽑아 대조하면 썩지는 않지만,
  여전히 복사본과 원본의 자기 대조다 — 깨질 수 있는 유일한 경우가 복사 실패이고 그건
  항목 존재로 이미 답한다. 기각.

## Consequences

- 릴리즈 경로에 **+약 2분**. 20.3분을 얹지 않는다.
- **`update` 계열은 게시를 막지 않는다.** #374 가 실제로 사용자에게 도달한 축이라 위험은
  남는다 — 신호 워크플로의 red 를 릴리즈 때 눈으로 본다는 전제다. 이 전제가 깨지면
  (= red 를 또 아무도 안 보면) `update-external-skills` 하나를 차단으로 올린다.
- **거짓 red 빈도는 `docker-scenarios.yml` 의 실행 이력으로 관측한다.** 태그마다 자동으로
  도므로 인프라 사유 red 비율이 거기 쌓인다. 낮으면 승격, 높으면 승격하지 않는 근거다.
- `run.sh all` · `run-realcli.sh all` 이 **첫 실패에서 멈추지 않는다**. 요약과 red 개수를
  낸다 — 하나씩만 보이면 고칠 때마다 20분을 다시 써야 하고, 그러면 아무도 안 돌린다.
- 적용 범위: `test/docker/scenarios/**` 전부. 새 시나리오도 세 질문 안에서 쓴다.
