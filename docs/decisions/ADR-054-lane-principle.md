# ADR-054: 상위 원칙 — 만든 레인은 자기 산출물을 판정하지 않는다

- Status: Accepted
- Date: 2026-07-26
- PR: (머지 시 기재)
- Supersedes: ADR-052 (사용자 결정 2026-07-26 — *"ADR-052도 잘못된 거야"*)
- Superseded-by: — (해당 없음)

> **규약 확장 고지**: `change-management.md` 의 ADR 템플릿에 정의된 필드는 `Supersedes` 뿐이고
> **`Superseded-by` 는 정의돼 있지 않다.** 본 ADR 과 ADR-052 에서 그 필드를 쓴다 — 한쪽만 고치면
> 어느 것이 현행인지 알 수 없다는 같은 규약의 요구를 만족시키기 위한 **양방향 링크**다. 필드 추가는
> 규약 확장이므로 여기 명시한다.

## Context

사용자가 5건에 걸쳐 같은 축을 지시했다: 구현 검증은 다른 에이전트에게 · 잘 모르는 것은 적대적 다면
리뷰로(단 **중요한 결정일 때만**) · 설계·구현·검증을 독립 분리 · **기획서와 그 리뷰도** 분리 ·
**테스트 생성도** 독립 레인 · 그리고 이 원칙들을 **상위 원칙 하나로 통합**할 것.

기존 ADR-052 는 이 축의 일부(구현 위임)만 다뤘고, 그 문안이 세 지점에서 틀렸다(아래 Decision ⓐⓑⓒ).

**왜 지금 추가하는가 — 감산 사이클 중의 추가는 예외가 아니다.** 판정 기준은 방향이 아니라
**필요성**이다. 이 원칙은 0단계 실수 테스트를 통과한다 — 사고 기록이 실재하고, 그중 셋은 이번
세션에서 났다:

| 축 | 사고 기록 | 누가 잡았나 |
|---|---|---|
| 구현 ↔ 검증 | `no-false-ship` v26.138.0 — 태그·npm 게시가 없는 릴리즈를 "배포 완료·npm 라이브"로 보고 | 적대적 검증 에이전트 |
| 구현 ↔ 검증 | `no-false-ship` v26.128.0~131.0 — 릴리즈 CI 4연속 red 를 3릴리즈 동안 미인지. 보고한 "CI exit 0"은 전부 로컬 | 사후 |
| 테스트가 무는가 | `no-false-ship` v26.127.0 — 게이트를 만들며 같은 실수 3회, 셋 다 음성 대조가 잡음 | 음성 대조 |
| 설계 ↔ 설계 리뷰 | ADR-053 §정정 이력 — 같은 표를 3번 고치며 결론의 부호가 매번 뒤집힘 | 재측정 |
| 설계 ↔ 설계 리뷰 | 이번 세션 §② — 이전 세션이 준 죽은 참조 8건 중 **1건이 거짓**. 다른 패스가 확인해 드러남 | 재확인 패스 |
| 설계 ↔ 설계 리뷰 | 이번 세션 — 설계 v2 가 "non-claude 앵커에 구현 레인 0건"을 전제했으나 **임베드를 안 따라가 실측이 틀림** | 설계 리뷰 레인(NO-GO) |

**배포판 증거 기준**(ADR-053 은 로컬 사고 1건으로는 배포판 상주를 허용하지 않는다)은 **손상
비대칭**으로 통과한다. 판정이 생산과 겹쳐 새는 오류는 **되돌릴 수 없는 형태로 배포된다** — 이
리포가 실제로 겪었다: 사설 프로젝트 내용이 npm 26.83.0~26.127.0 에 실렸고 주간 다운로드가 임계를
넘어 **unpublish 가 불가능**해 감수 결정으로 종결됐다.

## Decision

**상위 원칙 하나를 앵커에 상주시킨다: "만든 레인은 자기 산출물을 판정하지 않는다."** 파생(설계 리뷰 ·
테스트 작성 · 구현 위임 · 검증의 자기 증거 · 적대적 패널의 문턱)은 규칙이 아니라 사례이므로, 새
산출물이 생기면 행이 하나 늘 뿐 원칙은 안 바뀐다.

> **후속 (ADR-055, 2026-07-26)**: 이 문안은 ADR-055 에서 배포판 앵커의 **원칙 1·4 로 분산
> 배치**됐다(전용 `## The Lane Principle` 절 → 삽입 1·2). 그리고 **테스트 작성 분리 축은 사용자
> 결정으로 기각**됐다 — *"테스트 누가 작성하던 테스트케이스도 결국 코딩이니깐 리뷰어가 검증할거야"*
> (분리 요구는 작성이 아니라 **리뷰**에 걸린다). Supersede 가 아니라 재배치 + 축 1개 철회다.

**ADR-052 에서 승계 — 아래는 유효하며 본 ADR 이 그 현행 소유자다**:
`templates/agents/implementer.md` 자산 · `DEV_AGENTS` 배선(`src/manifest.ts`) · 모델 선택 ·
**종료 조건 계약("done = a test that fails without the change")**. 폐기되는 것은 **위임 문안 3점뿐**
(아래 ⓐⓑⓒ). `change-management` 가 `Superseded` 를 terminal 로 정의하므로, 승계분을 Context 가
아니라 **여기 Decision 에 명시 재기재**한다 — 그러지 않으면 미래 독자가 그 자산을 정리 대상으로
오독한다.

**ADR-052 가 틀린 지점 3개**:

- ⓐ 계약이 "종료 조건 = 무는 테스트 green"만 두고 **누가 그 테스트를 쓰는지 규정하지 않았다** —
  그래서 구현자가 자기 통과 기준을 썼다. 구현자가 자기 종료 테스트를 쓰면 그 테스트는 "코드가 하는
  일"을 적고 "해야 할 일"은 안 적는다.
- ⓑ *"Keep the Deciding"* 이 **설계와 검증을 같은 액터에 남겼다** — 원칙이 막으려는 바로 그 형태다.
- ⓒ *"dev tracks ship an `implementer` agent"* 가 **거짓 문장으로 배송됐다.** 에이전트는
  `.claude/agents/` 로만 설치되는데(`src/manifest.ts`), `{PROJECT_RULES}` 임베드가
  `templates/CLAUDE.md` 본문 전체를 codex·opencode·antigravity 앵커에 넣기 때문에 그 문장이
  **에이전트가 설치되지 않는 3 CLI 앵커에 이미 나가 있었다**. 본 ADR 의 조건절 문안
  (*"where an `implementer` agent is installed, use it, and without it …"*)이 이 결함을 닫는다.

**적대적 다면 리뷰에는 문턱을 함께 규정한다**(사용자 정정: *"중요한 의사결정에만"*). 새 기준을 만들지
않고 이미 있는 선을 쓴다 — `change-management` 의 **Major CR** 정의와 "되돌리기 어렵거나 공유
상태를 건드리는 것". 방법은 `multi-persona-review` 스킬이 이미 소유하므로 **자산은 신설하지 않고**
원칙은 *언제 부르는가*만 규정한다.

## 적용 범위

| 축 | 범위 |
|---|---|
| 파일 | `templates/CLAUDE.md`(배포판 원칙, `## Rule 1` 앞) · `.claude/CLAUDE.md`(이 리포 앵커, 파일 맨 끝 — 전례 포함) |
| CLI | **claude + non-claude 전부.** codex·opencode·antigravity 는 `{PROJECT_RULES}` 임베드로 자동 수신 — **3개 `AGENTS.md.template` 은 건드리지 않는다**(같은 사실을 두 곳에 두면 doc-governance 위반이고 원칙이 2벌 상주한다) |
| 트랙 | 전 트랙 (`templates/CLAUDE.md` 는 트랙 무관 상주) |
| 자산 | **신설 없음.** implementer 는 ADR-052 승계분, 패널 방법은 `multi-persona-review` 위임 |
| 범위 밖 | 옛 Rule 1~12 정리 · non-claude 앵커의 `## Agents` 표 정합성 · 놓친 죽은 참조 M-1~M-10 · test-author 전용 자산 |

## Alternatives

| 대안 | 왜 기각 |
|---|---|
| 3개 `AGENTS.md.template` 에 각각 절 추가 (설계 v2) | **전제가 실측 오류.** 임베드로 이미 받으므로 같은 원칙이 영·한 2벌 상주하고 게이트가 그 중복을 고정한다. 설계 리뷰 레인이 NO-GO 로 반송 |
| ADR-052 를 **확장**(supersede 아님) | 설계 리뷰가 권했으나 **사용자가 명시 결정**(*"ADR-052도 잘못된 거야"*). 대신 유효분을 본 ADR Decision 에 승계 재기재해 그 우려를 해소 |
| `Rule 13` 으로 번호 부여 | 12룰 정리 작업이 번호를 흔든다. 상위 원칙은 룰 목록의 n번째가 아니라 그 위 |
| test-author 전용 에이전트 신설 | 원칙은 자산 없이 만족된다(설계 레인이 직접 쓰거나 범용 서브에이전트). 자산 추가는 상주 descriptor 증가라 ADR-053 절차를 별도로 통과해야 한다 — **사용자 결정으로 미신설** |
| 적대적 패널을 문턱 없이 규정 | 두 방향으로 다 실패한다 — 안 쓰거나(이번 세션에서 사용자가 두 번 지시해야 했다), 사소한 것에까지 써서 비용이 판단 가치를 넘는다 |

## Consequences

- **상주 순증(상쇄 후) — `+217 tok` (tooling, 개수 축 불변). 확정: ADR-055 Consequences 1 의 3값
  표가 SSOT 이고 여기 복제하지 않는다** — 보류 사유였던 CLAUDE.md 재구성이 ADR-055 로 끝났다.
  개수 축(Resident Item Count,
  1차 NSM)은 **불변**이다 — 파일이 늘지 않는다. 토큰 축(부수)만 증가하며 `context-cost-baseline.json`
  의 ratchet 상한 인상이 따라온다. **상한 인상은 감산 기본값과 반대 방향**이므로 사유를 남긴다:
  0단계 실수 테스트를 통과한 신규 원칙이고, 상쇄(`Delegate the Building` 절 삭제 + 예외 단락을
  `no-false-ship` 참조로 축약)를 먼저 반영한 뒤의 값이다.
- **다도메인 반복은 미확보.** 근거 모집단이 이 맥 1인이다. "이 원칙이 성과를 올린다"는 주장이
  아니라 **"판정이 생산과 겹쳐 샌 사고가 실재한다"**까지가 확정분이다.
- **test-author 전용 자산은 신설하지 않는다**(사용자 결정). 원칙만으로 만족되며, 필요해지면
  ADR-053 절차를 따로 통과시킨다.
- **미측정**: 모델이 이 원칙을 **자발적으로 지키는 비율**. 준수 여부를 세는 계측이 없다 — 게이트는
  "앵커에 문안이 있는가"까지만 본다(D4, 별도 테스트 작성 레인 소관).
- **"파일을 재고 그 파일이 끌어오는 것을 안 따라간" 오류가 이 리포에서 4회째다**(`@import` 3회 +
  이번 임베드). 상주 계측·앵커 판정에서 "이 파일이 다른 파일을 끌어오는가"는 파일 크기보다 **먼저**
  물어야 하는 질문이다.
- **감산 기본값 문안(NORTH_STAR §3)을 함께 정정**한다. 정정이 없으면 다음 세션이 "감산 사이클
  중에는 추가하면 안 된다"로 오독해 **필요한 자산을 못 넣는다** — 그 오독을 이번 세션이 실제로 했다
  (레인 원칙 추가를 "미안한 예외"로 프레이밍했고 사용자가 정정했다: *"무조건 빼는 것만이 정답은
  아니지. 불필요한 것을 빼겠다지. 기존에 필요한 것이 없으면 추가해도 된다"*).
