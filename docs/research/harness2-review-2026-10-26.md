# #877 Harness² 검토 — 우리 제품에 쓸 것이 있나 (2026-10-26)

**결론**: 제품에 바로 넣을 것은 없다(채택 0). 시험해 볼 것은 2건이고, 둘 다 #513 측정 쪽이다. 기각은 4건이다.
Harness² 의 핵심 아이디어는 과제마다 하네스를 고쳐 다시 돌리는 것이다. 이 방식은 검증된 자산을 고정해서 설치하는 우리 제품과 맞지 않는다.
반면 이 논문이 쓴 **WorkBuddy-Bench Code**(80개 과제, 테스트로 채점)는 #513 의 셋째 벤치마크 후보가 될 수 있다.
우리가 이미 만든 Pier 실행기로 돌릴 수 있는지 확인할 가치가 있다.

## 1. 확인한 사실 (출처: README · docs/ · 소스 · arXiv HTML · Tencent/workbuddy-bench)

- **과제 단위 루프**: 기본 하네스로 먼저 한 번 실행한다(reference). 이어서 두 편집자가 후보를 하나씩 낸다. INVARIANT 편집자는 작업 방식을, DOMAIN 편집자는 분야 지식을 맡는다. 두 후보를 각각 실행해 보고, composer 가 궤적을 대조해 최종 하네스를 만든 뒤 그것을 다시 실행한다.
  k=1 이면 과제 하나에 실행 약 4회와 편집 세션 3회 이상이 든다(실행 횟수는 논문 서술로 센 추론이다). 정답 채점기는 쓰지 않고, 익명화한 산출물 중 하나를 모델이 고른다(`core/selection.py`).
- **지속 개선 라이브러리**: 채택된 하네스와 "근거 있는 교훈"을 분야별 라이브러리에 쌓는다. 다음 과제는 이 라이브러리를 예시로 읽는다(`core/library.py`, EXPERIMENTS.md).
- **실행기**: OpenCode(기본)와 Codex(`--substrate cx`) 두 가지뿐이다. **Claude Code 는 지원하지 않는다.** 하네스를 고칠 수 있는 대상은 `AGENTS.md` 프로즈, `.opencode/skills`, `agent`, `plugin/*.ts` 이다(`harness_baseline_oc/harness.yaml`). 비교 기준선 v0 는 순정 OpenCode 이고 구성요소 파일은 전부 비어 있다.
- **자격증명**: Vertex AI(`gcloud` ADC, `GOOGLE_CLOUD_PROJECT`)가 기본이다. WorkBuddy 의 setup 은 solver 가 `google-vertex/gemini...` 가 아니면 **실행을 거부한다**(BENCHMARKS.md). Codex 실행기는 LiteLLM 브리지를 거친다. judge 모델도 따로 필요하다.
- **결과(논문 Table 1, WB Code)**: GLM-5+OpenCode 는 58.4 → k=1 에서 77.1 → k=5 에서 81.9 이다. Gemini 3.5 Flash+OpenCode 는 73.4 → 76.5 → 80.8 이다.
  **같은 계산량으로 맞춘 비교(best-of-N · 반복 샘플링)는 없다.** 과제당 비용·토큰 수치도 없다. 논문 한계 절은 "추가 실행이 필요하다", "다른 과제로 옮겨 가는지는 보장하지 않는다"고 스스로 적는다.
- 학습한 하네스를 고정해 처음 보는 과제에 쓰는 비교는 Meta-Harness 기준선 하나뿐이다. WB Code 에서 73.4 → 75.5 로, 이득이 +2.1 에 그친다.
- **구성요소 제거 실험(App. E.1, Gemini 기준)**: skills 를 빼면 평균 −5.3, scripts 를 빼면 −3.7, 프롬프트 묶음을 빼면 −1.5 이다. 효과가 서로 더해진다는 증거는 아니라고 저자가 직접 밝힌다.
- 편집자 프롬프트(`core/prompts.py`)의 형태별 비용 원칙: "상주 프로즈는 가장 비싼 선택이다", "skills 는 호출될 때만 비용이 든다", "plugin 은 도구 루프 안에서 작동해 모델이 건너뛸 수 없는 유일한 수단이다 — 프로즈는 안 읽힐 수 있지만 훅은 그럴 수 없다".
- **웹 접근**: 검증 실행 중 Codex 가 지시 없이 JobBench 채점 기준을 내려받은 사례가 있었다. 그래서 HF·GitHub 호스트를 차단하라고 권고한다(EXPERIMENTS.md).
- **WorkBuddy-Bench**(Tencent)
  - 과제: Code 80개. Python 저장소 수준 SWE 과제이고, 기준 커밋에서 출발해 테스트를 통과시켜야 한다. 18개 범주, 5개 역할로 나뉜다.
  - 형식·실행: Harbor 기반이고 Docker 가 필요하다. 상류 저장소에 **`configs/harnesses/claude-code`** 가 들어 있다. 모델은 openai 또는 anthropic 프로토콜이면 아무 백엔드나 붙일 수 있다.
  - 데이터: HF 에서 받고 SHA256 으로 검증한다.
  - 라이선스: Tencent 자체 라이선스이고 "EU 내 사용 대상 아님" 조항이 붙어 있다.

## 2. 우리 쪽에서 이미 있는 것 (feat/513-effect-eval 브랜치 기준)

- Pier 0.3.1(Harbor 포크)과 `EvalClaudeCode` 로 양팔 A/B 를 돌린다. 에이전트 네트워크는 egress 프록시가 **API 호스트만** 허용한다(`513-effect-eval-design.md` §1.1).
  → Harness² 의 웹 차단 권고는 우리에게 **이미 적용돼 있다**. 새로 넣을 것이 없다.
- 형태별 비용 원칙과 같은 판정이 이미 NORTH_STAR §1 에 있다: "반복 실수는 룰, 심각한 실수는 훅", "관측이 없으면 상주에서 스킬로 내린다".

**기각 사유**
- **1**: 우리는 검증된 자산을 **고정해서** 배달하고, 설치자 디스크의 하네스 몫은 설치 기록 하나가 정한다(CLAUDE.md §설치자 디스크). 과제마다 자산을 다시 쓰면 그 원칙이 무너진다. update·uninstall·백업이 무엇을 하네스 것으로 볼지 정할 수 없게 된다.
  더구나 이득의 근거가 약하다. GLM-5 의 +18.7 은 계산량을 맞추지 않은 수치라, 같은 과제를 여러 번 돌리고 그중 하나를 고른 효과와 구분되지 않는다. 고정 하네스로 처음 보는 과제를 풀 때의 이득은 +2.1 뿐이다.
  또 이 기능은 하네스가 아니라 실행기(에이전트 런타임)의 일이다. 설치 CLI 가 4개 CLI 의 실행 루프를 감쌀 자리도 없다.
- **2**: 모델이 쓴 지시문이 자동으로 상주에 쌓이게 된다. 상주 지시는 "관측이 근거"라는 NORTH_STAR §1 원칙과 정면으로 부딪친다. Codex `AGENTS.md` 예산(합계 32 KiB, 이미 74%)도 잠식한다. 설치자 쪽에서 교훈을 쌓는 일은 이미 각 CLI 의 메모리 기능이 맡고 있다.
- **3**: 맞는 말이지만 이미 우리 원칙이다. 제거 실험의 순서(skills 손실이 가장 크고 프롬프트 손실이 가장 작다)도 "상주에서 스킬로 내린다"와 같은 방향이다.
  다만 결과물이 문서·웹 작업이고 Gemini 에서 낸 수치라 우리 결정의 근거로 옮겨 쓸 수는 없다. 인용하더라도 참고 수준으로만 쓴다.
- **4**: Claude Code 실행기가 없다. 우리 4개 CLI 중 Codex·OpenCode 만 돌릴 수 있다. WB 경로는 solver 를 Vertex Gemini 로 강제한다(GLM 은 OpenCode provider 문자열로는 가능하지만 setup 이 거부한다 — BENCHMARKS.md).
  무엇보다 측정하는 질문이 다르다. Harness² 는 "과제마다 고친 하네스 vs 빈 하네스"를 비교하고, 우리는 "고정 하네스 설치 vs 미설치"를 비교한다. 쓸 만한 것은 프레임워크가 아니라 그 안의 벤치마크다(→ 후보 5).

## 4. #513 에 대한 답 — Harness² 의 방법·벤치를 우리 효과 측정에 쓸 수 있나

- **방법(재귀 개선 루프)**: 쓸 수 없다. 우리 질문인 "고정 하네스 A/B"와 측정 대상이 다르고, Claude Code 실행기도 없다.
- **벤치(WorkBuddy-Bench Code)**: 쓸 수 있을 가능성이 높다. 단 Harness² 를 거치지 않고 **상류 데이터셋을 Pier 로 직접** 돌린다.
  - 근거 1 — 형식이 맞는다: WB 는 Harbor 형식(`task.toml` · `instruction.md`)이고 Pier 는 Harbor 포크다. 우리 DeepSWE 경로와 같다. 단 Pier `-p` 로 바로 도는지는 **미확인**이다.
  - 근거 2 — Claude Code 가 공식 지원 대상이다: 상류 저장소에 `claude-code` 하네스 설정이 있다.
  - 근거 3 — 채점이 테스트 통과다(README): DeepSWE·SWT 와 같은 결정적 채점이다. code subset 에서 judge 모델을 쓰는지는 **미확인**이다. Harness² setup 이 WB 전체에 judge 를 요구하는 것은 web·office 때문일 수 있다.
  - 근거 4 — GLM 기준선이 공개돼 있다: GLM-5+OpenCode 기준 58.4 다. 과제가 너무 쉽거나 너무 어려워서 차이를 못 보는 상황을 미리 피할 사전값으로 쓴다. 실행기가 달라 그대로 옮기지는 않는다.
  - 근거 5 — 독립 표본을 하나 더 얻는다: DeepSWE(다언어 장기 과제)·SWT(재현 테스트)와 다르고, Python 저장소 수정 + 역할 범주라는 축이다.
  - 자격증명: GLM 코딩 플랜 키(Z.ai, 이미 보유)뿐이다. Vertex·gcloud·HF 토큰은 필요 없다(공개 데이터셋, curl 로 받고 SHA256 확인). judge 가 필요하다면 그 키가 추가된다(미확인).
  - 인프라: Docker 다. 과제당 CPU·메모리 요구량은 **미확인**이고 `task.toml` 을 전수로 세야 한다. arm64 Mac 이면 amd64 에뮬레이션 여부도 확인해야 한다.
  - 비용: 모델 호출은 과제 × 2팔 × 반복 수다. 라이트(앞 8개 × 1회)면 16시행이다. 시간은 DeepSWE(최대 3h)보다 짧을 것으로 추정하지만 **미측정**이다.
- **시험 절차(제안, 유료 실행은 별도 승인)**
  1. code 데이터셋을 받아 `task.toml` 자원과 채점 방식을 전수로 확인한다.
  2. Pier 로 oracle=1 · nop=0 대조를 1과제에 돌린다(모델 호출 0).
  3. 통과하면 순서 파일(`Random(513)`)을 고정해 묶음 v2 후보에 올린다. 라이선스의 EU 조항은 한국 운영자에게는 해당하지 않지만, 결과를 공개할 때 출처와 라이선스를 적는다.
- **후보 6의 조건**: §5 판정 규칙상 미디엄에서 전체 효과가 "판별 가능"으로 나온 뒤에 연다. 전체 효과가 0인지도 모르는 상태에서 자산별 기여부터 쪼개면 표본만 늘어난다(513 원 리서치의 "효과 확인 뒤 ablation"과 같다).
  궤적 대조를 할 때는 Harness² composer 의 근거 규칙을 빌려 쓴다: "좋은 관행 같다는 근거가 아니다. 그 순간을 지목하라"(prompts.py 922–924). 갈린 과제의 원인을 쓸 때 이 형식을 따른다.
