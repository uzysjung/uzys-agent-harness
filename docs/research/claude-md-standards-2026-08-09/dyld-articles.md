## §1. dyld — "CLAUDE.md·AGENTS.md 작성법"

출처: https://dyld.kr/blog/how-to-write-claude-md-and-agents-md

### 핵심 명제

`CLAUDE.md`·`AGENTS.md` 를 **"저장소 수준의 운영 문서"**로 다룬다. 담는 것은 **"코드만으로는
드러나지 않는 것"** — 팀 기준, 검증 경계, 여러 작업에 걸쳐 반복되는 판단 원칙.

### 담으라 (원문 인용)

- **"코드에서 알 수 없는 내용만 적습니다"**
- **"결제 오류 처리는 `services/payments/errors.ts` 패턴을 따릅니다"** — 추상 패턴 대신 파일 경로
- **"화면 변경은 375px과 1280px에서 실제 브라우저로 확인합니다"** — 검증 대상·방법을 이름으로
- **"요구사항을 바꾸면 `docs/v-cycle/traceability.md`도 함께 갱신합니다"** — 변경과 추적의 연결
- **"실제로 실행하지 않은 검증은 통과했다고 보고하지 않습니다"** — 실행 가능한 검증만 강제

### 담지 마라 (원문 인용)

- ✗ "기존 스타일을 따릅니다" — 모호한 패턴 참조
- ✗ **"항상 두 번 확인하세요"** — 일반적 자기검토 지시. 최신 모델은 이미 한다
- ✗ **"조심하세요"** 류의 주의 환기 — **"행동과 승인 조건으로 적습니다"**
- ✗ 코드에서 보이는 내용의 반복
- ✗ 단일 작업용 요구사항을 저장소 룰에 — 앞으로의 작업에 불필요한 제약이 된다
- ✗ **두 파일에 같은 룰을 중복 보관** — `CLAUDE.md` 에서 `@AGENTS.md` 임포트하거나 심볼릭 링크

### 분량

| 대상 | 기준 | 근거 |
|---|---|---|
| CLAUDE.md (루트) | **~200줄** | Anthropic 공식(memory 문서). 세션 시작 시 로드 |
| AGENTS.md (누적) | **32 KiB** | OpenAI Codex 가이드라인. 병합된 프로젝트 지시문 총량 |
| 임포트 | 아껴 쓴다. 상세는 **인덱스 + 링크** | 임포트는 전문이 컨텍스트에 들어가고 링크는 가볍다 |
| 주기 점검 | **분기마다 오래된 항목 정리** | Anthropic 지침 |

철학(원문): **"항상 필요한 기준만 입구에 두고, 자세한 설명은 필요할 때 찾을 수 있게 만드는 것이
핵심입니다"**

### CLAUDE.md vs AGENTS.md — 도구별 차이

| 축 | Claude Code | Codex (AGENTS.md) |
|---|---|---|
| 루트 로드 | 세션 시작 시 `/CLAUDE.md` | 루트 → 현재 디렉터리 경로를 **병합** |
| 하위 디렉터리 | 그 폴더 파일을 읽을 때 하위 `CLAUDE.md` 로드 | 시작 디렉터리까지만. 좁히려면 `AGENTS.override.md` |
| 임포트 | `@docs/file.md` 로 인라인 포함 | 공식 임포트 없음 — 디렉터리 계층으로 |
| 확인 | `/context` 로 로드된 Memory 확인 | `codex --cd 경로 "Show…"` |

### 결정적 단서 (원문 인용)

1. **룰 ≠ 집행**: **"문서는 판단 방향을 제공하고, 시스템은 넘지 말아야 할 경계를 집행합니다"** —
   단단한 경계는 CI·권한·린터가 맡고, 문서는 판단만 안내한다.
2. **선제 성문화 금지**: 룰을 미리 박지 말고 **실제 실패를 관찰한 뒤** 모델이 반복하는 것과
   팀 간 누락이 요구하는 것만 넣는다.
3. **도구 차이**: 두 파일 간 룰 맹목 복사는 기대 동작을 깨뜨린다 — 하나를 원본으로 고르고
   나머지는 임포트·참조.
4. **성공 지표**: **반복 작업 사이의 일관성**이지 파일 크기나 망라성이 아니다.

### V-Cycle 프레임 (이 글의 확장 제안)

요구사항과 검증을 단계마다 연결: Needs&Outcomes→User Validation / System Requirements→System·
Acceptance Test / Architecture&Interfaces→Integration / Component Design→Unit / Implementation→
Build·Review·Deploy. 큰 프로젝트는 `docs/v-cycle/` 아래 00-index ~ 06-validation + `decisions/`
+ `traceability.md` 로 중첩. 각 단계 문서는 입력·결정·산출물·종료 조건·대응 검증·관리 정보를 답한다.

> 이 프레임은 **이 글의 제안**이고 공식 문서 근거가 아니다. 채택 여부는 별도 판단.

### 최소 시작 템플릿 (원문 인용)

```
# 프로젝트 작업 기준

## 작업 전에 확인할 곳
- 구조 변경 전 `docs/architecture.md`를 읽습니다.
- 새 API는 `src/api/orders.ts`의 오류 처리 방식을 따릅니다.

## 작업 제한 및 승인 규칙
- 공개 API 응답 형식은 별도 승인 없이 바꾸지 않습니다.
- 기존 작업 트리의 사용자 변경을 되돌리거나 함께 커밋하지 않습니다.
- 배포와 데이터 변경은 실행 전에 대상과 영향을 설명하고 승인을 받습니다.

## 검증
- TypeScript 변경 후 `npm test`와 `npm run lint`를 실행합니다.
- 화면 변경은 실제 브라우저에서 모바일과 데스크톱을 확인합니다.
- 실행하지 못한 검증은 완료로 보고하지 않습니다.

## 작업 범위
- 요청과 직접 관련된 파일만 수정합니다.
- 서로 다른 해석이 결과를 크게 바꿀 때만 사용자에게 확인합니다.
```

## §2. dyld — "AI가 발전해도 통하는 프롬프트 작성법"

출처: https://dyld.kr/blog/how-to-write-prompts-for-ai-work

### 핵심 명제 (원문 인용)

**"좋은 프롬프트는 AI를 설득하는 문장이 아니라, 동료에게 건네는 짧고 검증 가능한 업무 브리프에
가깝습니다"**

모델이 좋아질수록 문체 기교보다 **무슨 문제를 풀지 · 어떤 기준 자료를 볼지 · 범위는 어디까지 ·
결과는 어떤 형식으로 · 완료를 어떻게 확인할지**를 분명히 전달하는 것이 성패를 가른다.

### 단순 작업 5요소 (원문 인용)

1. **목표** — "AI가 해야 할 행동보다 그 행동으로 해결할 문제를 먼저 적습니다"
2. **맥락과 기준 자료** — "AI가 일을 판단할 때 필요한 사실과 출처를 제공합니다"
3. **범위와 제약** — "어디까지 맡길지 분명하게 정합니다"
4. **결과 형식** — "결과를 어디에 사용할지에 맞춰 길이와 구조를 정합니다"
5. **확인 방법** — "무엇과 비교해야 하는지 알려줍니다"

원칙: **"프롬프트가 길다고 일이 명확해지지는 않습니다"**

### 다단계 자율 작업 템플릿

```
<objective>
<inputs>
<success_criteria>
<boundaries>
  - Scope:
  - Non-scope:
  - Guardrails:
  - Resource limit:
<autonomy>
<recommended_direction>
<loop>
<output_format>
```

> 이 저장소의 `task-brief` 스킬이 쓰는 형태와 같다. 이슈 #286 본문도 이 형식으로 작성돼 있다.

### 모델 변화에 대한 원칙 (원문 인용)

**"모델이 바뀌면 프롬프트도 덜어내야 합니다"** — 옛 모델용 우회 지시를 걷어낸다.

### 이 글이 인용한 1차 출처

Anthropic prompting best practices · prompting Claude Opus 5 · Claude Code 고급 사용자 팁 ·
YC Boris Cherny 인터뷰. 앞 넷은 `00-index.md` 표 참조.

## §3. theaxlabs — "context file: eight lines" (참고 등급, 판정 기준 아님)

출처: https://theaxlabs.com/blog/context-file-eight-lines-prompt-guide
원 출처(X 포스트)는 HTTP 402 로 접근 불가.

주장: 컨텍스트 파일은 길이가 아니라 **밀도**. 에이전트가 스스로 알아낼 수 있는 것(디렉터리 구조·
파일 목록·설치된 패키지·코드 스타일·빌드 명령)은 빼고, **모델이 지시 없이는 반복하는 행동 결함**을
교정하는 문장만 담는다. 저자의 실제 AGENTS.md 는 8원칙으로 압축됐다(60억 토큰 규모 경험 기반).

원문 인용된 원칙 4개:

1. "해결책을 설계하기 전에, 이미 자리 잡은 제품들이 같은 문제를 어떻게 푸는지 먼저 살펴볼 것"
2. "하위 호환을 유지하지 말 것. 호환 레이어·폴백·마이그레이션을 덧붙이는 대신 쓰이지 않는 경로를
   삭제할 것"
3. "현재 요구사항을 완전히 충족하는 가장 단순한 구현을 선택할 것"
4. "시스템은 레이어로 키울 것… 동작하는 코드를 미완성 복잡도와 맞바꾸지 말 것"

나머지 4개는 모듈성·라이브러리 재사용·의존성 검증·장기 아키텍처 결정.

**"8줄로 줄여라"는 이 저장소의 판정 기준이 아니다** (사용자 확정 2026-08-09). 위 원칙들의 내용은
이슈 #287 제안에 반영돼 있고, 그 반영분의 적합성만 판단한다.
