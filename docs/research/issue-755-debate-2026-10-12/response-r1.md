1. 판정

조건부 — 현 단계에서는 상주 보류.

핵심 가치인 **사용자 성과 중심의 작업 분해(Outcome-driven Decomposition)**는 유지할 만하다. 하지만 원안은 기존 앵커와 상당히 중복되며, 특정 사용자의 프로젝트 관리 방식을 모든 설치자의 기본 행동으로 일반화한다.

특히 rather than from the conversation, one change, own description alone은 실제 행동을 잘못 유도할 수 있다.

제 판단은 성과 중심의 작업 구조화 원칙만 추출하고, 나머지는 기존 앵커와 스킬에 맡기는 것이다. 단, 그 원칙조차 추가 전 비교 실험이 필요하다.

2. 지적 목록
① 문서와 현재 사용자 지시 사이의 권한 관계가 잘못됨
높음

(a) 문제

derive the work from them rather than from the conversation

문서 우선이 아니라 대화 배제로 읽힌다. 문서가 존재한다는 사실만으로 최신성, 승인 여부, 권위가 보장되지 않는다.

(b) 오작동 시나리오

설계서에는 PostgreSQL을 사용하라고 되어 있지만, 사용자가 현재 대화에서 SQLite로 변경하도록 명시했다. 에이전트가 기존 설계서를 우선하고 최신 요청을 무시한다.

반대로 사용자의 즉흥적인 대화 변경이 이미 승인된 주요 설계 결정을 뒤집는 경우도 있다. 어느 한쪽의 기계적인 우선순위가 아니라 실제 충돌의 중요성과 승인 범위를 판단해야 한다.

(c) 수정

Use the current request alongside applicable project plans and agreed briefs.

applicable은 중요하다. 문서가 있다고 무조건 참조하거나 준수하는 것이 아니라, 현재 과업과 관련되고 유효한 내용을 사용한다는 뜻이다.

충돌 해결 절차는 기존 §2와 §6에 충분히 포함되어 있으므로 반복하지 않는다.

② 모든 작업을 User Flow로 묶는 것은 과잉 일반화
중간

(a) 문제

Group that work by the user flow it completes

사용자 경험을 중심으로 기능을 묶는 원칙 자체는 좋다. 그러나 사용자 흐름이 직접 존재하지 않는 작업도 많다.

(b) 오작동 시나리오

DB 인덱스 개선, 접근통제 강화, 배치 데이터 품질 개선, 경영 보고서 작성 작업에서 에이전트가 억지로 사용자 여정을 구성한다.

이때 작업 분해가 실제 기술적 의존성이나 검증 가능성보다 인위적인 사용자 플로우에 맞춰진다.

(c) 수정

Organize work around verifiable user or operational outcomes.

사용자에게 제공되는 가치와 운영상 달성해야 할 결과를 모두 포괄한다.

단, 이것도 모든 작업에 별도 그룹을 만들라는 의미가 되어서는 안 된다. **다중 작업(Multi-part Work)**에만 적용하는 것이 적절하다.

③ one change는 작업 크기의 기준으로 부정확함
중간

(a) 문제

units that one change can finish

change가 PR, 커밋, 파일 수정인지 불명확하다. 더 큰 문제는 변경 횟수가 적절한 작업 경계의 결정 기준이 아니라는 것이다.

(b) 오작동 시나리오

인증 체계 변경은 스키마 확장, 데이터 이관, 애플리케이션 전환을 순차적으로 수행해야 할 수 있다.

에이전트가 한 번의 변경으로 끝내려고 하면 위험한 일괄 변경이 된다. 반대로 한 PR 단위에 맞추려고 지나치게 분할하면 통합 검증과 조정 비용이 증가한다.

이는 기존 §3의 coherent solution 원칙과도 긴장한다.

(c) 수정

coherent, verifiable work units

작업 크기를 고정하지 않고, 논리적 완결성과 검증 가능성을 기준으로 삼는다.

제시된 범위 축소와 머지율 사이의 +16.4%p 관계는 원자료가 없어 인과성을 검증할 수 없다. 또한 머지율 자체가 사용자 가치나 총 작업 효율을 의미하지 않는다.

④ own description alone은 프로젝트 맥락을 배제할 위험
중간

(a) 문제

started from their own description alone

자족적인 작업 지시서는 유용하다. 그러나 독립적으로 이해 가능한 작업과 외부 맥락 없이 실행 가능한 작업은 다르다.

(b) 오작동 시나리오

기존 인증 모듈을 활용해야 하는 작업에서 에이전트가 작업 설명에 모든 정보를 복사하거나, 설명에 없는 프로젝트 제약을 무시한다.

완전한 자기완결성을 요구하면 문서 중복, 컨텍스트 팽창, 오래된 사양 복제 위험이 생긴다.

(c) 수정

작업 설명은 목표·범위·필요한 의존성·검증 기준을 파악하기 충분하면 된다.

표현은 다음 정도가 적절하다.

clearly described, verifiable units

작업 지시서의 상세 작성법은 이미 설치된 브리프 정규화 스킬이 소유해야 한다.

⑤ 그룹 완료 기준을 이름에 연결하는 것은 위험
높음

(a) 문제

a grouping is done when the user can do what its name says

이 문장이 제안에서 가장 가치 있는 부분이면서 동시에 수정이 필요한 부분이다.

이슈가 닫혔다고 성과가 달성된 것은 아니라는 취지는 타당하다. 하지만 그룹 이름은 수용 기준(Acceptance Criteria)이 아니다.

(b) 오작동 시나리오

그룹 이름이 사용자가 데이터를 내보낼 수 있다라면 다운로드 버튼과 CSV 생성만으로 달성했다고 판단할 수 있다.

그러나 권한검사 오류로 타인의 데이터가 노출된다면 실제 완료가 아니다.

기존 §4는 비가시적 보호 요건까지 검증하도록 요구한다.

(c) 수정

Consider an outcome complete when its required results and protections are evidenced, not merely when its units are closed.

이 표현은 원안의 가장 중요한 의미를 유지하면서 기존 §4와 정합성을 확보한다.

⑥ agreed order는 실행 순서와 병렬성을 경직시킴
중간

(a) 문제

Work the units in their agreed order

합의된 순서가 없다면 행동 기준이 모호하다. 순서가 있더라도 새로 발견된 의존성이나 위험 때문에 변경이 필요할 수 있다.

(b) 오작동 시나리오

최초 계획은 프런트엔드 → API → 데이터 변경 순서였지만, 실제로는 데이터 계약을 먼저 확정해야 한다.

에이전트가 합의 순서를 무조건 지키면 불필요한 재작업이 발생한다. 독립적인 작업까지 직렬화한다면 개발 속도에도 불리하다.

(c) 수정

Sequence work by dependencies and agreed priorities.

이는 고정된 실행 순서보다 합의된 우선순위와 실제 의존성을 존중하는 표현이다.

병렬화와 에이전트 간 오케스트레이션의 구체적인 방법은 해당 스킬에 남겨둔다.

⑦ 작업 기록과 대화를 양자택일로 만드는 문제
높음

(a) 문제

keep decisions and acceptance evidence where the project tracks its work rather than in chat

지속 가능한 기록을 남기자는 방향은 좋다. 그러나 모든 프로젝트에 외부 작업 추적 체계가 있는 것은 아니다.

또한 공유 저장소나 이슈 시스템에 기록하는 행위는 단순한 내부 추론이 아니라 영속 상태 변경일 수 있다.

(b) 오작동 시나리오

설치자 저장소에 별도 이슈 트래커가 없는데 에이전트가 기록 체계를 새로 만들거나, 승인받지 않은 공유 Wiki를 수정한다.

또는 기록 시스템에 남겼다는 이유로 현재 대화에서 사용자에게 결과를 제대로 보고하지 않는다.

(c) 수정

해당 문장은 공통 앵커에서 삭제한다.

문서화와 추적 체계 활용은 이미 이슈·마일스톤·Wiki 워크플로 스킬이 담당한다.

이 요구를 확실히 만족시키려면 상주 문장 추가보다 해당 스킬이 실제 필요한 상황에서 선택되고 실행되는지 검증하는 편이 낫다.

⑧ 상주 비용 대비 독립적인 행동 변화가 아직 증명되지 않음
중간

(a) 문제

기존 앵커에는 이미 다음 기준이 존재한다.

§1: 사용자 목표, 사용 흐름, 문서 맥락

§2: 효율적인 방법 선택과 상황 적응

§3: 일관된 작업 범위와 통합 완결성

§4·§5: 성과 검증과 완료 판정

§6: 권한과 영속 상태 변경 경계

신규 단락의 내용 중 상당 부분은 기존 원칙의 다른 표현이다.

(b) 오작동 시나리오

단순 문구 수정이나 마케팅 자료 작성에도 에이전트가 문서를 탐색하고 작업 그룹·단위·기록 체계를 구성해 실제 작업보다 준비에 더 많은 토큰을 사용한다.

더구나 모든 세션에서 약 133토큰을 추가 지불한다. Codex의 지시문 상한은 설치자 자신의 내용에도 영향을 주므로, 누적 상주 크기를 고려해야 한다.

(c) 수정

상주시키려면 실질적 추가 기능은 하나로 제한한다.

「여러 작업으로 구성된 요청을 검증 가능한 성과와 실행 가능한 작업 단위로 연결한다」

현재 제공된 근거로는 해당 원칙이 추가될 때 실제 작업 품질이나 효율이 개선된다고 단정할 수 없다. 개인의 사용 경험은 중요한 요구 근거이지만, 공통 제품의 성능 증거와는 구분해야 한다.

3. 개정 문안 전문

원안을 유지해야 한다면 다음 두 문장으로 줄이겠다. §2 끝에 배치하되, 비교 실험을 통과한 경우에만 채택하는 안이다.

권고 문안 — 2문장

For multi-part work, ground clear, verifiable work units in the current request and applicable project plans or agreed briefs, grouping them by user or operational outcome. Sequence them by dependencies and agreed priorities; consider an outcome complete when its required results and protections are evidenced, not merely when its units are closed.

5. 효과를 확인하는 가장 싼 방법

**동일 과업에 대한 기존 앵커 vs 개정 앵커의 짝지은 비교 실험(Paired A/B)**을 제안한다.

처음부터 실제 PR을 여러 개 생성할 필요는 없다. 우선 계획 생성과 작업 분해까지 실행해 행동 차이를 관측한다.

실험 전에 채점 기준을 고정하고, 결과물과 행동 로그를 앵커 종류를 가린 상태에서 비교한다. 에이전트가 스스로 원칙을 따랐다고 설명했는지는 성과로 인정하지 않는다.

이 계획 단계 실험은 작업 분해 행동의 변화만 확인할 수 있고 최종 구현 품질 향상을 입증하지는 못한다. 유의미한 개선과 중대한 회귀 부재가 확인되면 실제 구현 과업 1~2건에서 추가 검증한다. 모델이나 CLI가 달라지면 결과를 그대로 일반화하지 않는다.

최종 의견

원안에서 반드시 보존할 가치는 두 가지다.

첫째, 작업 항목을 완료하는 것과 사용자가 실제로 필요로 하는 결과를 달성하는 것은 다르다.

둘째, 큰 목표와 개별 구현 작업 사이에 논리적으로 설명 가능하고 검증 가능한 연결이 있어야 한다.

나머지 문서 우선순위, 작업 지시서 작성, 기록 저장, 오케스트레이션은 이미 기존 앵커와 스킬의 소유 영역에 상당 부분 포함된다.

따라서 제 권고는 원안 그대로 채택 반대, 축약안 실험 후 조건부 채택이다.

가장 중요한 판단 질문은 이것이다.

기존 §1~§6만 가진 에이전트와 비교해, 새 문장이 실제로 더 나은 작업 경계와 성과 중심 완료 판정을 만들어 내는가?

이 차이가 확인되지 않는다면, 축약안조차 공통 상주 앵커에 추가하지 않는 것이 이 하네스의 설계 원칙에 더 충실하다.
