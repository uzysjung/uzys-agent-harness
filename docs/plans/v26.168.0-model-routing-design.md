## 2. #681 — 모델 실측 대장

### 2.1 위치와 소유 — 둘로 가른다

| 파일 | 소유(루트 CLAUDE.md §한 원칙 분류) | 누가 쓰나 | install · update · uninstall |
|---|---|---|---|
| **시드** `templates/skills/external-model-consult/references/model-evidence.md` | **하네스 파일** | 이 리포(릴리즈마다) | 디렉터리째 복사 · `update` 가 최신판으로 덮는다(설치자가 고쳤으면 그 파일 하나 백업) · uninstall 이 회수. 네 CLI 자리 모두(§1.1 ④) |
| **프로젝트 대장** `docs/model-evidence.md` | **설치자 파일**(기록에 없다) | 설치자의 에이전트가 **첫 재측정 때 만들고** 덧붙인다. 하네스는 만들지 않는다 | 세 동작 모두 **건드리지 않는다**. 이것이 "update 가 덮지 않는다"의 근거이고, 경우별 예외 코드가 0줄이다 |

**왜 이렇게 가르나**
- 시드를 스킬 `references/` 에 두는 것은 #681 제안 1·3 그대로다(필요할 때만 읽혀 상주 비용 0 — descriptor 불변).
- 누적분을 같은 디렉터리에 두면 `update` 가 지운다(§1.1 ①). `.uzys-agent-harness/` 는 uninstall 이 지운다(②). "함께 쓰는 파일"(하네스 몫 마커 + 설치자 몫)로 만들 수도 있지만, 그러면 `portions` 기록·`stripShared` 경로에 새 파일 종류가 하나 늘고(ADR-097 의 어댑터 4종에 다섯째를 더하는 일) 설치자가 덧붙인 행과 하네스 시드 행이 한 파일에서 섞인다 — **대안 기각**. 설치자 파일 하나로 두면 코드가 0줄이고 원칙에 예외가 없다.
- `docs/model-evidence.md` 인 이유: 번들 스킬이 설치자 프로젝트의 `docs/` 를 가리키는 전례가 있다(`north-star` → `docs/NORTH_STAR.md` · `gh-issue-workflow` → `docs/SPEC.md`·`docs/todo.md` · `compaction-handoff` → `docs/decisions/`). `docs/research/` 는 `audit-harness-fit` 배포물에서 금지된 문자열이라(§1.3) 가리킬 수 없다 — 그래서 한 단계 위다.
- ADR-098(프로젝트 밖에 쓰지 않는다)과 충돌 없음 — 하네스는 이 파일을 쓰지 않고, 에이전트가 프로젝트 안에 쓴다.

**스킬이 설치자에게 하는 지시(시드 머리에 적는다)**: "두 파일을 함께 읽는다 — 이 시드(하네스가 갱신, 편집하지 말 것) + 프로젝트의 `docs/model-evidence.md`(없으면 첫 측정 때 만든다, append-only). 프로젝트 항목이 같은 과제 유형에서 시드와 어긋나면 **프로젝트 항목이 이긴다**(같은 모델·같은 코드베이스 쪽이 가깝다)."

### 2.2 항목 스키마 (시드 · 프로젝트 대장 공통 — 마크다운 표 1행 + 상세 블록)

```markdown
## E-2026-10-04-01 · 구현 — 기존 훅 패턴을 두 화면에 적용 (웹)
- status: measured | planned | superseded-by E-…
- date: 2026-10-04 · where: 사용자 프로젝트(이 리포 아님) · scope: task | user-scene | milestone
- task_type: implementation | design | review | korean-copy | concision | image | debate
- method: same-brief ✓ · isolated-worktree ✓ · blind-scoring ✓ (Opus 5.5 high, diff 만) · mutation-check ✓ · actual-model-from-transcript ✓ · cost = lower bound(사고 토큰 제외) · time = 동시 부하 영향
- candidates: <모델 · effort> …
- result: (표) 조합 | overall/10 | 결함 | 비용(하한) | 시간
- conclusion (한 줄, 조건 포함)
- limits: 과제 1건 · 채점자 1명 · …
- source: <이슈/PR/파일 경로 — 원문 위치>

```

규칙: `method` 의 체크가 빠진 항목은 **그대로 표시**한다(지우지 않는다 — "측정 방법이 약한 항목은 그렇다고 표시", #681 제안 1). `planned` 는 측정 전 항목이다. 항목을 고치지 않고 **새 항목 + `superseded-by`** 로 잇는다(ADR 의 Supersedes 와 같은 규율).

**시드에 들어가는 첫 항목들**
1. `E-2026-10-04-01` — #681 본문 8조합 표 그대로(결론·한계 포함). `where: 사용자 프로젝트`.

3. `E-2026-10-04-P1` · `P2` — **`status: planned`**. #681 댓글(사용자 판단 2026-10-04)의 첫 재측정: ① 설계 판단이 큰 변경 ② 서버/설치자 디스크 경로(update·uninstall 류). 조합 Sonnet 5.5 high · xhigh · max / Opus 5.5 medium · high. "Sonnet 5.5 는 정말 쉬운 개발에 high" 는 **사용자 판단**으로 표시한다(측정값이 아니다).

## 3. #727 — 비교(재측정) 절차와 그 소유자

### 3.1 소유: 대장이 "유효한 항목의 조건"으로 소유한다

절차 = **항목이 `measured` 로 인정받는 조건**이다. 그래서 한 곳, `references/model-evidence.md` §"항목을 추가하려면(재측정 절차)" 에만 둔다. 다른 두 스킬은 **가리키기만** 한다:

- `model-orchestration` — §2.4 의 한 문장(이미 대장을 가리킨다). 더 보태지 않는다.
- `audit-harness-fit/references/verification.md` §"Choose a suitable execution route" 끝에 한 문장: "When the route question is which model or effort to use and no entry in the project's model-evidence ledger covers the task type, propose a bounded comparison under that ledger's entry conditions rather than deciding from model names; record the result there. This is on request only — it adds no recurring comparison." (`docs/research/` 문자열 없음 — §1.3 통과.) `audit-harness-fit/SKILL.md` 라우팅 표는 바꾸지 않는다(Verification 행이 이미 "execution-route advice" 를 받는다).

대안 기각: ⓐ 새 스킬(`model-ab` 류) — 소유자가 둘이 되고 descriptor 상주가 +1 이다. ⓑ `model-orchestration/references/` 신설 — 그 스킬은 원칙문 하나로 설계됐고(#464) 대장을 두 곳에 두면 한쪽이 썩는다.

### 3.2 절차 체크리스트(시드에 적는 본문 — 그대로 옮긴다)

```markdown
## 항목을 추가하려면 — 재측정 절차 (#681 제안 4 · #727)
1. 같은 과제 · 같은 브리프. 브리프는 측정 전에 고정하고 파일로 남긴다.
2. 격리 — 조합마다 별도 worktree(또는 디렉터리). 공유 테스트 자원이 있으면 조합끼리 겹치지 않게.
3. 난이도 사다리 — **쉬운 과제부터, 가벼운 모델·낮은 effort 부터** 올린다. 어려운 과제·강한 모델 조합은
   그 아래가 떨어진 뒤에 넣는다(#727). 과제 유형이 다르면 다른 항목이다.
4. 블라인드 채점 — 채점자는 diff(산출물)만 보고 어느 조합인지 모른다. 채점자 모델·effort 를 기록한다.
   AC 통과 · 결함 등급 · 가드 뮤테이션(테스트가 실제로 무는지)을 직접 잰다.
5. 실제값 — 모델·effort 는 요청값이 아니라 트랜스크립트의 실제값을 적는다. 못 확인하면 `unknown`.
6. 비용은 **하한**(사고 토큰이 빠질 수 있다) · 시간은 동시 부하를 적는다. 모르는 값은 `unknown` 이고 꾸미지 않는다.
7. 결론은 조건 포함 한 줄. 표본 수와 실패 사례를 적고, 적은 사례의 승률을 법칙으로 쓰지 않는다.
8. 단위(scope) — 기본은 과제 1건. 사용자 씬·마일스톤 단위로 재면 산출물 기준에 **PR 묶음의 리그레션 결과**를
   넣고 `scope` 를 그렇게 적는다. 같은 양식, 다른 단위.
9. 언제 — 사용자가 요청했을 때, 또는 라우팅 결정에 쓸 항목이 없고 틀렸을 때의 비용이 측정 비용을 넘을 때
   **제안**한다. 주기 실행·훅·반복 루프를 만들지 않는다. 실제 실행에는 그 격리 자리·도구·비용에 대한 승인이 필요하다.
10. 적는 곳 — 프로젝트 `docs/model-evidence.md`(append-only). 시드(이 파일)는 편집하지 않는다.
```

"지속적으로 A/B" (#727 원문)는 **주기 실행이 아니라 요청마다 쌓인다**로 읽었다(가정 §8-3). 이유: `audit-harness-fit` 경계가 "introduces no recurring audit hook … or approval loop" 이고, 측정 1회가 수십 분·수 달러다(#681 표) — 자동 반복은 설치자가 모르는 비용을 만든다.

### 3.3 "사용자 관점 동일 묶어서 마일스톤 · PR 묶고 리그레션" 으로의 확대 — 무엇이 나가나

**나가는 것**: 스키마의 `scope` 필드 + 절차 8번 한 줄. 끝.
**안 나가는 것**: 새 스킬 · 룰 변경 · 그룹핑 도구.
이유: 사용자 씬 단위로 변경을 모아 검증한다는 규율은 배포 룰 `ship-checklist.md:5`("검증의 리듬") 와 `reviewer` 에이전트("입력 = 사용자 씬")가 **이미** 담고, 마일스톤·이슈 묶음은 `gh-issue-workflow` 가 담는다. #727 이 더 묻는 것은 "그 단위에서도 모델·effort 비교를 할 수 있나"이고, 답은 "같은 양식으로 단위만 바꿔 적는다"다. 측정 단위를 늘리는 데 필요한 것은 필드 하나지 장치가 아니다 — 관측 없이 장치를 만들지 않는다(루트 CLAUDE.md 함정 1 · 메모리 "가장 단순한 판본을 먼저").

## 4. #728 — `audit-harness-fit` 라운드 흐름 + 단계 강제 리뷰 문구

### 4.1 라운드 흐름 — 문구와 자리

### 5.7 카탈로그 배선

| 항목 | `multi-model-debate` | `gemini-delegate` · `chatgpt-delegate` · `genspark-delegate` |
|---|---|---|
| `INTERNAL_BUNDLED_SKILL_IDS` | 추가 | 추가(셋) |
| `DEV_METHOD_SKILL_IDS` | **넣지 않는다** — 수단(ADR-105 D2 와 같은 판정: external-model-consult 와 같은 부류) | 넣지 않는다 |
| `tier` · `source` · `category` | `official` · `uzys` · `dev-tools`(external-model-consult 와 같다) | 같다 |
| `condition` | **`has-dev-track`**(기본) | **`opt-in`** |
| `CONTINUOUS_SKILLS` | 넣지 않는다(작업형 — 프롬프트가 토론을 닮는다) | 넣지 않는다 |
| 위저드 | 개발 트랙에서 미리 체크 | 3단계에 행이 보이되 체크 해제(`--with <id>` 로 켬). 라벨에 "needs a browser tool + your logged-in browser" 를 적는다(description 안) |
| 기존 설치본 | 개발 트랙 기록이 있으면 `update` 가 두 자리에 깐다(§1.1 ⓒ) | update 는 깔지 않는다(opt-in 은 기록에 없다) |

**브라우저 3종을 opt-in 으로 두는 이유**(사용자의 "uzys 스킬은 대부분 기본" 과의 긴장 — 사용자 결정 §7-1):

| 축 | 기본 체크(has-dev-track) | opt-in(추천) |
|---|---|---|
| 실행 가능 비율 | 전제가 하네스 밖에 셋 더 있다(Chrome 확장 · 직접 Anthropic 플랜 또는 Codex 앱 · 그 서비스 계정). Codex CLI · OpenCode · Antigravity 설치자에게는 **문서상 또는 미확인으로 안 된다**(§5.6). `external-model-consult` 를 기본으로 올릴 때(ADR-105)의 논거 "설치는 성공하고 실행 때 알린다" 는 같지만, 안 되는 설치자의 비율이 훨씬 크다 | 원하는 사람만 받는다 |
| 상주 비용 | descriptor 3개가 **모든 개발 트랙 설치자**에게 매 세션 상주한다(현재 descriptor 15개 ~1,698 tok, ADR-105 실측 — 3개면 비슷한 비율로 늘고 `cost:baseline` 갱신) | 0 |
| 권한 | 설치 자체가 권한은 아니다(스킬도 그렇게 적었다). 그러나 "사용자의 **로그인된** 브라우저로 서드파티 서비스에 쓰고 유료 사용량을 소모"하는 능력을 **묻지 않고** 모든 개발 트랙에 깔면, 설치자가 고르지 않은 능력이 상주한다 — #489 가 `agent-browser` 를 opt-in 으로 내린 축("computer-use 가 같은 일을 하고 설치 비용이 가장 크다")과 같다 | 고른 사람의 디스크에만 |
| 사용자 결정의 범위 | #726 의 "대부분 기본" 결정은 그때의 opt-in 4종(ci-scaffold · model-orchestration · external-model-consult · natural-korean)을 대상으로 내려졌고 브라우저 위임 스킬은 그 자리에 없었다 | 결정을 넓히지 않고 **묻는다**(§7-1). 기본값은 opt-in 으로 두고 사용자가 뒤집으면 `condition` 한 줄이다 |

`multi-model-debate` 가 기본인 이유: 브라우저 전제가 없다(adapters 가 "없으면 unavailable 로 기록, 승인된 다른 경로로 진행"). 기본 설치본만으로도 `external-model-consult` 의 Gemini + Codex 로 "서로 다른 실제 모델 2개"가 성립한다. 상주 +1 descriptor 는 사용자의 "대부분 기본" 결정 범위 안이다.
