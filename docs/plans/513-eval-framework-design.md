## 2. 과제 선정 근거 (묶음 v1)

- **DeepSWE 어려운 31** — DeepSWE 공개 시행 결과(`trials.json`, sha256 `310cb428…`)에서 `mini_swe_agent_glm_5_3_max` 1~3/4 통과 · 다른 69 설정 평균 통과율 ≤ 중앙값 0.598(`select-hard.py` → `deepswe-hard-v1.txt`). 우리 A 로 고르면 평균으로의 회귀로 효과 0 에서도 B 가 약 +20%p 유리(공개 데이터 실측, 검토 재현). 공개 70 설정은 전부 mini-swe-agent — Claude Code 로의 전이는 증명되지 않았다(리포트에 A 관측 통과율 vs 공개 0.548 · 무정보 과제 수).
- **SWT-bench Verified** — 이슈를 재현하는 테스트(수정 전 실패 · 수정 후 통과)를 쓰는가. 하네스의 test-policy · implementer 가 노리는 능력이다(가설, 조사 harness-fit 1순위). 무작위 순서. 원본이 SWE-bench Verified(오염 지적)라 **절대 점수는 내세우지 않고 A·B 차이만** 쓴다. 앞 60 의 저장소 분포 = django 28 · matplotlib 8 · sympy 6 · sphinx 6 · 기타 12.
- **NL2Repo** (v2) — 명세만으로 빈 폴더에서 라이브러리를 완성하는가. 선정 = Medium·Hard 중 `test_case_count` 상위, 범주 층화(조사 user-list).
- 제외와 이유: 도구 없는 HLE · 시각 3종 · Apex(수학) — 하네스가 작동할 자리가 없다. Agents' Last Exam — 맥에서 실행 불가에 가깝다. ProgramBench · Terminal-Bench — 헤비 v2 후보(무겁거나 일부 과제가 이 머신 밖).
- **결과는 진 것까지 전부 낸다.** 벤치마크마다 따로 보고하고 합산 점수를 만들지 않는다.

## 3. 두 팔 — 차이는 하네스 하나

| | A (노하네스) | B (하네스 판 X) |
|---|---|---|
| 루트 `CLAUDE.md` | **목표 · 스택 두 절** | 같은 두 절 + 설치가 넣는 import 블록(`@CLAUDE-uzys-harness.md`) |
| 하네스 | 없음 | `install --track base --cli claude` |

- 목표·스택은 과제 메타데이터에서 기계적으로 만든다 — DeepSWE: `display_title — display_description` · `language · repository_url`. SWT-bench: `Write test cases that reproduce the reported issue (do not fix it)` · `Python · <instance 저장소>`. 빌드·테스트 명령은 넣지 않는다.
- 두 팔 모두 에이전트 설치 단계에서 CLAUDE.md 를 먼저 쓰고 B 는 그 뒤 설치한다(설치기는 기존 본문을 두고 import 블록만 더한다 — 리허설에서 확인). 상류에 CLAUDE.md 가 있으면 두 팔 모두 같은 두 절을 덧붙인다. 새 CLAUDE.md 는 **두 팔 모두** 채점 diff 에서 뺀다(`.git/info/exclude`, 상류 파일이면 skip-worktree — 이전 §4.3 규칙을 양팔에).
- 작업 폴더는 벤치마크마다 다르다(DeepSWE `/app` · SWT-bench `/testbed`) — B 실행기의 경로를 인자로 받는다.

## 4. 채점과 종료 사유

1. **공식 점수**(주) — 각 벤치마크 규칙 그대로. DeepSWE: 커밋분(`git diff <base> HEAD`) → 별도 검증 컨테이너의 숨은 테스트, reward 1 = F2P·P2P 전부. SWT-bench: 작업 트리의 테스트 변경 → 수정 전 실패·수정 후 통과(성공률 S) · 커버리지 증가 ΔC(보조).
2. **DeepSWE 작업 트리 점수**(보조) — 31 과제 로컬 `task.toml` 에 둘째 collect `cd /app && git add -A -N && git diff --binary <base> > /logs/artifacts/worktree.patch` → 사후 채점(검토 B6). "풀 능력"과 "끝까지 제출"을 가른다. SWT-bench 는 원래 작업 트리 채점이라 필요 없다.
3. **종료 사유**(시행마다 기계 판정): 스스로 끝냄+제출 · 스스로 끝냄+제출 없음 · **백그라운드 대기 중 종료**(마지막 `result` 직후 `task_updated killed`) · 시간 상한 · 턴 상한 · API 오류. SWT-bench 는 **"테스트만" 위반**(소스 파일 변경 여부)도 기록한다.

## 5. 판정 (사전 등록 — 측정 전에 고정)

**슈퍼라이트 · 라이트 = 경보만**(효과 주장 없음). 각 항목 PASS / WARN:

| # | 경보 | WARN 조건 |
|---|---|---|
| C1 | 하네스가 실렸나 | B 시행 중 하나라도 §6 증거 불일치 → **측정 무효**(배관 결함) |
| C2 | 제출 규율 | B 에 "제출 없음" 또는 "백그라운드 대기 중 종료"가 1건이라도 (A 의 같은 사건은 함께 표시) |
| C3 | 방해 신호 | (A 만 성공 − B 만 성공) ≥ 2(슈퍼라이트) · ≥ 3(라이트) |
| C4 | 비용 | 둘 다 끝까지 간 과제에서 B/A 과제 세션 시간 또는 입력 토큰 중앙값 > 2.0 |
| C5 | 시간 상한 | B 의 시간 상한 도달 수 > A 의 수 + 1 |
| C6 | 측정 안정성 | 인프라 무효(1113 · 끊김) > 20% → 다시 돈다 |

WARN 은 "원인을 본다"이지 "효과가 나쁘다"가 아니다. 리포트에 시행 원자료를 함께 낸다.

**미디엄 · 헤비 = 효과 판정**. 벤치마크마다 따로:
- 단위 = 과제. Δ = B 통과율 − A 통과율(3회 중). 평균 Δ 의 95% CI = 과제 재표집 부트스트랩 10,000회.
- 결론은 셋만: CI 하한 > 0 → **"더 잘 푼다"** · CI 상한 < 0 → **"방해한다"** · 그 밖 → **"판별 불가(검출 한계 …)"**. "효과 없음"이라 쓰지 않는다. 벤치마크가 둘 이상이면 "더 잘 푼다" 주장에 Holm 보정을 건다.
- 검출 한계(공개 p 모의, 효과 0 오판 2–3%): DeepSWE 20×3 → +15%p 51% · +20%p 81% · 31×3 → 70% · 90%. SWT-bench 는 라이트의 관측 통과율로 산정해 미디엄 전에 적는다.
- **판 비교는 퇴행 경보만**: (Δ_Y − Δ_X) CI 상한 < 0 → "판 Y 퇴행"(검출 한계 약 +25%p, 검토 B1). 개선은 그 판의 Δ CI 로만 말한다.
- 보조(판정 아님): pass^3 · DeepSWE 작업 트리 Δ · SWT-bench ΔC · 성공 1건당 토큰 · 시간 비율 · 종료 사유 분포 · "테스트만" 위반 수.
