## 1. 고정하는 것 — 과제 묶음 `deepswe-hard-v1`

- **선정 데이터는 DeepSWE 공개 시행 결과**(`https://deepswe.datacurve.ai/artifacts/v1.1/trials.json`, B2, 2026-10-19 받음 · `included_in_score` 만)이다. 우리 실행 결과는 선정에 쓰지 않는다 — 우리 A 로 고르면 평균으로의 회귀로 효과 0 에서도 B 가 약 +20%p 유리하게 나온다(공개 데이터 실측: 앞 2회 0/2 인 20과제가 뒤 2회 0.20, 검토에서 재현).
- **규칙**: `mini_swe_agent_glm_5_3_max` 에서 4회 중 **1~3회 통과**(바닥·천장 제외 — 정보가 있는 과제) **이고**, 나머지 69 설정의 평균 통과율 ≤ 그 중앙값(**0.598**). 결과 **31과제**. 목록 = `513-eval-evidence/deepswe-hard-v1.txt`(sha256 `de428218…`) · 선정 스크립트 `select-hard.py` · 원자료 sha256 `310cb428…`(저장소 밖 `~/eval-513/public/`).
- **묶음 판(-vN)을 올리는 것은 넷뿐**: 과제 목록 · 선정 규칙 · DeepSWE 판 · 채점 규칙(§4 의 collect 2개 포함). Claude Code 판 · 과제 모델 · effort · 상한 · 이미지 digest 는 **잠금본(§6)에 기록만** 한다 — 바뀌어도 추적은 이어지고, 잠금본이 다른 두 측정의 비교에는 "런타임 상이" 표시를 단다(같은 기간에 다시 돈 A 가 그 차이의 대조군이다).
- 한계(공시): 공개 70 설정은 전부 mini-swe-agent 다. 이미 돌린 겹치는 3과제(bandit · pest · textual, 공개 3/4)에서 우리 A 는 0 · 0 · 1 — 대역이 Claude Code+GLM 에서는 바닥 쪽으로 밀릴 수 있다(민감도: A 평균 0.33 이면 +15%p 61% · +20%p 81%). 그래서 리포트에 "A 관측 통과율 vs 공개 0.548 · 양팔 모두 0/3 또는 3/3 인 무정보 과제 수"를 낸다. 과제별 p 는 4회 추정이라 거칠다. **이미 돌린 옛 시행은 이 측정에 쓰지 않는다.**

**정리 trial (과제당 1, Pier 로)** — 에이전트 = `HarnessedClaudeCode` 의 **정리 전용 모드**(설치 + 정리 3회, 과제 세션 없음), `-m claude-opus-5-5 --env-file ~/eval-513/anthropic.env --disable-verification`. egress 는 `api.anthropic.com` 하나 — 정리 세션이 `git fetch`·웹으로 상류 수정 커밋에 닿아 CLAUDE.md 에 적는 오염 경로를 막는다(trial 의 `egress-proxy/` 설정으로 증명). 키는 env-file 로만, 실패는 `result.json` 에 남는다.

**묶음 내용** = 설치 직후 스냅샷 대비 정리 뒤 **내용이 달라진 `/app` 파일 전부**(tracked skip-worktree 파일 포함 — 상류 `AGENTS.md` 가 있는 저장소에서 정리가 그 파일을 편집한 실측이 있다)의 tar + 삭제 목록 + sha256 manifest. `CLAUDE_CONFIG_DIR` 아래(자동 메모리 등)는 넣지 않는다. 삭제 목록이 비어 있지 않으면 정리 결함으로 보고한다. 묶음은 `--artifact` 로 꺼내 `~/eval-513/prep-bundle/<하네스 판>/<과제>.tar` 에 둔다.

**B 과제 trial 의 반입** — `run()` 첫 단계에서 묶음을 넣고(읽기 전용 마운트 또는 exec heredoc — 리허설 1회로 하나 고정) 풀고, §4.3 의 git 규칙(skip-worktree · exclude)을 다시 적용한 뒤 `git status --porcelain -uall` 이 설치 직후와 같아야 시작한다. 다르면 그 시행은 배관 오류(무효 · 재실행).

**정리 실패 처리 — 어느 경우에도 과제를 빼지 않는다**(정리 결과로 표본을 고르면 하네스에 유리해진다. 이전 §5.3 과 `pier_agent_b.py` 21–22행의 원칙):

## 4. 채점 — 점수 둘과 종료 사유

1. **공식 점수**(주): DeepSWE 규칙 그대로 — `git diff --binary <base> HEAD`(커밋분)를 별도 검증 컨테이너가 받아 숨은 테스트. reward 1 = F2P·P2P 전부 통과.
2. **작업 트리 점수**(보조) — "풀 능력"과 "끝까지 제출"을 가른다(중단 결과의 리뷰어 대기 중 커밋 없이 종료 2건). 검증기는 `model.patch` 만 받으므로(`environment_mode = "separate"`), 31 과제의 로컬 `task.toml` 에 **둘째 collect** `cd /app && git add -A -N && git diff --binary <base> > /logs/artifacts/worktree.patch` 를 model.patch 뒤에 더한다(Pier 의 `collect` 는 목록). `-N` 은 `.gitignore`·`.git/info/exclude`·skip-worktree 를 따르므로 B 의 하네스 파일이 자동으로 빠진다 — 양팔 동일, 에이전트 무수정. 채점은 사후: `tests/Dockerfile` 이미지에 `worktree.patch` 를 `model.patch` 자리로 넣고 `test.sh`(시행당 약 1.5분, 186 → 약 5h). `task_checksum` 이 바뀌므로 묶음 판 v1 의 고정 항목에 "collect 2개"를 적는다.
3. **종료 사유**(시행마다 기계 판정): 스스로 끝냄+커밋 · 스스로 끝냄+커밋 없음 · **백그라운드 대기 중 종료**(마지막 `result` 직후 `task_updated killed`) · 시간 상한 · 턴 상한 · API 오류.

## 5. 판정 (사전 등록 — 측정 전에 고정, 측정 중 바꾸지 않는다)

- 단위 = 과제. 과제별 **Δ = B 통과율 − A 통과율**(각 3회 중). 주 지표 = 31과제 평균 Δ, 95% CI = 과제 재표집 부트스트랩 10,000회(H8 · B20). B 의 3회가 정리 묶음 1개를 공유하므로 **정리 간 분산은 이 CI 에 없다**(공시).
- 결론은 셋만: CI 하한 > 0 → **"어려운 과제를 더 잘 푼다"** · CI 상한 < 0 → **"방해한다"** · 그 밖 → **"판별 불가(검출 한계 약 +15%p)"**. "효과 없음"이라 쓰지 않는다(H 결론 2).
- **판 비교는 퇴행 경보만**: (Δ_Y − Δ_X) 의 CI 상한 < 0 이면 "판 Y 가 퇴행했다". 그 밖에는 판 Y 의 개선을 **판 Y 자신의 Δ CI** 로만 말한다(판 간 차이로 "개선"을 주장하지 않는다 — 검출 한계 +25%p).
- 보조(판정 아님): pass^3(3회 모두 성공한 과제 수, B18) · 작업 트리 점수의 Δ · 성공 1건당 입력·출력 토큰 · 과제 세션 시간 비율(둘 다 성공한 과제의 중앙값) · 종료 사유 분포 · 하네스 고유 실패 건수 · A 관측 통과율과 무정보 과제 수(§1).
