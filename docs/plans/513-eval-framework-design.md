## 3. 실행

- **과제당 팔당 3회**(31 × 2 × 3 = 186 시행). 검정력(조사 B 결론 4, 공개 GLM 통과율로 모의): 30×3 은 +15%p 에 62% · +20%p 에 88%. **+15%p 미만은 판별하지 못한다** — 보고서 첫 줄에 적는다.
- 순서: 과제 순서와 과제 안의 팔 순서를 `seed=판 번호` 로 섞고, 같은 과제의 6 시행(A×3 · B×3)을 붙여 돈다 — 제공자 상태·시간대 잡음이 짝 안에서 상쇄된다(H11: 자원 설정만으로 6%p).
- **판 비교는 매번 A 를 새로 돈다.** 과거 A 와 맞대지 않는다(B 결론 6). 판 X 와 판 Y 의 비교는 같은 과제 묶음에서 각자의 (B−A) 를 과제별로 비교한다.
- 동시 2(Docker 8 CPU · 18.5 GiB) · 1113 은 그 시행 무효 → 한도 회복 뒤 재실행 · 결과 없이 끊긴 시행은 무효 → 재실행 · 그 밖의 실패(시간 상한 포함)는 실패로 센다. 기존 `run-full.sh` 를 과제 묶음 · 반복 · 정리 묶음 입력으로 넓힌다.

## 4. 채점 — 점수 둘과 종료 사유

1. **공식 점수**(주): DeepSWE 규칙 그대로 — 커밋된 변경(`git diff <base> HEAD`)에 숨은 테스트. reward 1 = F2P·P2P 전부 통과.
2. **작업 트리 점수**(보조): 같은 검증기를 **커밋 안 된 변경까지 포함한 최종 작업 트리**에 돌린다. "풀 능력"(2)과 "끝까지 제출"(1)을 가른다 — 중단 결과에서 B 가 리뷰어 대기 중 커밋 없이 끝난 2건이 정확히 이 차이다(H 결론 7). B 의 하네스 파일은 이 diff 에서 뺀다(§4.3 의 규칙 재사용).
3. **종료 사유 분류**(시행마다 기계 판정): 스스로 끝냄+커밋 · 스스로 끝냄+커밋 없음 · **백그라운드 대기 중 종료**(`task_updated killed` 가 마지막 `result` 직후) · 시간 상한 · 턴 상한 · API 오류. 

## 5. 판정 (사전 등록 — 실행 전에 고정, 실행 중 바꾸지 않는다)

- 단위 = 과제. 과제별 **Δ = B 통과율 − A 통과율**(각 3회 중). 주 지표 = 31과제 평균 Δ, 95% CI = 과제 재표집 부트스트랩 10,000회(H8 · B20).
- 결론 세 가지만 쓴다: CI 하한 > 0 → **"어려운 과제를 더 잘 푼다"** · CI 상한 < 0 → **"방해한다"** · 그 밖 → **"판별 불가(검출 한계 약 +15%p)"**. "효과 없음"이라고 쓰지 않는다(H 결론 2).
- 보조(판정 아님): pass^3(3회 모두 성공한 과제 수 — "가끔 → 매번" 개선, B18) · 작업 트리 점수의 Δ · 성공 1건당 입력·출력 토큰 · 과제 세션 시간 비율(둘 다 성공한 과제의 중앙값) · 종료 사유 분포 · B 의 하네스 고유 실패(백그라운드 대기 종료 등) 건수.
- 판 비교: 판 Y 의 Δ − 판 X 의 Δ 를 과제별로, 같은 부트스트랩. 결론 문구는 위와 같은 세 가지.
