## 2. 과제 선정 근거 (묶음 v1)

- **DeepSWE 어려운 31** — 공개 시행 결과(`trials.json`, sha256 `310cb428…`)에서 `mini_swe_agent_glm_5_3_max` 1~3/4 통과 · 다른 69 설정 평균 ≤ 중앙값 0.598(`select-hard.py` → `deepswe-hard-v1.txt`). 우리 A 로 고르면 평균으로의 회귀로 효과 0 에서도 B 가 약 +20%p 유리(공개 데이터 실측). 공개 70 설정은 전부 mini-swe-agent — Claude Code 로의 전이는 증명되지 않았다(리포트에 A 관측 통과율 vs 공개 0.548 · 무정보 과제 수).
- **SWT-bench Verified** — 이슈를 재현하는 테스트(수정 전 실패 · 수정 후 통과)를 쓰는가. 하네스의 test-policy · implementer 가 노리는 능력(가설). 원본이 SWE-bench Verified(오염 지적)라 **A·B 차이만** 쓴다. 앞 60 의 저장소 = django 28 · matplotlib 8 · sympy 6 · sphinx 6 · 기타 12.
- **NL2Repo** (v2) — 명세만으로 빈 폴더에서 라이브러리를 완성하는가. 선정 = Medium·Hard 중 `test_case_count` 상위, 범주 층화.
- 제외: 도구 없는 HLE · 시각 3종 · Apex(수학) — 하네스가 작동할 자리가 없다. Agents' Last Exam — 맥에서 실행 불가에 가깝다. ProgramBench · Terminal-Bench — 헤비 v2 후보.
- **결과는 진 것까지 전부 낸다.** 벤치마크마다 따로 보고하고 합산 점수를 만들지 않는다.

## 3. 두 팔 — 같은 실행기, 차이는 하네스 하나

**두 팔 모두 같은 에이전트 클래스**(`EvalClaudeCode`, Pier `claude-code` 상속, 인자 `harness=off|<판>` · `workdir`)로 돈다 — A 를 Pier 내장 그대로 두면 CLAUDE.md 를 쓰는 자리도 채점 diff 에서 빼는 자리도 없다(재검토 B2).

| | A (노하네스) | B (하네스 판 X) |
|---|---|---|
| 빌드 단계 | Claude Code 2.1.302 | 같음 + `npm install -g @uzysjung/agent-harness@X` **까지만** |
| `run()` ① | 루트 `CLAUDE.md` = **목표 · 스택 두 절** | 같음 |
| `run()` ② | — | `agent-harness install --track base --cli claude`(기존 CLAUDE.md 본문을 두고 import 블록만 더한다) |
| `run()` ③ | `<workdir>/.git/info/exclude` 에 CLAUDE.md(상류 파일이면 skip-worktree) | 같음 + 설치 기록의 하네스 경로 전부 |
| `run()` ④ | 증거 기록(§6) · `head-before` | 같음 |
| `run()` ⑤ | 과제 세션: GLM-5.3 · effort max · 턴 300(안전망) · 예산 상한 없음 | 같음 |
| `finally` | 벤치마크별 정규화(§4) | 같음 |

- CLAUDE.md 를 `run()` 에서 쓰는 이유: 빌드 단계(`install_spec()`)는 과제 정보 없이 돌아 제목·스택을 모르고, CLAUDE.md 없이 설치가 먼저 돌면 템플릿 본문이 생겨 두 팔의 CLAUDE.md 가 달라진다(재검토 B3).
- 목표·스택은 과제 메타데이터에서 기계적으로 — DeepSWE: `display_title — display_description` · `language · repository_url`. SWT-bench: `Write test cases that reproduce the reported issue (do not fix it)` · `Python · <instance 저장소>`. 빌드·테스트 명령은 넣지 않는다.
- **시간 상한은 각 벤치마크 공식값을 양팔에**: DeepSWE 3h(배율 1.0 — 공개 시간 꼬리로 B 가 2h 를 넘을 과제 4개가 3h 안에 든다) · SWT-bench **60분**(Harbor 어댑터의 20분은 B 과제 세션 1.55배에서 B 만 먼저 닫혀 "재현 테스트를 쓰는가" 대신 "20분 안에 끝나나"를 재게 된다 — 재검토 B4. 공식 SWT-bench 의 벽시계 규칙은 미확인). 시간 차이는 C4 로 본다. 벤치마크마다 별도 `pier run`.
- 과제 이미지는 과제가 끝나면 지운다(SWT 압축 1.2–1.8 GB/과제).

## 4. 채점·정규화와 종료 사유

1. **공식 점수**(주) — 각 벤치마크 규칙 그대로.
   - DeepSWE: 커밋분(`git diff <base> HEAD`) → 별도 검증 컨테이너의 숨은 테스트, reward 1 = F2P·P2P 전부. 지시문이 "새 브랜치에서 커밋하라"다.
   - SWT-bench: 채점은 `git add -A; git diff HEAD`(test.sh 85–86행) — **커밋한 변경은 패치에서 사라져 0점**이다. 지시문은 커밋을 말하지 않는데 하네스 스킬은 커밋을 자주 말한다 → B 만 체계적으로 0 이 된다(재검토 B1). 그래서 **양팔 모두 `finally` 에서 `git reset --soft $(cat head-before)`** 로 커밋을 작업 트리로 되돌린 뒤 채점한다(타임아웃에도 `finally` 가 돌고 검증기도 돈다 — Pier execution.py 254–263 · trial.py 981→372). 커밋 여부는 종료 사유에 남긴다. 패치 경로는 테스트 지시어로 쓰이므로(`.md` · `.json` 등 11종 확장자만 빠진다) 하네스 파일·CLAUDE.md 가 섞이면 테스트 실행이 깨진다 — §3 ③ 의 exclude 가 이것을 막는다.
2. **DeepSWE 작업 트리 점수**(보조) — 31 과제 로컬 `task.toml` 에 둘째 collect `cd /app && git add -A -N && git diff --binary <base> > /logs/artifacts/worktree.patch` → 사후 채점. **슈퍼라이트 전에 넣는다**(뒤에 넣으면 채점 규칙 변경으로 묶음 판이 올라가 앞 시행을 재사용할 수 없다).
3. **종료 사유**(기계 판정): 스스로 끝냄+제출 · 스스로 끝냄+제출 없음 · **백그라운드 대기 중 종료**(마지막 `result` 직후 `task_updated killed`) · 시간 상한 · 턴 상한 · API 오류 · (SWT) 커밋함. **제출**의 정의 — DeepSWE: `model.patch` 비어 있지 않음(HEAD ≠ base) · SWT: 정규화 뒤 패치 비어 있지 않음.
4. SWT **"테스트만" 위반**(소스 파일 변경)도 기록한다 — 채점이 스스로 벌한다(정답 적용 뒤 모델 패치 적용 실패 → resolved False, 또는 수정 전에도 통과 → F2P 아님). B 의 구현 성향을 해석하는 자리다.

## 5. 판정 (사전 등록 — 측정 전에 고정)

**슈퍼라이트 · 라이트 = 경보만**(효과 주장 없음). 각 항목 PASS / WARN:

| # | 경보 | WARN 조건 | 작동 특성(효과 0 · 1반복) |
|---|---|---|---|
| C1 | 하네스가 실렸나 | B 중 하나라도 §6 증거 불일치(세션 직전 기준) → **측정 무효** | — |
| C2 | 제출 규율 | B 에 "제출 없음" 또는 "백그라운드 대기 중 종료"가 1건이라도(A 의 같은 사건은 함께 표시) | 결정적 신호 |
| C3 | 방해 신호 | 슈퍼라이트: **갈린 과제 표시만**(판정 없음) · 라이트: (A 만 성공 − B 만 성공) ≥ 4 | 라이트 오경보 7–9% · 30%p 해악 검출 62% |
| C4 | 비용 | 둘 다 끝까지 간 과제에서 B/A 과제 세션 시간 또는 입력 토큰 중앙값 > 2.0 | — |
| C5 | 시간 상한 | B 의 시간 상한 도달 수 > A 의 수 + 1 | — |
| C6 | 측정 안정성 | 인프라 무효(1113 · 끊김) > 20% → 다시 돈다 | — |

WARN 은 "원인을 본다"이지 "효과가 나쁘다"가 아니다. 리포트에 시행 원자료를 함께 낸다.

**미디엄 · 헤비 = 효과 판정**. 벤치마크마다 따로:
- 단위 = 과제. Δ = B 통과율 − A 통과율(3회 중). 평균 Δ 의 95% CI = 과제 재표집 부트스트랩 10,000회.
- 결론은 셋만: CI 하한 > 0 → **"더 잘 푼다"** · CI 상한 < 0 → **"방해한다"** · 그 밖 → **"판별 불가(검출 한계 …)"**. "효과 없음"이라 쓰지 않는다. 벤치마크가 둘 이상이면 "더 잘 푼다" 주장에 Holm 보정.
- 검출 한계(공개 p 모의, 효과 0 오판 2–3%): DeepSWE 20×3 → +15%p 51% · +20%p 81% · 31×3 → 70% · 90%. SWT-bench 는 라이트의 관측 통과율로 산정해 미디엄 전에 적는다.
- **판 비교는 퇴행 경보만**: (Δ_Y − Δ_X) CI 상한 < 0 → "판 Y 퇴행"(검출 한계 약 +25%p). 개선은 그 판의 Δ CI 로만 말한다.
- 보조(판정 아님): pass^3 · DeepSWE 작업 트리 Δ · SWT ΔC · 성공 1건당 토큰 · 시간 비율 · 종료 사유 분포 · "테스트만" 위반 수 · SWT 커밋 수.
