## 2. ⓐ 삭제 3종 — 기존 설치본에서 어떻게 되나

**결정: 남긴다 + update 화면이 정확히 말한다 + uninstall 은 지금 그대로.** 지우지 않는다.

| 자산 | 방식 | update | uninstall | 근거 |
|---|---|---|---|---|
| product-skills | plugin (Claude 전용) | 지우지 않음. **새 안내 줄**(지금은 무음) | `--only product-skills` → `claude plugin uninstall --scope project product-skills@claude-code-skills` (기록의 pluginId) | ADR-063 · ADR-093 |
| agentmemory | plugin (Claude 전용) | 같음 | 같음(`agentmemory@agentmemory`). 별도 런타임 서버(`npx @agentmemory/agentmemory`)는 설치자가 띄운 것이라 기록 밖 — 하네스가 다루지 않는다 | ADR-063 · ADR-093 · ADR-096(기록이 몫을 정한다) |
| revealjs | skill (4-CLI) | 갱신하지 않음(지금도 그렇다). 일반 줄 대신 **전용 안내 줄** | `--only revealjs` → 기록된 파일만 삭제(#573). 기록 없는 옛 판은 남은 자리를 안내 | ADR-078 · ADR-046 |

**왜 update 가 지우지 않나** — 세 가지가 같은 방향이다. ① 루트 CLAUDE.md "지우는 동작은 확인을 받고, 터미널이 없으면 명시 플래그를 요구한다" — `update` 에는 확인 단계가 없고 무엇을 깔지 다시 묻는 자리도 아니다(ADR-075 범위 밖 사유). ② 셋 다 설치자가 위저드 체크나 `--with` 로 **골라서** 깐 것이다(전부 opt-in). 하네스가 "불필요"라고 선언한 것이 설치자의 의도를 대신하지 않는다(ADR-075 Alternatives). ③ 스킬 디렉터리에는 설치자 파일이 섞인다(ADR-046).

**왜 `RETIRED_SKILL_IDS` 에 넣지 않나** — 그 목록은 **디스크**에서 이름을 찾는다(`staleSkillDirs`). 하네스 기록 없이 설치자가 직접 `npx skills add ryanbbrown/revealjs-skill` 로 깐 `revealjs` 도 "은퇴 · 지워도 된다" 로 잡힌다 — 디스크 존재는 소유의 증거가 아니다(ADR-096). 그 목록은 이름이 우리 것인 **번들** 스킬용으로 남긴다. 외부 자산은 **설치 기록**에서만 고른다.

### 2.1 새 데이터 하나 — `REMOVED_CATALOG_ASSETS`

`src/external-assets.ts` 에 추가(카탈로그 바로 아래, `RENAMED_SKILL_IDS` 옆):

```ts
/**
 * 카탈로그에서 빠진 외부 자산 — **설치 기록에** 이 id 가 남은 설치본에게 update 화면이 할 말을 정한다.
 * 기록에서만 고른다(디스크 존재 ≠ 소유, ADR-096). 지우지 않는다(ADR-093). replacedBy 는 지금 카탈로그에 실재해야 한다.
 */
export const REMOVED_CATALOG_ASSETS: Readonly<Record<string, { replacedBy?: string }>> = {
  "product-skills": {},
  agentmemory: {},
  revealjs: {},
  "trailofbits-skills": { replacedBy: "claude-security" },
  "web-video-presentation": { replacedBy: "hyperframes" },
};
```

ADR-093 이 퇴역시킨 11종(superpowers 등)을 소급해 넣지 않는다 — 이번 범위 밖. 그쪽은 지금처럼 skill 이면 일반 줄, plugin 이면 무음이다(§12 범위 밖 항목).

### 2.2 update 화면 — 자산마다 한 줄

`src/update-mode.ts` (`skillRefresh` 직후, 798행 부근):

- `report.catalogRemoved` = `logAtStart.assets` 중 `REMOVED_CATALOG_ASSETS` 에 있는 id(중복 제거, **`excluded` 여부와 무관** — 뺀 채 남은 것도 같은 줄로 말한다).
- `report.externalSkillsNotInCatalog` 에서 위 id 를 뺀다 — 한 자산에 두 줄이 나오지 않게.

`src/excluded-still-there.ts` `excludedStillThere()` 의 카탈로그 분기에서 `REMOVED_CATALOG_ASSETS` id 를 건너뛴다(한 줄 필터). 안 빼면 `--without product-skills` 로 뺐던 설치본에 "계속 쓰려면 `--with product-skills`" 를 권하는데 그 플래그는 이제 `Unknown asset id` 로 거절된다 — 화면이 틀린 명령을 말한다. install · update · list 세 화면이 이 함수를 같이 쓴다(`installer.ts:743` · `update-mode.ts:736` · `list.ts:110`).

`src/commands/install-render.ts` (1338행 블록 앞): `catalogRemoved` 의 id 마다 `assetRow("skip", …)` 한 줄. 문구는 구현자가 쓰되 **아래 사실을 빠짐없이** 담는다(기존 이 블록의 한국어 문체를 따른다):

| 항목 | skill 방식(revealjs · web-video-presentation) | plugin 방식(나머지 3) |
|---|---|---|
| 무엇 | `<id>` · 카탈로그에서 빠졌다 / `<새 id>` 로 바뀌었다 | 같음 |
| 깐 것 | 그대로 남는다 · **update 가 더는 갱신하지 않는다** | 그대로 남는다(갱신은 Claude Code 플러그인 관리자 몫이라 "갱신 중단"은 말하지 않는다 — 하네스는 원래 플러그인을 갱신하지 않았다) |
| 새 것 받기(교체만) | `agent-harness install --with <새 id>` | 같음 |
| 새 것이 이 설치본에 안 닿을 때 | 대체 자산이 설치 기록의 CLI(`installedClis(log)`)에 닿지 않으면(`assetReachesCli`) "`<새 id>` 는 Claude Code 전용이라 이 설치본의 CLI 에는 깔리지 않는다" 로 대신한다 — codex 전용 설치본에 web-video-presentation 이 있던 경우 | 해당 없음(옛 것도 Claude 전용이었다) |
| 옛 것 치우기 | `agent-harness uninstall --only <id>` | 같음 |

## 3. ⓑ 교체 2종 — 옛 id 기록이 있는 설치본의 이행

**결정: 자동 이행하지 않는다. 옛 것은 남고, 새 것은 설치자가 고른다. 화면이 두 명령을 준다(§2.2).**

| 대안 | 판정 |
|---|---|
| update 가 새 자산을 자동 설치 | 기각 — update 는 기록에 있는 것만 다룬다(ADR-078 "대상 선정은 기록에서만 … 고른 적 없는 자산이 update 로 새로 깔린다"). claude-security 는 `git push` 에 훅을 걸고 스캔이 시간·토큰을 쓴다(조사 보고서 §3) — 묻지 않고 깔 것이 아니다 |
| update 가 옛 자산을 제거 | 기각 — §2 와 같은 이유(확인 없는 삭제) |
| **옛 id 를 유지하고 method 만 새 플러그인으로 바꾼다** | 기각 — `trailofbits-skills` 라는 이름으로 Anthropic 플러그인을 까는 거짓 이름이 되고, 기록의 `detail.pluginId` 는 옛 값이라 uninstall 이 새 것을 못 지운다 |
| **새 id 로 추가 + 옛 id 는 `REMOVED_CATALOG_ASSETS` 에 `replacedBy`** | **채택** |

### 3.2 hyperframes 를 plugin 으로 까는 이유 (설계자 결정)

조사 보고서가 남긴 갈림("skill 이면 4-CLI, plugin 이면 Claude 전용")을 상류 실측으로 가른다:

- 상류 `skills/hyperframes/references/skill-lifecycle.md`: 단독 스킬 설치는 "core set eagerly, workflow skills lazily" — `--skill hyperframes` 하나만 깔면 core(`hyperframes-core` 등 9종)조차 없고, 진입 스킬이 작업 중에 `npx hyperframes skills update <workflow>` 로 **런타임에 나머지를 받아 깐다.** 그 쓰기는 하네스 기록 밖이고 배치 방식은 상류 CLI 가 정한다 — ADR-078 이 실측한 해악(고른 적 없는 `.agents/` 트리 · 심링크 슬롯)이 같은 형태로 다시 열린다.
- 상류 `.claude-plugin/marketplace.json`: plugin 이 "Recommended: all published HyperFrames skills in one versioned bundle". plugin 모드에서는 진입 스킬이 "Do not run `npx skills add`" 로 런타임 설치를 멈춘다(`references/plugin-installation.md`).
- claude-security 와 같은 마켓플레이스라 `marketplace add` 가 한 번이다.

**정정(B3)**: 위 첫 항목은 `--skill hyperframes` 하나만 까는 경우다. skill 방식에는 **전량 설치**도 있다 — `method: { kind: "skill", source: "heygen-com/hyperframes" }`(`--skill` 없음)이면 `buildSkillArgs` 가 `--yes` 비대화형으로 상류 21종을 4-CLI 에 `--copy` 로 깔고 #573 파일 기록 · `uninstall --only` 도 받는다(전례 jakubkrehel-skills). 그 경로의 진짜 대가는 설치 뒤다: standalone 모드의 상류 라우터가 워크플로 진입 전 `npx hyperframes skills update <workflow>` 를, 스캐폴드 때 `npx hyperframes init` 을 돌리고 bare `skills update` 는 미게시 스킬을 prune 한다 — 상류 CLI 가 런타임에 같은 스킬 디렉터리를 다시 쓰고 지워 하네스 기록 sha 와 어긋나고, update 의 refresh 와 두 주체가 한 자리를 쓴다. **결정(메인 세션, 2026-10-11): plugin 경로로 확정** — 이 이유를 ADR-104 Alternatives 에 적었다.

**대가**: Codex·OpenCode·Antigravity 만 쓰는 새 설치자에게는 영상형 발표 자산이 없어진다(web-video-presentation 은 4-CLI 였다). 위저드는 이미 "outside reach — not installed" 로 표시한다(`src/interactive.ts:796-807`). 기존 설치본의 web-video-presentation 파일은 남는다. → 사용자 확인 항목 §13-1.

### 3.3 마켓플레이스 선택 — `claude-plugins-official` vs `heygen-com/hyperframes`

`hyperframes@hyperframes`(HeyGen 자체 마켓플레이스, 최신 추종)도 있다. 공식 마켓플레이스 쪽을 고른다: 사용자 지시 문구("공식 마켓플레이스에도 등재") · tier `official` 정의와 맞음 · Anthropic 이 sha 를 고정해 검토된 판만 받는다. 대가는 상류 개선이 마켓플레이스 sha 갱신까지 늦게 온다는 것.

## 4. ⓒ uzys 4종 기본 체크 — 조건 종류와 불변식

### 4.1 조건 종류

4종 모두 `condition: { kind: "has-dev-track" }` (현재 전부 `opt-in`: `src/external-assets.ts:223` · `:336` · `:348` · `:416`).

- "기본 체크"의 실체: 이 코드베이스에는 **"위저드 미리 체크만 하고 비대화형에서는 안 까는" 범주가 없다.** 위저드 미리 체크(`recommendedExternalAssets`, `src/preset-recommend.ts:19-31`)와 비대화형 기본 설치(`shouldInstallAsset`)가 같은 `condition` 에서 나온다. 새 범주를 만드는 대신 기존 조건을 쓴다(가정 §11-1).
- `has-dev-track` = `DEV_TRACKS`(base · csr-* · ssr-* · data · tooling · full), executive · project-management · growth-marketing 제외(`src/external-assets.ts:149-169`). "개발 트랙"과 정확히 같다.
- tier 는 4종 모두 `official` 이라 experimental 게이트(`shouldInstallAsset` `:1153`)에 걸리지 않는다.

### 4.2 불변식 충돌 — 없음, 그리고 `DEV_METHOD_SKILL_IDS` 에 넣지 않는다

### 4.3 external-model-consult — 설치를 실패시키지 않는다

- 설치는 `templates/skills/external-model-consult/` 디렉터리 복사뿐이다. 설치 단계에 `agy`·`codex` 존재·로그인 검사가 없다(grep `src/`: provider CLI 사전 검사 0건).
- CLI 가 없거나 로그인이 만료되면 **실행 시점에** 래퍼가 exit 3(바이너리 없음)·인증 오류를 내고, 스킬 본문이 "설치·로그인은 사용자 몫 — 알리고 멈춘다"를 지시한다(`SKILL.md:50-71`, `scripts/codex-ask.sh:16` · `gemini-ask.sh:21`).
- ADR-034 §4 가 "외부 CLI 의존(agy/codex) pre-check 승격은 하지 않음 (First-Run Success 리스크)"으로 막았던 것이 정확히 이 기본 체크다. 첫 설치 성공(First-Run Success)은 위 이유로 영향이 없다. 남는 비용은 **스킬 descriptor 가 매 세션 상주**하고, provider CLI 가 없는 설치자에게는 발화해도 "설치하라"는 안내만 돌아온다는 것 — ADR 에 그대로 적는다.

### 4.4 ci-scaffold — 기본이 되면 무엇이 달라지나

- 새 설치(개발 트랙)마다 `.github/workflows/` 에 트랙별 템플릿(node `ci.yml` · python `ci-python.yml` · UI 트랙 `e2e.yml`, `src/ci-scaffold.ts:43-61`)이 **없을 때만** 생긴다. 기존 파일은 덮어쓰지 않는다. 기록은 `rootFiles`(created), uninstall 은 지우지 않고 "left for you" 로 안내한다 — 루트 CLAUDE.md 원칙의 **advisory(넘겨준 산출물)** 분류 그대로다(ADR-097 L72, `one-principle-design-2026-09-27.md` 결정 5·7). 원칙 위반 없음.
- 템플릿 트리거는 태그 `v*` + `workflow_dispatch` 뿐이다(`templates/github-workflows/ci-node.yml:13-16`). 설치자가 파일을 커밋해야 동작한다.
- **ADR-037 §3ⓐ 를 뒤집는다** — "opt-in 전용(트랙 조건 설치 없음 — 무인지로 사용자 CI 디렉토리에 쓰지 않는다)"이 그 ADR 의 안전 계약이었고, "트랙 조건(has-dev-track) 기본 설치"는 Alternatives 에서 기각됐었다. 사용자 결정(2026-10-11)으로 개정한다. §3ⓑ(덮어쓰기 금지)·ⓒ(uninstall 미접촉)은 그대로.
- `update` 는 ci-scaffold 를 돌리지 않는다(`src/update-mode.ts` 에 호출 없음). 기존 설치본은 `update` 만으로는 `.github/` 가 안 생기고, 다시 `install`(위저드 add 포함)할 때 생긴다.
- `base` 트랙(스택 없음)은 node 템플릿 `ci.yml` 을 받는다(파이썬 트랙이 없을 때의 폴백, `ci-scaffold.ts:47-50`) — 가정 §11-3.

### 4.5 기존 설치본에 대한 파급 (#480 의 기존 규칙)

`update` 의 `installNewSkillDirs`(`src/update-mode.ts:1341-1386`)는 "이 트랙 구성이 기본으로 설치했을 번들 스킬 중 디스크에 없는 것"을 깐다. 조건이 has-dev-track 이 되면 **설치 기록에 개발 트랙이 있는 모든 설치본**이 update 한 번으로 세 스킬을 받는다(화면 "added by this release") — Claude 자리는 `installNewSkillDirs`(#480 ①), Codex·OpenCode·Antigravity 공유 자리 `.agents/skills/<id>/` 는 `agents-skill-targets.ts`(#530 S3). 둘 다 누적 `excluded` 를 지킨다(ADR-099 R3). **정정(B2)**: 이전 판은 "Claude 를 안 쓰는 설치본은 받지 않는다"고 적었는데 틀렸다 — `installNewSkillDirs` 의 이른 반환은 `.claude/` 자리만의 일이다(🧪 `tests/update-dev-default-skills.test.ts` 가 codex 단독도 잰다).

또 `model-orchestration` 은 `CONTINUOUS_SKILLS`(`src/external-assets.ts:1053-1066`) — 깔리면 프로젝트 맥락 블록에 상시 안내 한 줄이 들어간다(ADR-085). 상주 비용이 개발 트랙 전부에서 는다 → §6 의 cost baseline 갱신 대상.

## 5. 위저드 확인 화면 수정 (삭제 자산이 기록에 있는 설치본)

§1 표 마지막 행: 기록에 삭제 자산이 있는 설치자가 위저드에서 무엇이든 바꾸면 확인 화면이 그 id 를 "selected"·"+User added" 로 적는다(설치는 안 된다). 삭제 자산이 5종 늘어 이 화면에 닿는 설치자가 늘어나므로 함께 고친다.

- **수정**: `computeUserOverride`(`src/interactive.ts:766`)에서 `forceInclude` 를 **카탈로그 id 로 거른다**(`EXTERNAL_ASSETS` 에 있는 id 만). 
- `installedTargetState` · `classifyUpdateIntent` 는 바꾸지 않는다 — 숨은 id 가 `confirmed.assetIds` 에 남아야 `classifyUpdateIntent`(`src/interactive.ts:248`) 의 "기록된 project 자산의 체크를 풀었다 → add" 가 오발하지 않는다(거르면 아무것도 안 바꾼 Update 가 전부 add 로 바뀐다).
- 기록의 `assets` 는 install 이 누적하므로(ADR-097 Q2 · ADR-099 "assets 는 그대로 누적") add 로 가도 삭제 자산 기록은 남고, §2.2 안내·uninstall 은 계속 동작한다.
- 같은 결함은 ADR-093 퇴역 11종에도 있다(기존). 이 수정이 그쪽도 함께 고친다.

## 7. ⓔ Docker 확인 — 정확한 명령

### 7.0 왜 `bash test/docker/run.sh <시나리오>` 로는 플러그인 id 를 확인할 수 없나

기본 이미지(`test/docker/Dockerfile`, node:20-slim)는 `claude` 를 **mock** 으로 바꿔 둔다(`test/docker/mocks/claude`) — `plugin install <아무 id>` 에 캐시 디렉터리를 만들고 exit 0 을 낸다. 실 CLI 이미지(`Dockerfile.realcli`)도 claude 는 같은 mock 이다(`:22-26`). 그래서 **기존 시나리오는 잘못된 pluginId 에도 초록**이다. 실 claude 로 카탈로그를 까는 기존 장치는 `.github/workflows/catalog-verify.yml`(월 1회 cron + dispatch, `scripts/verify-catalog.mjs` — 주석이 가리키는 `test/docker/scenario-catalog-verify.sh` 는 저장소에 없다).

**정정(B4)**: `node:22-bookworm` 에는 jq 가 없다(`command -v jq` → 없음). 아래 스크립트는 머리에 `apt-get update -qq && apt-get install -y -qq jq >/dev/null && command -v jq` 가 필요하다 — 없으면 D2 는 127 로 멈추고 D3 의 `diff <(jq …) <(jq …)` 는 빈 스트림 둘을 비교해 **거짓 초록**을 낸다. 그래서 D3 diff 앞에 대조군 `jq -e '.plugins | length > 0' /tmp/plugins-before.json`(실패면 무효), D1 에 일부러 틀린 id 의 `plugin install`(실패해야 한다)을 넣는다. 구현 레인은 jq · 실 claude 를 미리 넣은 **레인 전용 이미지**(`uzys-lane-726-skills:local`)로 돌렸다.

따라서 교체본 확인은 **실 claude CLI 를 까는 일회용 컨테이너**로 한다. 저장소 변경 없이, 호스트 마운트 없이(타르볼은 stdin 으로) 돈다. 호스트에서 실 CLI 실행은 훅이 막으므로 반드시 컨테이너다.

## 10. ⓗ 머지 전 독립 리뷰 문턱 — **위**

`.claude/rules/test-policy.md` §머지 전 독립 리뷰 문턱 = "핵심 사용자 기능 · 되돌리기 어려운 것 · … 설치자 디스크·공유 상태를 되돌리기 어렵게 바꾸는 변경 · 갈리면 독립 리뷰 쪽으로".

- **핵심 사용자 기능**: 개발 트랙 전부의 기본 설치 집합이 바뀐다(4종 추가). 설치자가 아무것도 안 골라도 받는 것이 달라진다.
- **설치자 디스크(하네스 폴더 밖)**: 새 설치가 설치자 저장소의 `.github/workflows/` 에 파일을 쓴다 — 지금까지는 명시 opt-in 에서만 하던 일이다(ADR-037 이 바로 이 이유로 기각했던 형태). 커밋되면 설치자의 GitHub Actions 에서 돈다.
- **기존 설치본의 update 경로**: update 가 세 스킬을 새로 깔고, 새 안내 줄을 낸다(삭제·덮어쓰기는 없음).
- 반대 근거: 삭제·덮어쓰기 경로는 하나도 추가하지 않는다. 그래도 위 둘은 "틀려도 설치자가 잃는 것이 없다"가 아니다.

→ **문턱 위. 독립 리뷰 필수.** 리뷰어에게 넘길 것: 이 설계서 · 사용자 결정 원문 · 최종 diff · `npm run ci` 결과 · §7 D1–D3 컨테이너 출력 원문 · §8 음성 대조 기록.

**Change Request 분류**: `docs/SPEC.md` Non-Goals 에 "기본 설치 항목 재정의 · 스킬 통합 — G 사이클(이슈 #262)" 이 있다. 현행 SPEC(문서 체계 F 사이클)의 경계에 닿으므로 change-management 상 **Major** 이고, 인간 결정은 이미 있다(2026-10-11). SPEC Change Log 에 한 줄(날짜 · Major · "기본 설치 항목 재정의 — v26.167.0 사용자 결정, ADR-105(가)") 을 남긴다 — 이 사이클이 SPEC 범위 밖에서 진행된다는 사실이 기록에 남게.

## 11. 가정 (모호해서 기본값으로 정한 것)

1. **"기본 체크" = `has-dev-track` 조건**(위저드 미리 체크 + 비대화형 개발 트랙 기본 설치). "위저드에서만 미리 체크" 범주는 없고 새로 만들지 않는다(§4.1).
2. **기존 설치본도 update 로 세 스킬을 받는다** — #480 ① 의 기존 규칙(릴리즈가 새로 기본에 넣은 번들 스킬은 update 가 깐다)을 그대로 따른다. 사용자가 "새 설치에만"을 원했다면 #480 규칙에 예외를 더해야 하는데, 루트 CLAUDE.md 가 경우별 예외를 금한다.
3. **ci-scaffold 는 `base` 트랙에도 기본**(node 템플릿 폴백). "개발 트랙"의 정의(`DEV_TRACKS`)가 base 를 포함하고, 템플릿은 FILL 마커가 있는 채우기형이다.
4. hyperframes 는 **plugin · `claude-plugins-official`**(§3.2·§3.3).
5. 새 두 자산의 tier 는 **official**(Anthropic 마켓플레이스 = 정의상 official). `trust-tier-drift` 가 official 을 건너뛰므로 별 수 감시 대상이 아니다.
6. 이행 문단(옛 id → 새 id)은 **CHANGELOG** 에 둔다. GUIDE_DOCS 에 옛 id 를 쓰면 `doc-asset-ref-drift` 가 문다.
7. 삭제 자산 안내 줄은 **update 화면에만** 낸다(기존 `notInCatalog` 와 같은 자리). install 재실행 화면에는 내지 않는다.
8. `RETIRED_SKILL_IDS` · `RENAMED_SKILL_IDS` 는 손대지 않는다(번들 스킬 전용으로 남김).
