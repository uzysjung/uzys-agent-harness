## BLOCKER (구현 전에 설계에 넣어야 한다)

### B1. 함께 쓰는 파일이 `externalFiles` 에 있을 때 두 경로(strip · judge(remove) harness)에 동시에 들고, 지금 필터는 둘 다에서 뺀다 — 설치자 표가 든 `.codex/config.toml` 이 통째로 사라지거나 아무 경로도 타지 않는다

**근거**
- 설계 §2.3 ⓑ: 후보 = `policyFiles ∪ skillFiles ∪ externalFiles(.uzys-agent-harness 제외)` 에 `judge(remove)` — `kind` 를 가르지 않는다. 하네스가 **만든** `.codex/config.toml` · `opencode.json` · 절 모델 `AGENTS.md` 는 전부 `externalFiles` 에 있다(`shared-write.ts:220-233` `harnessMade` → `writer.write` → `owned-write.ts` `written` → `externalFiles`; `codex/transform.ts:213` `writeShared`). 그 경로로 가면 `judge({kind:"harness"})` 는 sha 가 다를 때 `backup+remove`(`judge.ts` `harnessRemove`) — 설치자가 `[mcp_servers.mine]` 을 더한 `config.toml` 이 **라이브에서 통째로 빠진다**. ADR-097 D4("세 동작 모두 하네스 몫만 뺀다") 위반이고, 원 설계 §2 행 19(`S; created 면 X`) · 행 24(`고쳤으면 통째로 남김 → 몫 strip`) 와도 다르다.
- 설계 §2.3 ⓐ: `stripCliShared` 에 두 파일을 더한다 — 그런데 `uninstall.ts:1394` `paths.filter((path) => !harnessMade.has(path))` 가 `externalFiles` 에 있는 파일을 strip 에서 뺀다. §11 ⑭ 는 그 필터를 **유지**하라 하고(시나리오가 살려면) §11 ⑮ 는 **걸지 말라** 한다 — 설계 안에서 서로 반대다.
- `kindOf(log, path)`(`recorded.ts`)는 어댑터 표(`adapters/shared-files.ts` 7개)에 있는 경로를 `shared` 로 낸다 — 가르는 재료는 이미 있다.
- 하네스가 만든 `.codex/config.toml` 은 `rootFiles.change = created` 가 **아니다**(`writeShared` 의 `ownCreated` 기본 true → writer 경로). 그래서 설계 §2.3 #5 의 "`created` 면 파일째" 조건만으로는 몫만 남은 하네스 파일이 걷힌 뒤 빈 껍데기로 남는다(`stripShared:489` `removeIfEmpty`).

**실패 시나리오**: claude+codex 설치 → 설치자가 `.codex/config.toml` 에 `[mcp_servers.mine]` 추가 → 전량 `uninstall --yes`. ⓑ 경로면 `config.toml.backup-<ts>` 만 남고 Codex 가 설치자 서버를 잃는다(§2.4 테스트 3 red). 필터를 유지하고 ⓑ 에서 `kindOf===shared` 를 빼면 **아무 경로도 안 타** 하네스 구간이 그대로 남는다(§2.4 테스트 3 역시 red).

**설계에 넣을 문장**(§2.3 ⓐ·ⓑ 와 #5 행을 대체)
> ⓑ 의 후보에서 `kindOf(log, path) === "shared"` 인 경로는 **뺀다** — 함께 쓰는 파일은 ⓐ 에서만 다룬다(`AGENTS.md` · `opencode.json` · `.codex/config.toml` · `.claude/settings.json` · `.mcp.json` · `.gitignore` · 루트 `CLAUDE.md`). ⓐ 의 대상 = `CLI_SHARED ∪ ROOT_SHARED ∪ {.claude/settings.json, .codex/config.toml}`. `stripCliShared` 의 `harnessMade` 필터는 "뺀다" 에서 "하네스가 만든 파일의 규칙" 으로 바꾼다: 그 파일이 `externalFiles` 에 있고 **디스크 sha 가 기록 그대로**면 파일째 `remove`(지금 `removeExternalFiles` 와 같다 — 하네스 것뿐이다) · **다르면** `strip-portion` 으로 기록된 몫만 걷고 나머지는 남긴다(설치자 표 · 설치자 키 · seed 키) — `backup+remove` 는 하지 않는다. `removeIfEmpty` 는 `rootFiles created` **또는** `externalFiles` 에 있는 파일에 건다. 절 모델 `AGENTS.md`(sha 같음 → `stripHarnessFromAgentsMd`, 다름 → kept #516) 는 지금 분기 그대로 ⓐ 안에 둔다. 테스트: "설치자 표 하나 더한 하네스 제작 `config.toml` 의 전량 uninstall 뒤 하네스 구간 0 · 설치자 표 라이브" + "안 고친 하네스 제작 `config.toml` 은 파일째 사라진다"(`scenario-uninstall-cli.sh:92` 가 그 뒤를 본다). 음성 대조: ⓑ 의 `kindOf` 필터를 빼면 첫 테스트가 `backup-*` 생성으로 red.

### B3. 옛 로그(`records: "writer"` 없음)에서 `recorded()` 는 `.claude/` 하네스 대상 경로를 기록에 없어도 `no-sha` 로 낸다 — #761 의 첫 접촉이 `displaced` 가 아니라 "no checksum — saved a copy once" 가 되고 uninstall 이 되돌리지 않는다

**근거**
- `recorded.ts` 마지막 분기: `if (writer) return none; … if (ownedByLog && isTarget(path) && (!claudePath || legacyOwned())) return no-sha`. 옛 로그 + claude 설치 + 경로가 번들 스킬 · 기록 트랙 룰이면 **`skillFiles`/`policyFiles` 에 그 경로가 없어도** `no-sha` 다. `tests/recorded.test.ts:121-123` 이 그 동작을 단언한다(의도된 동작).
- 그래서 설계 §3.1 장면(손수 둔 `.claude/skills/multi-model-debate/SKILL.md`) 이 v26.161 이하 로그 위에서 `update` 되면 `judge` 는 `no-sha · 다르다 → backup+overwrite · record "sha"`(`judge.ts` `harnessWrite`) — **`displaced` 가 적히지 않고**, 화면은 `LINES.noChecksum`, uninstall 은 되돌릴 근거가 없다. 설계 §3.1 TOBE 표 · §2.3 #3("v26.125 이전 설치본") · §3.3 ⓐ① 단언(`rootFiles displaced 2건`)은 writer 로그에서만 참이다. `pretendOlderRelease`(`update-dev-default-skills.test.ts:46`) 는 현 판이 쓴 로그(writer)를 그대로 쓰므로 이 구멍을 보지 못한다.
- 바이트 손실은 없다(백업은 남는다). 손실은 "제자리로 되돌린다" 는 약속이 옛 로그 설치자에게는 성립하지 않는 것이고, #747 이 보여 주듯 옛 로그 설치본은 실재한다.

**설계에 넣을 문장**(§3.2 ⓐ 앞 또는 §10 가정에 — 둘 중 하나를 고른다)
> (ⓐ 좁히기 — 권장) `recorded()` 의 로그 수준 `no-sha` 는 **그 필드가 아예 없는 옛 로그**에만 둔다: `.claude/skills/` 경로는 `log.skillFiles === undefined` 일 때만, 그 밖 `.claude/` 정책 경로는 `log.policyFiles === undefined` 일 때만 `no-sha`; 필드가 있는데 경로가 없으면 `none`(체크섬 시대의 스캔은 템플릿에 있는 파일을 전부 적었으므로 빠진 경로 = 하네스가 쓴 적 없는 자리). `.claude/.installed-tracks` 처럼 어느 필드에도 적힌 적 없는 하네스 파일은 호출부가 `isTarget` 으로 넘겨 지금처럼 `no-sha`. `tests/recorded.test.ts:121` 을 "필드 없음" 픽스처로 바꾸고 "필드 있음 · 경로 없음 → none" 1건을 더한다. 음성 대조: 좁히기를 되돌리면 §3.3 ⓐ① 의 옛 로그 변형이 red.
> (ⓑ 한계로 적기) "옛 로그(v26.161 이하, 그 뒤 update 한 번도 안 한 설치본)에서는 첫 접촉을 `no-sha` 로 읽어 1회 백업하고 하네스 것으로 삼는다(ADR-097 D3 마지막 문장) — displaced 되돌리기는 writer 로그부터" 를 §3.1 표에 행으로 넣고, 화면 `noChecksum` 줄에 "put back on uninstall is not possible for this one — your copy is at …" 를 붙인다. §3.3 ⓐ 에 옛 로그 케이스(기대 = 백업 1 · displaced 0)를 더한다.

### B4. `.claude/skills/<id>` 가 이 프로젝트의 `.agents/skills/<id>` 로의 링크인 자리(claude-slot · #524)에서 §2.3 #10 "안 링크는 따라가 실체에 적용" 을 그대로 하면 `uninstall --cli claude` 가 **남는 CLI(codex · opencode) 의 스킬 본문**을 지운다

**근거**
- 설치자가 설치 뒤 `.claude/skills/<id>` 를 `.agents/skills/<id>` 링크로 바꾸는 운용이 공식 지원이다(`installer.ts:1148-1153` `linksToProjectSharedSkill` → `linkedSkills` · `linked-skill-bodies.ts` · `tests/claude-slot.test.ts:144`). 그 설치본의 `skillFiles` 에는 첫 설치가 적은 `<id>/SKILL.md` 등이 **그대로 남아 있다**(링크로 바꾼 것은 설치자고, `refreshSkillBaseline` 이 돌기 전까지 기록은 그대로다; `listFilesRecursive` 는 링크 dirent 를 디렉터리로 보지 않아 다시 적지도 지우지도 않는다).
- 설계 §2.3 #10: "프로젝트 안을 가리키는 링크는 **따라가** 실체에 1·2·5 를 적용한다". `uninstall --cli claude` 가 `.claude/skills/<id>/SKILL.md` 를 `judge(remove)` 하면 `rm(join(projectDir, ".claude/skills/<id>/SKILL.md"))` 가 링크를 통과해 `.agents/skills/<id>/SKILL.md`(포팅판 — codex 가 읽는 본문) 을 지운다. sha 는 다르니(`skillFiles` 의 Claude 판 sha ≠ 포팅판) `backup+remove` — codex 는 스킬을 잃고 백업만 남는다. 지금은 `.claude/` 를 폴더째 옮기므로 링크만 옮겨 가고 본문은 남는다 — 이번 변경이 새로 여는 손실 경로다.
- 전량 uninstall 에서는 `.agents/` 본문이 `externalFiles` 로 어차피 회수되므로 결과는 같지만, 한 파일을 두 기록이 두 번 판정한다(두 번째는 `disk null → forget`) — 무해하나 화면 수가 어긋날 수 있다.

**설계에 넣을 문장**(§2.3 #10 대체 · #9 보강)
> 회수 경로의 실체 판정은 **기록 필드의 자리**로 한다: `.claude/skills/<id>` 슬롯이 디렉터리가 아니면(링크 · 파일 — `occupiedByNonDirectory`, `syncSkills:2217` 과 같은 술어) 그 아래 `skillFiles` 기록은 **건너뛰고 `forget`** 한다 — 그 본문은 `.agents/` 몫이고 `externalFiles` 가 소유를 말한다(설치자가 건 링크는 남긴다, ADR-098 과 같은 쪽). 파일 링크를 따라가 실체를 회수하는 것은 **그 실체가 다른 기록 필드의 자리가 아닐 때**(`.codex/config.toml` → 프로젝트 안 실파일, #630)만이다. `uninstall --cli claude` 테스트: claude+codex 설치 → 슬롯을 링크로 → `--cli claude` → `.agents/skills/<id>/SKILL.md` 바이트 그대로 · 링크는 남거나 사라져도 본문 무변경 · codex 기록 그대로. 음성 대조: 슬롯 링크 건너뛰기를 빼면 본문 단언이 red.

### B5. PR-E 를 "CI 만" 으로 둔 표기는 ADR-094 의 가름 규칙과 어긋난다 — 설계 스스로 갈린다고 적은 자리(§11 ⑧)는 규칙상 독립 리뷰다

**근거**
- `.claude/rules/test-policy.md` §머지 전 독립 리뷰 문턱: "설치자 디스크·공유 상태를 되돌리기 어렵게 바꾸는 변경(update·uninstall 의 삭제·덮어쓰기 경로 …)" + "**갈리면 독립 리뷰 쪽으로**". PR-E 는 update 가 **설치자가 고친**(sha 다름) `opencode.json` 의 키를 백업 없이 갈아 끼우고(`json-keys.upsert` 는 백업이 없다) 은퇴 키(`mcp.github`)를 지운다 — 공유 파일의 덮어쓰기·삭제 경로다. 설계 §11 ⑧ 이 "문장만 보면 문턱 위" 라고 인정하면서 CI 만으로 둔 것은 규칙의 tie-break 와 반대다.
- 선례 `.mcp.json`(ADR-106 · PR #750)은 **독립 리뷰를 거쳤다** — 선례가 말하는 것은 "같은 종류의 변경은 리뷰했다" 이지 "두 번째는 리뷰 생략" 이 아니다. `knownServerValues` 의 값 sha 대조가 틀리면(예: `renderOpencodeMcp` 형식 변환이 한 필드를 떨어뜨려 설치자 값과 우연히 같아질 때) 설치자 값이 백업 없이 바뀐다 — 변이 대조 1건(§4.3 "legacySeed 전달을 빼면 1·4 red")은 **빠뜨림**만 잡고 **과잉 매칭**은 잡지 않는다.

**설계에 넣을 문장**(§8 PR-E 행 · §11 ⑧)
> PR-E — **문턱 위**(update 의 공유 파일 덮어쓰기 경로 · 백업 없는 키 교체). 독립 리뷰의 변이 대조에 "설치자가 `mcp.chrome-devtools` 의 `environment` 만 더한 파일에서 씨가 그 키를 **잡지 않는다**(값 sha 가 다르다)" 를 넣는다(과잉 매칭 음성 대조). §11 ⑧ 은 삭제.

## 2. 리드가 특별히 물은 둘

### 2-1. B1 — "하네스가 만든 함께 쓰는 파일이 sha 그대로면 파일째 지우기" 가 설치자 손실을 내는가 → **내지 않는다**

`writeShared`(`shared-write.ts:184-246`)의 두 갈래가 근거다.
- `harnessMade = baseline.get(path) === hashContent(onDisk)`(`:186`)면 `existing = null`(`:187`) → `json-keys` 는 seed 에서, `toml-region` 은 빈 것에서 **새로 조립**해(`:192-199`) `writer.write` 로 쓰고 **그 바이트의 sha** 를 `externalFiles` 에 적는다(`:242` → `owned-write.ts:206`). 즉 기록 sha 와 디스크가 같다 = 파일 내용이 "하네스 렌더 + seed" 뿐이다. 귀납적으로 설치자 바이트가 들어갈 길이 없다.
