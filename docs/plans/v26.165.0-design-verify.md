## 1. BLOCKER

### BLOCKER-1 — 은퇴가 옛 로그의 antigravity 유도 근거를 지운다 (§B-2 넷째 항 · §6-6)

**설계의 전제**: "유도가 걸린 설치본은 그 update 가 `clis` 를 쓰므로(ADR-096 D3 '다음에 로그를 쓸 때 실린다') 앵커 기록이 빠진 뒤에도 antigravity 가 집합에 남는다."

**코드**: 그 전제는 틀렸다.
- `spec.clis` 를 쓰는 곳은 둘뿐이다 — install 의 `buildInstallLog`(`src/install-log.ts:445-485`, `clis = sortClis([...installedClis(previous), ...spec.cli])`) 와 `uninstall --cli` 의 `settleCliLog`(`src/commands/uninstall.ts:1033-1050`).
- update 는 `buildInstallLog` 를 부르지 않는다(`src/update-mode.ts` 에 호출 0건). update 의 외부 CLI 기록 갱신은 `next: InstallLog = { ...log }` 에 `externalFiles` · `portions` · `rootFiles` 만 바꿔 `writeInstallLog` 한다(`src/update-mode.ts:1783-1800`). `spec` 은 복사된 그대로다 — 옛 로그에 `spec.clis` 가 없으면 **없는 채로** 다시 쓴다.
- `installedClis(log)` 는 `spec.clis` 가 없을 때만 `externalFiles ∋ .agents/rules/uzys-harness.md` 로 antigravity 를 유도한다(`src/install-log.ts:333-345`). ADR-096 D3 의 "다음에 로그를 다시 쓸 때" 는 `buildInstallLog` 를 뜻하고(ADR 본문 L56 · `install-log.ts:325`), install 에서만 일어난다.

**설치자에게 생기는 일**: v26.160.1 이하에서 antigravity 를 깔고 그 뒤 **install 없이 update 만** 해 온 프로젝트(`spec.clis` 부재)가 v26.165.0 으로 update 하면 ① 이 update 는 유도로 antigravity 를 알아보고 AGENTS.md 를 만들고 앵커를 은퇴시킨다(여기까지 설계대로) ② 기록에서 앵커 경로가 빠진다(`forget`) ③ 그 다음 실행부터 `installedClis` = antigravity 없음 → `runCliTransforms` 의 `cli` 에서 빠져 `.agents/rules/<룰>.md` 가 더는 갱신되지 않고, AGENTS.md 집합에서도 빠져 제목·절이 codex/opencode 판으로 돌아가며(antigravity 단독이면 집합이 비어 변환 자체가 안 돈다), `uninstall --cli antigravity` 는 "깔려 있지 않다" 고 거절하고, `reclaimOutOfTrack` 도 건너뛴다(`out-of-track.ts:75`). 화면은 아무 말도 하지 않는다. 설치자 파일 손실은 아니지만 "깐 것이 각 CLI 에서 그대로 동작한다" 는 이 릴리즈의 목표가 그 설치본에서 조용히 뒤집힌다.

**넣을 문장(§B-3 3단계 교체)**:
> 3. **기록**: 은퇴 단계는 `externalFiles` 에서 앵커 경로를 빼기 **전에** `installedClis(log)` 를 계산해 두고, 같은 기록 쓰기에서 `spec.clis` 를 그 값으로 **명시로 적는다**(없던 필드면 만든다 — `buildInstallLog` 가 install 에서 하는 1회 이행을 이 update 가 대신한다, ADR-096 D3 의 "다음에 로그를 쓸 때" 가 바로 이 쓰기다). update 경로의 다른 기록 쓰기(`src/update-mode.ts:1783-1800`)는 `spec` 을 건드리지 않으므로 이 한 자리가 유일한 이행점이다. B-T4 · B-T5 의 픽스처는 **`spec.clis` 가 없는 옛 로그 모양**으로 만들고, update 뒤 기록에 `spec.clis ∋ antigravity` 를 단언한다 — 지금 설계의 B-T4 단언 "`clis` 에 antigravity" 는 `installedClis()` 반환값이 아니라 **기록 필드 자체**를 읽어야 이 결함을 문다.

### BLOCKER-2 — "손대지 않은 스캐폴드" 판정이 바뀐 문구와 마커 없는 안내 절을 설치자 글로 읽는다 (§B-3 1단계 · §B-3 FILL 문구)

**설계의 전제**: 옛 앵커의 `## Project Context` 본문에서 `dropHarnessQuoteBlocks` 로 배너를 떼고 `isPristineScaffold(body, …)` 면 옮길 것이 없다. 같은 절에서 `FILL_SPECS["installed-assets"].prompt` 문구를 바꾼다.

**코드**:
- `isPristineScaffold`(`src/anchor-seed.ts:86-89`)와 `stripHarnessFromAgentsMd`(`src/agents-md-merge.ts:402-405`)는 디스크 절 본문을 **지금 코드의** `renderFillScaffold(surface)` 출력과 `compact()`(빈 줄·끝 공백만 정규화) 뒤 **바이트 비교**한다. `renderFillScaffold` 는 `<!-- FILL:<id> — <prompt> -->` 주석 줄을 그대로 담는다(`src/project-claude-merge.ts:211-217`). 프롬프트 한 글자가 바뀌면 옛 판으로 깐 **모든** 안 채운 스캐폴드가 "채웠다" 로 판정된다. 프롬프트 문구가 마지막으로 바뀐 커밋은 `7474d5a`(#259) 이고 이 비교기(#516 · #528)는 그 뒤에 들어왔다 — 즉 **비교기가 생긴 뒤 프롬프트가 바뀌는 첫 사례**다.
- 옛 Antigravity 앵커는 `withContinuousSkillsNote(renderFillScaffold("antigravity-rule"), skillIds)` 로 렌더되고 마커를 전부 걷어 썼다(`src/antigravity/transform.ts:183-196`) — `## Skills that apply continuously` 절이 **마커 없이** Project Context 본문에 남아 있다. `user-centered-explanation` 은 `DEV_METHOD_SKILL_IDS`(`src/external-assets.ts:1003`) 라 개발 트랙 기본 설치에 들어가므로 보통의 앵커에 이 절이 있다. AGENTS.md 쪽은 마커(`SKILLS_BLOCK`)로 감싸 `installerLines` 가 뺀다(`agents-md-merge.ts:340-344`); 마커 없는 옛 AGENTS.md 는 `refreshBlock(…, CONTINUOUS_SKILLS_HEADING)` 이 헤딩으로 알아본다(ADR-095 D4). 설계의 은퇴 절차에는 이 두 처리가 없다.

**설치자에게 생기는 일**:
- (은퇴) 앵커를 **안 채운** 설치자(대다수)의 update: 옛 FILL 주석(바뀌기 전 문구 — `.claude/rules/*.md …` 를 보라던 바로 그 줄, #631 둘째 축) + 마커 없는 상시 스킬 절이 "설치자 글" 로 판정되어 `AGENTS.md` 의 `## Project Context` 로 **옮겨 심어진다**. 새 렌더는 그 위에 다시 마커 달린 상시 스킬 절을 붙여 안내가 두 벌이 되고, 화면은 `your Project Context moved there` 라고 말한다(거짓). codex+antigravity 설치본(ⓒ 경로)에서는 "AGENTS.md already has its own Project Context" 로 판정될 수도 있다 — AGENTS.md 쪽 옛 스캐폴드도 "채운 것" 으로 읽히기 때문이다. B-T5 는 red.
- (은퇴 밖, 기존 설치본 전부) `uninstall` 마지막 CLI 가 나갈 때 안 채운 `AGENTS.md` 가 "채웠다" 로 읽혀 옛 스캐폴드만 든 파일이 남는다(`stripHarnessFromAgentsMd:405`). `install --cli codex` 를 옛 claude 설치본에 더하면 `seedAgentsMdProjectContext`(`anchor-seed.ts:106-113`) 가 안 채운 옛 루트 `CLAUDE.md` 의 **옛 스캐폴드**를 새 `AGENTS.md` 에 심는다 — 새 프롬프트 대신 옛 프롬프트가 퍼진다. 설치자 글의 손실은 아니지만 "옮겼다/채웠다" 판정이 전부 뒤집히고 #631 둘째 축의 수정 효과가 기존 설치본에 도달하지 않는다.

**넣을 문장(§B-3 1단계 앞에 추가 · §B-3 FILL 문구 항에 덧붙임)**:
> **스캐폴드 판정은 하네스가 쓴 줄을 뺀 뒤 한다.** `isPristineScaffold` · `stripHarnessFromAgentsMd` · 은퇴 1단계의 "채웠는가" 는 ① `<!-- FILL:… -->` 주석 줄(여러 줄이면 `-->` 까지)과 ② `## Skills that apply continuously` 헤딩부터 다음 `## ` 전까지의 절(마커 유무 무관 — ADR-095 D4 가 옛 AGENTS.md 에 쓰는 같은 단서 `CONTINUOUS_SKILLS_HEADING`)을 **양쪽(디스크 본문 · 기준 스캐폴드)에서 뗀 뒤** 비교한다. 그래야 FILL 문구를 고친 이 릴리즈가 기존 설치본의 안 채운 스캐폴드를 "채웠다" 로 읽지 않고, 옛 Antigravity 앵커의 마커 없는 안내 절이 설치자 글로 옮겨 가지 않는다. 설치자가 "Delete this comment when done" 대로 주석만 지우고 자리표시자를 남긴 상태도 같은 규칙으로 "안 채움" 이다(같은 뜻). 회귀: B-T5 픽스처는 **옛 FILL 문구 + 상시 스킬 절이 든** 26.164 앵커로 만들고 `AGENTS.md` Project Context 에 `Skills that apply continuously` 가 **한 번만** 있음을 단언한다. 기존 `tests/anchor-seed*` · `uninstall-cli-scope` 에 "옛 문구 스캐폴드(안 채움) → seed 없음 / 파일째 삭제" 대조군 1건.

### BLOCKER-3 — 은퇴 1단계의 호출 순서가 모순이고, 변환 뒤 절을 고쳐 쓰면 기록 sha 와 갈린다 (§B-3 머리 · 1단계 ⓐ/ⓑ · §C-2 seed · §B.6 순서)

**설계 본문**: "install · update 가 같은 함수를 CLI 변환 뒤에 부른다(`runCliTransforms` 안, `AGENTS.md` 변환 **뒤**)" ↔ 1단계 ⓐ "§C 변환이 이 실행에서 만들 때 **seed 로 넘긴다**" ↔ ⓑ "파일이 있고 Project Context 가 손대지 않은 스캐폴드다 → 그 절 본문을 옛 앵커의 설치자 줄로 **바꾼다**".

**코드**:
- AGENTS.md(절 모델)는 `writer.write(abs, mergeAgentsMd(...))`(`src/shared-write.ts:345-350`)로 쓰이고 owned-write 가 **그 바이트의 sha** 를 `ownership.files` 에 적어 `externalFiles` 기준선이 된다(`src/cli-transforms.ts:265-269`). 변환 **뒤**에 다른 함수가 같은 파일의 절을 고쳐 쓰면 디스크 ≠ 기록 sha 가 되고, 다음 update 의 `judge(write, sha, disk≠sha)` 는 "you edited it — saved as …backup" 으로 간다(`shared-write.ts:184-187` 의 `harnessMade` 도 false).
- `mergeAgentsMd`(`agents-md-merge.ts:258-299`)는 디스크의 `## Project Context` 를 **그대로 이어받는다** — "디스크가 손대지 않은 스캐폴드면 seed 로 바꾼다" 는 분기가 없다. ⓑ 를 하려면 이 함수(또는 `writeAgentsMd`)에 그 규칙을 **명시로** 더해야 한다.
- 변환 뒤에는 seed 를 넘길 수 없다 — `seedAgentsMdProjectContext` 는 파일이 **없을 때만**, 변환 **안에서** 읽는다(`src/codex/transform.ts:158-163`).

**설치자에게 생기는 일**: 구현이 설계 문장대로 "변환 뒤 절 교체" 로 가면, 앵커를 채웠던 설치자는 은퇴 update 다음의 **매번 첫 update** 에 `AGENTS.md.backup-<ts>` 를 하나 받는다(#550 · #557 이 없앤 형태). B-T4 는 "`*.backup-*` 1건"(앵커 백업)만 단언하므로 이 결함을 못 문다.

**넣을 문장(§B-3 머리 교체)**:
> B-3 은 두 토막이다. **(읽기 · 변환 전)** `readLegacyAntigravityContext(projectDir, log)` — 기록 `externalFiles` 에 앵커가 있을 때만 디스크 앵커의 `## Project Context` 설치자 줄(BLOCKER-2 규칙으로 하네스 줄을 뗀 뒤)을 돌려준다(없으면 `null`). `runAgentsMdTransform` 은 이 값을 `seed` 후보(루트 `CLAUDE.md` 다음 순위)로 받고, **파일이 없으면** seed 로 만들며, **파일이 있고 그 `## Project Context` 가 (BLOCKER-2 규칙으로) 손대지 않은 스캐폴드이면** `mergeAgentsMd` 가 그 절 본문을 seed 로 바꾼다(새 분기 — 지금은 디스크 절을 그대로 이어받는다, `agents-md-merge.ts:264-271`). 이미 채워져 있으면 바꾸지 않는다(ⓒ). 쓰기는 지금처럼 owned-write 한 번 — 기록 sha = 최종 바이트. **(지우기 · 변환 후)** 앵커를 `judge(remove)` 로 지우고(백업 규칙 그대로) 기록에서 빼며 `spec.clis` 를 적는다(BLOCKER-1). 회귀: B-T4 · B-T6 에 "**이어서 `update` 를 한 번 더 해도 `AGENTS.md.backup-*` 0건 · 화면에 `retired` 줄 없음**" 을 단언한다(C-T3 가 uninstall 재렌더에 거는 것과 같은 음성 대조).

## 2. NOTE (선택 개선 · 사실 정정)

### NOTE-1 — `segment()` 가 `[[hooks.SessionStart.hooks]]` 의 이름·경로를 부모와 같게 만든다 (§A.3.1 · §7-2 · A-T1)

`soloPath`(`src/adapters/toml-region.ts:101-112`)는 헤더 줄 하나를 파싱한 객체에서 **키가 하나인 표**만 따라 내려가고 배열을 만나면 멈춘다. `[[hooks.SessionStart.hooks]]` 한 줄은 `{hooks:{SessionStart:[{hooks:[{}]}]}}` 로 읽혀 `path = ["hooks","SessionStart"]`, `name = "[[hooks.SessionStart]]"` — **부모 항목과 같다**. 그래서 ① A-T1 의 "`kept` 가 두 이름을 모두 포함" 은 지금 이름 규칙으로는 `[[hooks.SessionStart]]` 두 번이 되고 ② 설계 화면 `kept yours: [[hooks.SessionStart]] · [[hooks.SessionStart.hooks]]` 가 나오지 않으며 ③ §7-2 의 "접두 판정" 은 두 항목의 경로가 같아 자명하게 통과한다(판정 자체는 `unchangedUnder` 가 자식만 들어가는 경우도 잡는다 — 자식만 더하면 `hooks[0]` 에 `SessionStart` 표가 생겨 값이 바뀐다). **넣을 문장**: "`soloPath` 는 헤더 항목에서 원소 하나뿐인 배열을 그 원소로 내려가 끝까지 따라간다(`[[a.b.c]]` → `["a","b","c"]`). `kept` 는 이름으로 중복을 걷는다." A-T1 은 그 뒤에 두 이름을 단언한다.

### NOTE-2 — `kept yours: [[hooks.SessionStart]]` 는 설치자에게 "네가 그 표를 가졌다" 로 읽힌다 (§A.3.1 화면)

#605 픽스처의 설치자는 `[[hooks]]` 를 가졌고 `SessionStart` 는 없다. 지금 문구 규칙(USAGE "where you already set the same key or table, yours wins")은 **같은 키가 있을 때** 참이다. 배열 표 항목이 "값이 바뀌어서" 빠질 때는 뜻이 다르다 — 하네스 훅이 배선되지 않았다는 사실을 설치자가 그 줄에서 읽어낼 근거가 없다. 선택: `kept` 와 별개 목록(`notAdded: would change your hooks table`)으로 한 줄 더 내거나, 지금처럼 두되 USAGE 의 그 행에 "or would change a table of yours" 한 구절을 더한다(설계가 "별도 줄 없음" 으로 결정한 것은 존중 — 다만 문서 한 구절은 공짜다). 참고: 그 픽스처의 `[[hooks]]`(배열) 는 Codex 스키마(`HooksToml` = 표, `hook_config.rs:20-27`)와 맞지 않아 **Codex 가 그 파일 전체를 거절**할 가능성이 크다 — 하네스가 고칠 일은 아니다(설계 §A.2 둘째 행 그대로). 구현 메모: `unchangedUnder` 의 깊은 동치는 `smol-toml` 의 `TomlDate` 를 값으로 비교해야 한다(객체 참조 비교면 날짜 키가 있는 설치자 파일에서 늘 "바뀜").

## 4. §6-1 은퇴(추천안) 가정 — 원칙·기존 설치본 위험

- **원칙**: 기록이 몫을 정하고(`externalFiles` 에 있을 때만 은퇴 — 디스크에만 있으면 설치자 파일, B-T7), 지우기는 `judge(remove)` 의 파일 단위 백업 규칙, 함께 쓰는 파일은 몫만 — 세 동작 모두 같은 함수. 루트 CLAUDE.md 원칙 · ADR-096(기록) · 097(판정 함수 · 파일 단위 백업) · 098(밖은 안 쓴다 — `OutsideGuard` 명시) · 099(은퇴는 "사라진 몫 되돌리기" 의 반대 방향이지만 **명시 결정**이고 기록에서 뺀다 — R2 와 충돌 없음) · 100(기록 커밋 — 은퇴 update 뒤 기록 diff 가 커밋 대상, 문서 한 줄 권장)과 어긋나는 곳은 못 찾았다. ADR-095 D6(앵커는 병합하지 않는다)은 ADR-103 이 amend 해야 한다(설계 §5 에 있음).
- **기존 설치본이 잃는 것**: 앵커를 채운 글은 (BLOCKER-2·3 반영 시) `AGENTS.md` 로 한 번 옮겨지고 원본은 백업으로 — 손실 0. 채우지 않은 앵커는 백업 없이 사라진다(기록 sha 그대로 — 원칙대로). **잃을 수 있는 것은 BLOCKER-1 의 "antigravity 가 깔렸다는 사실"** 하나다.
- **새로 생기는 것**: antigravity 단독 설치본에 전에 없던 루트 `AGENTS.md` 가 생긴다(ADR-100 뒤라 커밋 대상). 공식 문서가 권하는 자리이고 화면이 말하지만, USAGE §update 에 "antigravity 설치본은 첫 update 에 `AGENTS.md` 가 생긴다" 한 줄이 있어야 설치자가 놀라지 않는다(설계 §5 USAGE 항에 "은퇴 한 줄" 로 포함돼 있다 — 생성도 함께 적을 것).
- **혼합 설치의 이중 상주**(룰이 `AGENTS.md` 인라인 + `.agents/rules/`)는 설계가 감수로 적었고, 26.164.0 보다 줄어드는 방향이라 동의.
- "유지" 로 결정되면 §B 를 B1′ 로 다시 써야 하는데, 그 경우에도 BLOCKER-2 는 그대로 남는다(FILL 문구 변경이 원인).
