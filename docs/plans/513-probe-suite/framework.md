# #513 하네스 효과 측정 프레임워크 — 설계 (초안 · 2026-11-09)

**질문**: 하네스가 잘해야 한다고 주장하는 일마다(기능 추가 · 기술 선택 · 아키텍처 · 명확화 · 안전 …),
하네스를 깔면(B) 깔지 않았을 때(A)보다 결과가 나아지는가 — 모델 등급마다 · 판마다 같은 방법으로 다시 잴 수 있게.
**판정 기준 한 줄**: 새 하네스 판을 내기 전에 명령 하나로 "관점별 성적표(A 대비 B)"가 나오고, 그 표가 개선 후보를 가리키는가.

지금은 실행기가 둘(`run.py` = 자작 판단 과제 · `featbench/fb.py` = 실제 저장소 기능 구현)로 갈라져 있고,
결과 폴더 깊이 · 지표 · 집계가 서로 다르다. 관점을 늘릴 때마다 실행기를 새로 쓰지 않도록 공통 뼈대를 세운다.
측정 원칙(팔 · 등급 · 선별 → 확인 · 채점 규칙)은 `design.md` §3–§4 가 SSOT 이고 여기 옮겨 적지 않는다.

## 2. 구조 — 지금 실행기를 넓히고, 패키지 재배치는 세 번째 묶음이 실제로 필요할 때

`fb.py` 는 이미 `run.py` 의 제공자 · 지표를 가져다 쓴다. 두 실행기가 집계에서 갈리는 이유는 결과 경로 깊이 한 단계뿐이다.
그래서 새 뼈대를 세우고 결과를 옮기는 대신(새 측정이 0 인 작업) 아래만 한다(설계 검토 N6):
- 결과 경로를 `<out>/<model>/<task>/<variant>/<arm>-<rep>/result.json` 하나로 — FeatBench 에 variant 단(`main`)을 더한다. `report` 는 두 깊이를 다 읽어 옛 결과도 그대로 쓴다.
- 팔 준비(A 의 공통 CLAUDE.md · B 설치 · C 패치)와 지표 추출을 공유 모듈로 뺀다. 세 번째 묶음(SWE-bench)이 같은 실행기를 쓰면 그때 `suites/` 로 나눈다.

**과제 묶음이 채우는 계약**(실행기가 묻는 것 — 코드 배치와 별개로 지금부터 이 이름을 쓴다):

| 메서드 | 하는 일 |
|---|---|
| `tasks()` | 과제 ID · 변형(과제 내용은 비공개 위치에만) |
| `image(task)` / `workdir(task)` | 컨테이너 이미지와 그 안의 작업 사본 경로. 모든 묶음이 시작점(`probe-base`) 기준 `agent.patch` · `agent.files` 를 남긴다 |
| `context(task)` | 두 팔 공통 CLAUDE.md 의 목표 · 스택 문장 — B−A 에 "지시 파일이 있다는 것" 효과가 섞이지 않게 |
| `prompt(task, variant, stage)` | 요청 + 공통 STATUS 꼬리. stage 는 2단계 과제용 |
| `grader_files(task)` · `grade_cmd(task)` | 에이전트가 끝난 뒤 넣을 채점물과 컨테이너 안 채점 명령(None 이면 호스트 채점만) |
| `grade(task, run_dir)` | 공통 판정 `{pass, safety, valid, notes}` + 관점별 연속 지표 |
| `baselines(task)` | 정답 · 오답 정책(모델 호출 0) — 깨진 과제를 거른다 |
| `artifact(task, run_dir)` | 품질 판정자(Opus)에게 줄 과제 설명 + 결과물 diff |

**2단계 "다음 변경" 과제**(설계 검토 B4): 1단계는 A · B 가 각자 만든다. 2단계는 **두 팔의 1단계 산출물 위에서 같은 고정 실행자(A 팔 · 같은 모델)**가 돈다 —
2단계 실행자가 같으니 차이는 1단계 설계에서 온다. 지표 = 2단계 숨은 시험 + (1+2단계) 총 변경 줄. "2단계 diff 크기"만 보면 1단계에서 요청 밖으로 미리 넓힐수록
유리해져 앵커 §3 이 금지하는 투기적 확장에 상을 준다 — 1단계 범위 이탈은 사고 축에 따로 센다. 2단계 run_dir 은 1단계 run_dir 을 입력으로 받는다.

## 3. 측정 절차 — `design.md` §4 를 명령으로

**과제 고르기 = 공개 결과에서 상위 모델이 못 푼 문제**(사용자 제안 2026-11-09). 공개 벤치마크의 과제별 결과에서
우리 시험 모델 이상인 모델이 실패한 과제를 고른다 — 우리 팔(A · B)을 보지 않고 정하므로 독립 필터이고, 따로 거르는 실행이 필요 없다.
우리 설정의 A 는 여전히 같이 돌린다 — B 의 성공을 하네스 덕으로 돌리려면 같은 시각의 짝이 있어야 하고, 공개 결과의 "못 풂"은 다른 스캐폴드(Trae · Agentless)의 결과라 우리 설정의 바닥을 말해 주지 않는다.
이 선택에서 성적표의 효과는 "어렵지만 우리 설정으로 풀 수 있는 과제에서의 효과"다. 상위 모델 실패 과제에는 채점 깨짐(1 의 기준선이 거른다)과 정답 패치만 통과하는 과잉 명세 시험(기준선이 못 거른다)이 농축되는데, 2 의 "어느 팔이든 한 번은 푼 과제"가 뒤의 것을 거르는 실질 방어다.
자작 과제처럼 공개 결과가 없는 관점만 우리 A · B 합친 통과율로 고른다(`design.md` §4).

1. `eval.py baseline --suite S` — 과제마다 정답 · 오답 정책 채점(모델 0). 기대대로 안 갈리면 그 과제는 쓰지 않는다 — 모두가 못 푼 과제에는 채점이 깨진 것이 섞인다.
2. `eval.py run --suite S --arms A,B --reps 1` — 고른 과제에서 두 팔을 같은 시각에. 어느 팔이든 한 번이라도 푼 과제가 확인 대상이다.
3. `eval.py run --select <2의 결과> --reps 5` — 확인(새 시행 · 한 배치). 효과 판정은 여기서만.
4. `eval.py judge` — 품질 축이 필요한 관점만, Opus 5.5 고정 · 두 순서 · 이진 루브릭.
5. `eval.py report --scorecard` — 관점 × 등급 × 축 표. 축은 합산하지 않는다.

## 4. 북극성 지표로 쓰는 법

- **닻 묶음**: 관점마다 변별이 확인된 항목(확인 실행에서 갈린 것) + 천장이라도 회귀 감시가 필요한 안전 항목 몇 개를 고정한다.
  판마다 닻 묶음을 돌려 성적표를 남기고(`harness_version` 이 열), 새 항목 일부를 바꿔 넣어 과제에 맞춘 개선을 막는다.
- 하네스 변경 후보는 C 팔(후보 문구만 바꾼 하네스)로 같은 닻 묶음에서 먼저 잰다 — ADR-121 이 이 경로의 첫 사례다.
- 비용 상한: 등급 · 판마다 닻 묶음 1회 실행이 GLM 주간 한도 안에 들어가는 크기로 묶는다. 시행당 실측은 네트워크 격리 뒤 첫 실행으로 채운다(파일럿 수치는 정답을 내려받은 시행이라 쓰지 않는다).
- 닻 항목의 기준값은 고른 뒤 같은 판에서 **새로 돌린 첫 닻 실행**이다. 확인 실행 값은 선정 근거로만 기록한다 — 결과를 보고 고른 값은 과대라 다음 판이 이유 없이 "회귀"로 보인다.

## 5. 오염 · 공정성 경계

- 채점물(숨은 시험 · 정답 패치)은 에이전트 단계에 컨테이너 안에 없다 — 있으면 에이전트 단계가 멈춘다(음성 대조 rc=91).
- **에이전트 단계에는 인터넷이 없다.** 팔 준비 · 채점은 일반망, 에이전트 단계만 인터넷 경로 없는 내부망 + 모델 API 호스트 하나만 통과시키는 프록시. 시작 때 출구 점검(github · pypi)이 열려 있으면 멈춘다(음성 대조 rc=92 · 양성 대조 = 같은 망에서 pip · git clone 실패, 모델 호출 성공).
  근거: 격리 전 파일럿 3시행 모두 원 저장소의 PR diff · 수정 커밋 · 수정이 든 배포판을 내려받았다 — 상위 모델이 못 푼 과제일수록 이 경로가 결과를 뒤집는다.
- 모델 기억에 의한 오염은 별개로 남는다. 관점마다 자작 과제를 섞고, 공개 과제는 날짜가 늦은 것을 우선한다.
- 시작 때 이미지 안에 남은 것(pip · uv 캐시, git 객체)은 지운다 — 네트워크를 막아도 이미지에 든 수정 배포판은 못 막는다. 프록시가 거부한 호스트는 시행마다 기록한다(오염 *시도* 지표 · 막았다는 시행별 증거).
- 채점 재연결은 에이전트 단계 끝 표지(`t_end`)가 있을 때만.
- 과제 내용 · 채점기 · **결과 원본**(stream.jsonl · agent.patch — 에이전트가 환경 변수의 키를 볼 수 있어 섞일 수 있다)은 공개 저장소에 두지 않는다. 결과 요약과 설계만 이 디렉터리에.
- "비공개"는 공개 코퍼스 오염만 막는다 — 자작 과제 본문은 시행마다 모델 제공자(z.ai)로 간다.
