# Document Governance

문서가 "거짓 상태"가 되는 것을 막는 SSOT 규약.

## SSOT 위계 (한 사실은 한 곳)

| 문서 | 역할 | 갱신 시점 |
|---|---|---|
| `NORTH_STAR.md` | 왜·어디로 (비전·지표·Non-Goals) | 방향 전환 시만 |
| `SPEC.md` (+ `specs/`) | 무엇 (제품/기능 스펙) | 기능 정의/변경 |
| `PRD.md` | 문제·솔루션·요구사항 | 제품 방향 변경 |
| `TODO.md` (또는 `docs/todo.md`) | 다음 할 일 · 진행/완료 추적 | 작업 시작/완료 |
| `README.md` | 진입점 · 현재 상태(shipped/stack/배포) | 현재 상태 변동 |
| `docs/decisions/` | ADR (아키텍처·의존성·데이터모델·보안) | change-management 분류 |

- **역할표이지 없는 문서를 만들라는 지시가 아니다** — README 하나면 되는 프로젝트가 정상이다. 파일 위치는 프로젝트 레이아웃을 따르되(루트 또는 `docs/`) 역할·위계·동기화 의무는 불변.
- **충돌 시 상위 우선**(NORTH_STAR > SPEC). **같은 사실을 두 곳에 쓰지 않는다** — 한 곳에 두고 나머지는 링크로 가리킨다. 중복 서술 = drift 의 씨앗.
- 신규 기능은 SPEC 이 있는 프로젝트면 **등재가 먼저, 구현이 그 다음**(spec-first). 아키텍처·외부 의존성·데이터 모델·보안·breaking API 는 **ADR**(템플릿은 `change-management.md`).

## 작업 완료 처리 (merge = 코드 + 추적 동기화)

머지 직후 **같은 작업 단위로**: TODO 항목 → `[x] (✅ #PR번호)` · AC/Phase/Non-Goals/DO NOT CHANGE 에 영향 시 → SPEC Change Log · shipped 상태 변동 시 → README. 빠뜨리면 추적 SSOT 가 거짓이 되고 **다음 세션이 완료분을 backlog 로 오인해 중복 작업하거나 미완분을 완료로 오인해 건너뛴다.**

## 착수 전 baseline 대조 (Pre-flight)

앵커의 **원칙 1**("읽고 나서 쓴다")을 *문서가 미완이라 표기한 항목*에 적용한 것 — 착수 시점의 `[ ]` 는 "안 된 것"이 아니라 "모르는 것"이다.

**발동**(하나라도): 항목의 최종 수정 커밋 author 가 현재 작업자와 다름 · 그 커밋 이후 관련 코드 경로에 커밋이 있음 · 릴리스 경계를 넘겨 살아남음. **비적용**: 신규 프로젝트 · trivial · 이미 착수한 뒤. 대조는 **배치 진입 시 백로그 전체에 1회**, 항목이 지목하는 파일·심볼을 grep 한다.

| 상태 | 처리 |
|---|---|
| 완전 구현 | 문서를 완료로 정정 + **회귀 테스트만** 추가 (재구현 금지) |
| 부분 구현 | 잔여분만 task 로 남기고 재추정 |
| 미구현 · 판정 불가 | 계획대로 진행 — **못 찾았다고 착수를 보류하지 않는다** |

"완전 구현"에 심볼 존재만 쓰지 않는다(실행/테스트로 확인, 애매하면 **부분 구현**). UI 트랙이면 `benchmark-parity.md` 의 "**단순 존재 ≠ 완결**"이 같은 기준이고 다른 트랙엔 그 파일이 없어 이 줄이 SSOT. 승인 범위는 `change-management.md` CR 분류. 결과는 `- [ ] X (baseline 대조 YYYY-MM-DD: 기구현)` 로 인라인. **본 절은 프로즈이고 미준수를 잡는 게이트가 없다** — 스킵이 반복되면 게이트로 승격한다.

전례: 로드맵이 여러 PR 동안 미갱신돼 완료분이 미완으로 박제된 사례 — 상세는 ADR 로 위임한다.

## 현행 vs archive · 작성 원칙

현행 SSOT 만 루트/`docs/` 에 둔다. 히스토리(옛 버전·폐기 sub-spec·완료된 audit 산출물)는 `docs/archive/` 로 격리하고 지도 파일(`archive/README.md`) 하나로 찾게 한다. 현행 문서에 히스토리가 쌓이면 "지금 무엇이 맞는지" 읽는 비용이 히스토리에 비례해 커진다.

**why 중심으로 쓴다** — what 은 코드와 diff 가 보여준다. SPEC 이 800줄을 넘으면 기능별로 분리한다(`spec-scaling` 스킬).

## 검증 게이트

`.uzys-agent-harness/spec-drift-check.sh`(전 트랙 설치)가 SPEC/TODO 의 미완 잔존·Status 불일치를 검출한다 — **훅이 아니라 명시 호출**이다: 인자 없이 부르면 경고(exit 1), `ship` 인자면 차단(exit 2). 백로그는 `ship-gate:ignore` 구간만 면제된다(기본값은 검사 · 표식 짝이 깨지면 면제를 통째로 무시).

**한계를 알고 써라**: 탐지 경로(`docs/SPEC.md`·`docs/todo.md` 등) 밖의 문서 레이아웃은 게이트가 못 본다. 그 경우 본 규약은 프로즈로만 작동한다 — 안 지켜져도 아무도 안 막는다. 그게 확인되면 **게이트를 넓혀라, 프로즈를 늘리지 말고.**
