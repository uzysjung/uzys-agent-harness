# Apply Authorized Changes

## Confirm scope without repeating approval

Use the explicit request and valid recorded approvals. Named findings or a bounded
local improvement criterion can authorize edits where policy permits; an audit,
preview, or no-edit request stays read-only. Honor required exact-action / target
and destructive-operation approvals. Reuse existing specific approval while scope,
target, action, and material risk remain valid.

Revalidate changed sources and affected dependencies rather than restarting an
unchanged full audit. Check current wording and user worktree edits so the approved
patch still has the intended meaning. Continue independent authorized changes when
one finding remains unresolved; defer the disputed unit instead of the whole task.

## Preserve ownership and recovery

Identify project-owned prose, harness-owned assets, generated output, and managed
markers/imports. Modify the canonical editable source within authorization. Preserve
unrelated text, local customizations, headings, language, and formatting. Synchronize
mirrors only where ownership, synchronization contract, and scope are established.
When an installer would overwrite a local fix, report the source/integration change
needed; generator changes belong to a separately authorized task.

Keep removed content recoverable. Clean tracked content can use existing history;
dirty or untracked content needs an authorized snapshot. Store snapshots outside
discoverable rule/skill paths. This cleanup does not authorize commits, staging
unrelated changes, or remote state as a backup. Resolve unclear recovery or ownership
before that removal, while applying independent safe changes.

## Apply a coherent patch

Apply supported rewrite, narrow, supplement, merge, relocate, or retire decisions.
A supplement supplies only the missing actionable context supported by the finding.
An uncertain improvement remains a proposal unless a bounded trial is authorized;
trial evidence and permanent adoption are separate states. Preserve protected controls.

For relocation, establish the destination first, preserve factual and supersession
status, and retain current operational guidance plus a useful on-demand link at the
source. Keep the destination outside auto-loaded surfaces and usable after packaging.

For retirement, check callers, import/routing lines, bundled scripts and shared assets,
registrations, package inclusion, and gate dependencies. Remove or redirect authorized
prose references coherently. Retain resources still used elsewhere. If completion
requires application/installer code, permission/hook configuration, CI changes, or
other unapproved work, preserve the dependent unit and report the integration need.
Report a partial retirement as partial, with the outstanding dependency.

Maintain equivalent protected behavior when consolidating a duplicate statement.
Keep the safety instruction discoverable even when enforcement exists elsewhere.
Treat generic procedure according to its purpose and authority, not emphatic wording.
Mandatory test/review policy changes remain a separate decision, including during trials.

## Run an authorized bounded trial

Use this route when a material benefit is uncertain and a small reversible comparison
can resolve it. A trial needs explicit authorization for its scope and actions; a
request for feedback or guidance edits alone grants no permission to run representative
product work. Use an isolated non-production fixture and permitted tools/data.

Establish the question, unchanged acceptance criteria and safeguards, affected guidance,
allowed work/resource budget, and recoverable starting state. Reuse known information;
record only missing material conditions. Evaluation authorization must cover any task
execution or fixture edits, model calls, and data sharing actually needed. Keep live
product work, production state, and enforcement controls outside the trial.

Use existing representative tasks and checks rather than creating a benchmark system.
Read the [verification comparison criteria](verification.md#demonstrate-improvement-honestly)
when evaluating outcomes. Restore or revise trial-owned changes if quality falls,
material risk rises, or the expected benefit is absent; preserve unrelated user work.
When evidence supports adoption, apply it only within the approved adoption criteria
and configuration scope. Otherwise report the result and proposed decision. A permitted
trial is neither automatic adoption nor a reason to ask again when adoption was
already explicitly authorized on satisfied conditions.

## Check the result and stop

Inspect the diff for authorized scope, preserved meaning, unresolved conflicts, and
unrelated changes. Select document checks for the affected surfaces: links/imports,
frontmatter, package resources, and dependent routing where relevant. Complete
applicable required checks using actual project commands. Do not weaken a check or
its acceptance criteria to obtain a pass. Reuse valid results; run optional checks
where the patch invalidates evidence or creates a meaningful coverage gap.

Report each finding as applied, proposed, deferred, or superseded with a reason.
For trials, report trial status, observed results, restoration/adoption, and scope
separately. Distinguish file checks, product behavior not tested, and runtime loading
not observed. Required review remains pending when unavailable, rather than passed
by the author. Repeated application with unchanged evidence should leave valid text,
history, approvals, and optional validation unchanged.

Finish after the authorized patch and its checks. Report unrelated issues without
redesigning conventions or modifying their code. Revisit relevant findings when new
evidence warrants it; recurring audit hooks and blanket validation loops are outside
this cleanup.
