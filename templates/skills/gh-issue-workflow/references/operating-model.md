# 운영 원칙 — 무엇이 고정이고 무엇이 움직이는가

목표는 안 바뀌고, 묶음과 순서는 계속 바뀐다. 그 둘을 같은 자리에 두면 순서를 바꿀 때마다 목표가
흔들리거나, 목표를 지키려고 순서를 못 바꾸게 된다. 아래 일곱 줄은 **그 분리를 어디에 두는가**에
대한 것이고, 각 줄은 측정된 사실을 근거로 한다.

---

## P1. 층은 성질로 가른다 — 이력이 쌓이는 층엔 순서를 두지 않는다

| 층 | 실물 | 성질 | 바뀔 때 |
|---|---|---|---|
| **목표(북극성)** | 문서. 이슈가 아니다 | **고정** | 바뀌면 그건 다른 제품이다 |
| **이슈**(에픽·태스크) | Issue + 하위 이슈 | **축적** — 지우지 않는다 | 떼되 남긴다 |
| **묶음**(마일스톤·프로젝트) | Milestone / Projects v2 | **재편 자유** | 흔적 없이 바꾼다 |

**핵심은 세 번째 줄이 왜 자유로운가다: 거기에 이력이 없기 때문이다.** 마일스톤 설명란에
"이렇게 하기로 했다"를 적는 순간 그 마일스톤은 못 지우는 물건이 되고, 재편의 자유가 사라진다.

→ **결정은 이슈 본문에, 순서는 묶음에.** 묶음에는 이름·기한·소속만 둔다.

## P2. 본문 이력은 보존되지만 **보이지 않는다** — 보존과 실효는 다르다

실측(2026-08-17, 본문을 통째로 교체한 이슈 1건 대상):

| 조회 경로 | 이전 본문이 나오는가 |
|---|---|
| `gh issue view` · 웹 기본 화면 | ✗ 현재 판만 |
| REST 타임라인 (`/issues/N/timeline`) | ✗ **이벤트 0건** (`labeled`·`sub_issue_added`·`cross-referenced` 는 남는데 본문 편집은 안 남는다) |
| REST `/issues/N/edits` | ✗ 404 |
| GraphQL `issue.userContentEdits` | ✅ **전 판 전문**(`totalCount: 2`, `diff` 가 이전 본문 전체) |

기술적으로는 남는다. 그러나 **아무도 GraphQL 을 치지 않는다** — 리뷰어도, 다음 세션의 에이전트도,
6개월 뒤의 본인도. 그래서 실무 규율은 "보존된다"가 아니라 이것이다:

→ **본문을 교체할 때, 사라지면 안 되는 것은 본문 안에 남기거나 코멘트로 먼저 옮긴다.**
   특히 ⓐ 사용자 원문 요청 ⓑ 기각된 대안과 그 이유. 둘 다 나중에 "왜 이렇게 됐지"의 답이다.

## P3. 링크는 **도구가 만드는 것만** 산다

측정된 감쇠:

| 측정 | 값 | 출처 |
|---|---|---|
| 커밋이 이슈에 연결된 비율 (오픈소스 6개 평균) | **60%** | *Traceability in the Wild* — https://arxiv.org/abs/1804.02433 |
| 커밋 메시지 안 링크 중 접근 불가 | **34~43%** (distinct 기준 약 70%) | *18 Million Links in Commit Messages* — https://arxiv.org/abs/2305.16591 |
| 릴리스 아티팩트 중 추적 링크 없음 | **47%** (+ 12% 깨짐) | https://arxiv.org/abs/2511.18187 |

손으로 적은 URL 은 감쇠 대상이고, GitHub 이 **이벤트로 남기는** 형태는 아니다. 실측한 살아남는 형태:

| 남는 것 (타임라인 이벤트) | 만드는 법 |
|---|---|
| `sub_issue_added` | `gh issue create --parent N` · `gh issue edit E --add-sub-issue N` |
| `cross-referenced` | 다른 이슈·PR 본문/코멘트에 `#N` |
| `closed` (PR 연결 포함) | PR body 의 `Closes #N` |
| `labeled` · `milestoned` · `assigned` | 해당 gh 플래그 |

→ **추적성을 원하면 문장이 아니라 이벤트를 만들어라.** 본문에 "관련: <URL>" 을 적는 것은
   추적성이 아니라 메모다.

## P4. 순서는 세 축으로 나눠 적는다 — 셋은 **수명이 다르다**

| 축 | 무엇을 뜻하나 | 수명 | 재정렬 비용 |
|---|---|---|---|
| 라벨 `P0`/`P1`/`P2` | **오늘의 판단** | 짧다 | 0 — 마음껏 바꾼다 |
| 마일스톤 | **이번 묶음의 경계** | 중간 | 0 — 떼면 된다 |
| `blocked-by` | **사실** (A 없이는 B 를 판정할 수 없다) | 길다 | 높다 — 바뀌면 뭘 잘못 안 것이다 |

두 방향의 오용이 있고 둘 다 조용히 아프다:

- **우선순위를 `blocked-by` 로** 표현 → 재정렬할 때마다 의존 그래프를 수리해야 한다
- **진짜 의존을 라벨로** 표현 → 재정렬이 순서를 깨뜨려도 아무도 모른다

→ `gh issue list --json number,blockedBy` 에서 `blockedBy.totalCount == 0` 인 것만 남기면
   **순서** 축의 후보가 걸러진다. 이게 성립하려면 `blocked-by` 에 취향이 섞이면 안 된다.
   본문 `## 전제` 체크박스는 이 필터에 안 잡힌다 — 그 축은 `SKILL.md` §5 가 따로 본다.

## P5. 재편의 단위는 **떼기**이지 지우기가 아니다 — 그리고 개수로 확인한다

```bash
gh issue list --milestone "<이번 묶음>" --state all --json number | jq length   # ① 먼저 센다
gh issue edit <N> --remove-milestone                                          # WRITE
gh issue edit <EPIC> --remove-sub-issue <N>                                   # WRITE
gh issue comment <N> --body "이번 묶음에서 제외 — <사유>. 이슈는 열어 둔다."   # WRITE
# ③ 뺀 수 + 남은 수 == ①  ← 이게 맞을 때만 "정리했다"가 참이다
```

**"누락 없이 정리했다"는 개수가 맞을 때만 참인 문장이다.** 기억으로 하지 않는다.

## P6. 크기 — 계층도 백로그도 상한이 있다

| 상한 | 값 | 출처 |
|---|---|---|
| 하위 이슈 중첩 깊이 | **8단계** | GitHub |
| 부모 1개당 하위 이슈 | **100개** | GitHub |
| 활성 백로그 크기 | **50 내외** — 넘으면 하나 빼고 넣는다 | ⚠ **실무 경험칙(측정치 아님)** — 제품 관리 실무에서 널리 쓰이는 상한. 근거 연구 없음 |

100 에 닿았다면 한계가 문제가 아니라 **에픽이 너무 크다**는 신호다 — 중간 에픽으로 한 겹 나눈다.

참고 실측(GitHub 저장소 34곳 · 이슈 약 118,000건 — *Characterizing Issue Management in Runtime
Systems*, https://arxiv.org/abs/2310.15971): 라벨은 **82.65%** 에 붙지만 assignee 는 **28.30%**
뿐이고, **90.65%** 가 코멘트를 최소 1개 갖는다(닫히기까지 중앙값 **58일**). 모집단이 JVM 계열
런타임 저장소라 다른 생태계로 그대로 옮기지 못한다.

→ **판정 축은 라벨에 두고 assignee 에 기대지 마라.** 1인 + 에이전트 구성에서는 assignee 가
   아예 없는 축이다. 그리고 논의가 코멘트에 모인다는 것은 **결정도 거기 묻힌다**는 뜻이다(P2).

## P7. 묶음 이름은 **날짜가 아니라 확신도**로 짓는다

순서가 바뀔 것을 전제하면 날짜 이름은 곧 거짓이 된다. 그렇다고 이름을 고치면
`gh issue edit -m "<name>"` 이 **이름으로** 붙이므로 기존 스크립트·문서가 함께 깨진다.

확신도로 나누는 형태(Now / Next / Later)가 이 문제를 피한다:

| 묶음 | 뜻 | 안에 있는 것 |
|---|---|---|
| `now` | 해법까지 확정 | 방향성 `YYYY-MM-DD 확정` 인 이슈만 |
| `next` | 문제는 확정, 해법 미정 | 방향성 `OPEN` 이어도 된다 |
| `later` | 방향만 | AC 없이 배경만 있어도 된다 |

이름이 세 개뿐이면 재정렬은 **소속을 옮기는 일**이 되고 이름은 영원히 참이다.

## 이 원칙들이 서로 맞물리는 방식

목표는 안 움직이고(P1) · 이슈는 지워지지 않고(P5) · 그 사이의 묶음만 자유롭게 재편된다(P1·P7).
재편이 안전한 이유는 이력이 이슈 쪽에 이벤트로 박혀 있기 때문이고(P3), 그 이력이 실제로 읽히려면
결정이 본문에 있어야 한다(P2). 순서를 표현하는 세 축의 수명을 섞지 않으면(P4) 재정렬이
의존 관계를 조용히 깨뜨리지 않는다.

**한 줄로**: 바뀌는 것을 바뀌어도 되는 층에 두고, 바뀌면 안 되는 것은 이벤트로 박아 둔다.
