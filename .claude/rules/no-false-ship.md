# No False Ship (거짓출하 금지)

검증하지 않은 경로를 "작동한다"고 보고하는 것 = 거짓출하. 3회 재발로 본 rule 신설 (2026-06-11, 사용자 지시):

| 사례 | 내용 |
|------|------|
| v26.58~63 | silent drift — 광고 자산이 조용히 미설치 |
| v26.76.0 | `--with-openspec` 등 CLI 플래그 미등록 → 광고한 설치 명령이 크래시 |
| v26.78.0 | Understanding 카테고리 wizard 페이지 누락 → "wizard에서 선택" 보고는 거짓, agent-browser 무인지 설치. Docker 검증은 flag 경로만 수행 |
| v26.82.0 | `--version` 거짓 보고 — package.json 만 bump, `cli.ts` 하드코딩 VERSION(26.81.0) 잔존. npm 게시 패키지가 자기 버전을 틀리게 출력. v26.82.1 에서 package.json derive 로 동기화 자체 소멸 |
| v26.138.0 | **없는 릴리즈를 "배포 완료 · npm 라이브 · 3워크플로 green" 으로 보고.** PR #257 이 `package.json` 을 26.138.0 으로 bump 하고 CHANGELOG 항목까지 넣었으나 **태그를 안 밀어** 릴리즈 워크플로가 아예 안 돌았고 npm 게시도 없었다(137 → 139 건너뜀). 코드는 v26.139.0 에 포함돼 살아 있으니 **기능은 나갔고 그 버전 라벨의 릴리즈가 없었던 것** — 그래서 "동작한다"는 참인데 "배포됐다"가 거짓인, 구분이 어려운 형태였다. 기존 CHANGELOG 게이트가 **한 방향만** 봤다(`package.json → CHANGELOG` 는 검사, `CHANGELOG → 태그 → npm` 은 미검사). 적발 = 지표 재설계 중 돌린 적대적 검증 에이전트. **자기 릴리즈를 자기가 못 본 두 번째 사례**(첫째는 아래 v26.128.0~131.0) |

## 절대 원칙

**검증한 경로만 주장한다. 검증 못 한 경로는 "미검증"이라고 그대로 쓴다.**
"되어야 한다" / "될 것이다"는 ship 보고에서 금지. 추론·기대는 증거가 아니다.

## Surface Parity 의무 (자산/기능 추가·변경 시)

사용자 도달 경로를 **전부 열거**하고 각각 실행 증거를 확보한다:

1. **wizard interactive** — 해당 카테고리/옵션이 실제 페이지에 렌더되어 선택 가능한가
2. **비대화형 CLI flag** — `--with-*` / `--track` / `--cli` 경로
3. **문서 표기** — README / USAGE / COMPATIBILITY / CHANGELOG 의 광고 문구 = 실동작
4. **대상 CLI별** — claude / codex / opencode / antigravity 중 해당하는 것

**증거 = 실제 실행 산출물만**: 테스트 PASS 출력, Docker 시나리오 exit 0, `--help` 출력, 렌더된 화면. 한 경로의 증거를 다른 경로에 전용(예: flag PASS → "wizard 도 됨")하는 것 금지.

## 출하 보고 양식 (필수)

```
| 경로            | 증거                          | 상태      |
|-----------------|-------------------------------|-----------|
| wizard          | wizard-parity 테스트 PASS     | ✓         |
| CLI flag        | Docker scenario exit 0        | ✓         |
| 문서            | grep 광고문구 ↔ 실명령 일치   | ✓         |
| codex (해당 시) | —                             | 미검증    |
```

미검증 행이 있으면 보고에 그대로 노출. 숨기고 "완료" 선언 금지 (원칙 5 — 증거를 보고한다).

## Drift 구조 차단

동일 목록(카테고리/자산/flag)이 2곳 이상에 하드코딩되면: **derive 로 단일화**하거나 **exhaustiveness 테스트/init-throw 가드** 추가 없이 머지 금지. 주석 경고는 차단 수단으로 인정하지 않는다 (gen-compatibility·prompts.ts 2회 실패 전례).

### 게이트는 열거하지 말고 훑어라 (v26.115.0, 5회 재발 후)

표면을 하나 놓칠 때마다 **그 표면 전용 게이트를 하나 추가**하는 방식은 수렴하지 않는다 — 게이트가 커버하는 표면 목록 자체가 또 하나의 하드코딩 사본이 되고, 목록에 없는 표면이 다음 drift 서식지가 된다. 실증: llms.txt 는 v26.110.0 사후분석에서 drift 표면으로 **지목되고도** 게이트 0건으로 남았다.

| 사례 | 놓친 표면 | 그때의 대책 |
|------|-----------|-------------|
| v26.104.0 | COMPATIBILITY 수기 서문 | 서문 전용 regex 추가 |
| v26.106.0 | README.ko·REFERENCE·REQUIREMENTS·category-installer (제거 자산 광고) | 수기 스윕, 구조 차단은 F10 으로 연기 (**아직 미해결**) |
| v26.110.0 | 로드맵 수치·llms.txt | 로드맵 regex 추가, llms.txt 는 **미추가** |
| v26.113.0 | PRD 분류표 (C2/C3) | SOD 가 차단, 수기 정정 |
| v26.114.0 | PRD 분류표 — **직전 지적 직후 같은 파일** | 양방향 대조 테스트로 승격 |
| v26.126.0 | 위저드 라우터 update hint (skills 갱신 시작해놓고 문구는 그대로) | **derive 게이트** — update 를 실제로 돌려 건드린 디렉터리가 hint 에 있는지 (`render-hint-parity`) |

**원칙**: 문서 사실 게이트는 **파일 열거(enumeration)가 아니라 글롭(glob)** 으로 작성한다. 새 문서가 생겨도 게이트를 고칠 필요가 없어야 하고, 커버 목록을 사람이 기억해야 하면 그 게이트는 이미 실패한 것이다. 과거 기록은 경로 제외 또는 명시적 frozen 표식으로 면제하되, **면제는 표식이 있는 쪽**이어야 한다(기본값 = 검사).

**게이트 자신도 환경에 따라 달라지는 값을 하드코딩하지 않는다** (v26.128.0~131.0, 위 사례 표). 로컬 값과 하드코딩 값이 우연히 같으면 **로컬 테스트는 그 차이를 영원히 못 본다** — 그래서 그 버그가 4릴리즈를 살아남았다. 환경마다 달라지는 상수는 derive 하고, 불가능하면 판정 함수를 **다른 환경 레이아웃으로** 테스트한다(여기서는 CI 체크아웃 레이아웃을 temp dir 로 재현). 검사가 "로컬 한정"이라고 그 on/off 스위치까지 검증 면제인 것은 아니다 — 스위치가 고장나면 검사는 죽는 게 아니라 **오작동**한다.

## templates/ 는 배포물이다 (v26.128.0)

`templates/` 에 넣은 것은 npm 으로 나가 **낯선 사람의 프로젝트에 설치**된다. 룰이면 그 사람이 세션마다 토큰으로 부담한다. 그러니 여기엔 **일반화된 것만** 남긴다.

- **다른 프로젝트를 출처로 인용하지 않는다.** 유출 5건이 전부 같은 문장 형태였다 — "X 프로젝트의 실제 패턴을 일반화". 그 문장을 쓰는 순간 그 프로젝트의 구체 내용이 딸려 들어온다. 일반화했으면 결과만 적어라.
- **구체 좌표 금지** — 우리 릴리스 태그·ADR 번호·홈 경로·실제 GitHub 핸들은 설치자에게 가리키는 대상이 없다. `vX.Y.Z` · `ADR-0NN` · `<you>` 로.
- **이 리포의 사건 기록은 `.claude/` 사본에만.** 배포판에는 원칙만, 전례는 여기에.

게이트: `tests/templates-distribution-hygiene.test.ts` — 검사 범위를 **`package.json` 의 `files`(게시 계약)와 manifest 에서 derive** 한다. 새 자산·새 게시 경로가 생겨도 게이트를 고칠 필요가 없다. **`templates/` 만 보면 놓친다** — 소스 주석이 그대로 컴파일돼 `dist/` 로 나간 실제 사례가 있었고, 그때 "다 고쳤다"고 말할 뻔했다(생성물은 원본 `src/` 를 대신 본다). 한계는 정직하게 — 그 습관과 구체 좌표를 잡지 "모든 유출"을 잡지 못한다(고유명사 허용목록은 대문자 토큰 1,605종이라 기각).

전례(v26.127.0 게시본): 비공개 프로젝트의 실제 이슈 본문 30줄 · 또 다른 프로젝트명이 스킬 frontmatter 에 상주 · **`dist/` 번들에도 잔존**.

이 게이트를 만드는 동안 같은 실수를 세 번 더 했고, 셋 다 **음성 대조가 잡았다**:
1. 수기 grep 을 대소문자 구분으로 돌려 `Vantage` 2건을 놓치고 "잔여 0" 선언 → 게이트가 잡음.
2. 범위를 `templates/` 로만 잡아 `dist/` 유출을 놓침 → 게시 계약에서 derive 로 교체.
3. 형제 **디렉터리명 정확일치**만 검사해 짧은 형태(`GoalTrack` ⊂ `DYLD-GoalTrack`)를 통과시킴 → 조각 매칭 추가. **초록불이 무는지 확인하지 않았으면 그대로 실렸다.**

부수 교훈: git worktree 는 별도 프로젝트가 아니다(디렉터리명에 브랜치명이 섞여 흔한 영어 단어를 후보로 만든다). `.git` 이 파일이면 worktree — 제외한다.

## "미검증"에도 근거가 필요하다 (v26.127.0)

`미검증` 은 면죄부가 아니라 **주장**이다 — "확인할 수 없었다"도 틀릴 수 있고, 틀리면 할 수 있는 검증을 안 한 채 넘어간다. 미검증 칸에는 **왜 못 했는지 + 무엇이 풀리면 되는지**를 한 줄로 적는다. 그 줄을 못 쓰겠으면 미검증이 아니라 **미시도**다.

금지: "환경 제약상 불가" 같은 **주어 없는 불가 선언**. 무엇이 무엇을 막는지 쓴다.

전례 (v26.126.0): "update 에 비대화형 진입점이 없어 Docker 검증 불가"로 출하 보고. 실제로는 프롬프트가 2개뿐이고 `script(1)` 로 pty 를 붙이면 됐다 — 이미지에 이미 있던 도구다. 사용자 지적으로 재시도해 `scenario-update-skills` PASS. **"불가능"이 아니라 "지금 쓰는 러너로는 안 된다"였고, 그 차이가 곧 우회였다.**

## 초록불이 무는지부터 확인한다 (음성 대조, v26.127.0)

**한 번도 실패해본 적 없는 검증은 증거가 아니다.** 통과하는 검증은 "기능이 동작한다"와 "이 검증이 아무것도 안 본다"를 구분하지 못한다. 새 게이트·시나리오·테스트는 **고칠 대상을 일부러 되돌려 실패하는 것까지 보고** 증거로 쓴다.

음성 대조 자체의 유효성도 확인한다: **되돌린 코드가 빌드/타입체크를 통과했는가.** 빌드가 깨져서 난 실패는 "게이트가 잡았다"가 아니다. 전례: 되돌리기 mutation 이 문법 오류라 `&&` 단락으로 컨테이너가 안 돌았는데, 화면의 FAIL 을 게이트 동작으로 오독할 뻔했다 ([[feedback_verify_before_concluding]] 과 같은 계열 — 실패의 **이유**를 확인하지 않으면 실패도 증거가 아니다).

3. 본 rule 사례 표 + 메모리(`feedback_no_false_ship`)에 추가
