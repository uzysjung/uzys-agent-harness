# Readiness — 이슈가 에이전트에게 작동하는가

`SKILL.md` §준비도의 상세. 이 문서가 있는 이유는 "좋은 이슈를 쓰자"가 취향 논쟁으로 끝나기
때문이다 — **어떤 속성이 실제로 결과를 바꾸는지 측정된 값**이 있으면 논쟁이 필요 없다.

## 1. 근거

주 출처는 GitHub 이슈 3,180건과 그에 대응하는 에이전트 PR 을 짝지어, 이슈를 32개 기준으로
채점하고 **머지 여부를 예측**한 연구다(Random Forest, AUC 72% · precision 69.1% · recall 77.4%).
아래 수치는 각 축이 높을 때의 **머지율 차이**다.

- *What Makes a GitHub Issue Ready for Copilot?* — https://arxiv.org/abs/2512.21426
- GitHub 공식 지침 — https://docs.github.com/copilot/how-tos/agents/copilot-coding-agent/best-practices-for-using-copilot-to-work-on-tasks
- 이슈 품질의 고전 연구(사람 대상, 재현 절차·스택트레이스·테스트케이스가 가장 유용하나 가장 쓰기
  어렵다) — Bettenburg et al., *What Makes a Good Bug Report?*

**해석 주의**: 이 수치는 상관이지 인과가 아니고, 모집단은 공개 저장소의 Copilot PR 이다. 방향을
정하는 데는 충분하지만 "8.38%p 올랐다"를 이 저장소에서 재현할 수는 없다.

## 2. 올리는 축 (높을수록 머지율 ↑)

| 축 | 차이 | 이슈에서 이렇게 보인다 |
|---|---|---|
| **자족성** (self-contained) | **+16.7%p** | 링크를 안 따라가도 착수 가능. 필요한 요지가 본문에 있다 |
| **범위** (well-scoped) | **+16.4%p** | 한 PR 로 닫힌다. "그리고"로 이어붙은 목표가 없다 |
| **익숙한 작업** | +13.1%p | 이 코드베이스·생태계의 흔한 형태. 신규 발명이 아니다 |
| **기대·경계 동작 명시** | +10.7%p | 정상 경로 외에 예외·edge 를 최소 1개 적었다 |
| **모호성 회피** | +8.4%p | "개선"·"정리"·"최적화" 같은 판정 불가 동사가 없다 |
| **실행 가능한 입도** | +7.6%p | 단계로 쪼개져 있어 어디부터 손댈지 보인다 |
| **좌표 제공** | +6.4%p | 파일·모듈·심볼이 적혀 있다 |
| **해법 방향** | +6.1%p | "이렇게 가면 된다" 한 줄. 강제가 아니라 출발점 |

상위 둘이 나머지를 합친 것만큼 크다. **쪼개기와 자족성이 다른 무엇보다 먼저다.**

## 3. 내리는 축 — 글이 아니라 작업의 신호

| 축 | 차이 | 실제 의미 |
|---|---|---|
| **성능 고려** | **−33.8%p** | 성능 문제는 대개 측정·프로파일링이 먼저다. 에이전트 단독 범위 밖 |
| **환경·설정 서술** | −9.4%p | 재현에 특수 환경이 필요하다 = 에이전트가 그 환경을 못 만든다 |
| **외부 의존 강조** | −6.9%p | 외부 API·마이그레이션이 걸리면 저장소 안에서 안 끝난다 |
| **본문 길이** | 길이 단위당 −9~11% | 길수록 요지가 묻힌다 |

**이 넷을 글에서 지우는 것으로 대응하지 마라.** 앞의 셋은 *작업이 무겁다*는 진단이다 — 대응은
**쪼개거나 사람 레인으로 보내는 것**이다. 성능 얘기를 지운 이슈는 준비된 이슈가 아니라 함정이다.

넷째(길이)만 글의 문제다. 필요한 축을 채우고 **남는 서술을 지운다** — 축을 지워서 짧게 만들면
자족성이 같이 떨어진다.

## 4. 등록 전 체크 (SKILL.md 의 8줄 확장)

```
[ ] 범위     한 PR 로 닫히는가. "그리고"가 목표에 있으면 쪼갠다
[ ] 자족     이 본문만 읽고 착수 가능한가. 링크 뒤 요지는 옮겨 적는다
[ ] 모호성   판정 불가 동사(개선/정리/최적화/고도화)가 0인가
[ ] AC       When → Then 이 pass/fail 로 갈리는가. "잘 동작함"은 AC 가 아니다
[ ] 좌표     건드릴 파일·모듈·심볼이 적혀 있는가
[ ] 경계     예외·edge 를 최소 1개 적었는가
[ ] 길이     위를 채운 뒤 남는 서술을 지웠는가
[ ] 무게     성능·환경·외부 의존이 본문의 축이면 → 쪼개거나 사람 레인
```

일곱 줄을 못 채우면 그건 **이슈가 아니라 메모**다. 메모는 메모라고 적고 에픽 본문의
`## 후속 작업` 에 한 줄로 남긴다 — 반쯤 채운 이슈를 양산하면 목록이 신뢰를 잃는다.

## 5. 작업 종류별 적합도

GitHub 공식 지침이 밝힌 갈림. **잘 맞는 것**: 버그 수정 · 테스트 추가 · 문서 갱신 · 접근성 개선 ·
좁은 UI 변경 · 작은 기술부채. **사람이 낫다**: 저장소를 넘나드는 변경 · 깊은 도메인 판단 ·
큰 리팩터(일관성 설계가 필요) · 보안/인증/장애 대응 · 요구가 열려 있어 반복 탐색이 필요한 일 ·
**배우려고 하는 일**.

마지막 항목은 품질 문제가 아니다 — 이해를 얻는 게 목적이면 위임이 목적을 없앤다.

## 6. 나쁜 이슈 → 준비된 이슈 (같은 내용)

**전**

```
## 배경
로그인이 가끔 안 됨. 확인해서 고쳐주세요.
```

준비도: 범위 ✗ · 자족 ✗ · 모호성 ✗ · AC ✗ · 좌표 ✗ · 경계 ✗ → 착수 불가.

**후**

```
## 배경
세션 만료 직후 로그인하면 401 이 뜨고 로그인 화면으로 되돌아온다. 재시도하면 성공한다.
만료 갱신 경로에서 옛 토큰을 한 번 더 쓰는 것으로 보인다.

## 전제 (Given)
- [x] 재현: 세션 TTL 을 60s 로 낮추고 만료 후 로그인

## 방향성 (2026-08-17 확정)
- 갱신 실패 시 **저장된 토큰을 먼저 폐기**하고 재인증한다 (재시도 루프 추가는 기각 — 증상만 가린다)

## 적용 대상 / AC
- `src/auth/session.ts` 의 `refresh()` · `src/auth/client.ts` 의 인터셉터
- [ ] 만료 토큰으로 로그인 → 401 없이 1회에 성공 (When 만료 후 로그인 → Then 200)
- [ ] 갱신 중 네트워크 실패 → 저장 토큰이 남지 않는다 (경계)
- [ ] 위 둘을 고정하는 회귀 테스트가 변경 없이는 red

## 후속 작업
- [ ] 동시 갱신 요청 합치기는 #M 으로 분리 — 이번 범위 밖
```

바뀐 것은 분량이 아니라 **판정 가능성**이다. 두 번째는 다 읽고 나면 무엇을 하면 끝인지 안다.
